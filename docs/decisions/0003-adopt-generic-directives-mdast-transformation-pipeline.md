# 0003: Generic DirectivesとmdastによるMarkdown変換パイプラインを採用する

- 状態: 採用
- 決定日: 2026-08-22

## 背景

`clono`は、独自記法を含むMarkdownを構造として解析し、Vivliostyleが処理できる文書へ安全に変換することを目的としている。前身のビルドスクリプトでは正規表現による文字列置換を使用していたため、コード例の誤変換、変換規則同士の干渉、処理順序の複雑化といった問題が生じる可能性があった。

[プロジェクト憲章](../project-charter.md)では、独自記法の第一候補をGeneric Directives Proposalに基づく記法とし、ASTなどの構造化表現を介して変換する方針を定めている。また、Vivliostyleが担える処理を再実装せず、`clono`は入力文書の解析、意味検証、情報の収集と解決、後段で扱える文書への変換を担う。

この方針を実装へ移す前に、Generic Directivesをmdastへ解析できること、ClojureScriptからASTを操作できること、意味検証と用途別の変換を分離できること、VFMが処理できるMarkdownへ直列化できることを検証した。その結果をもとに、初期の著者向け構文、内部表現、変換パイプライン、主要な出力形式を決定する必要がある。

将来のプラグインシステムは重要な設計上の方向性である。一方、外部プラグインの読み込み、公開API、変換順序、依存関係、状態共有にはまだ具体的な要件が不足している。初期実装ではThunder Clawの次回作に必要な変換を優先しながら、組み込み処理だけが特権的な構造へ依存しない境界を設ける必要がある。

## 決定

### 著者向け構文

`clono`の独自記法には、[Generic Directives Proposal](https://talk.commonmark.org/t/generic-directives-plugins-syntax/444)に基づく構文を採用する。

ブロック範囲、単独ブロック、インライン指定を、それぞれContainer directive、Leaf directive、Text directiveで表現する。具体的なdirective名、属性、内容モデルと、各用途で使用するdirectiveの種類は、個別機能の仕様で決定する。

### 内部表現と採用ライブラリ

Markdownの構造化表現にはmdastを採用する。初期実装では、mdastをJavaScriptオブジェクトのままClojureScriptから参照および変更し、AST全体をClojureScriptの永続データ構造へ変換しない。

解析と直列化には、次の低レベルAPIを直接使用する。

- Markdownからmdastへの解析: `mdast-util-from-markdown`
- mdastからMarkdownへの直列化: `mdast-util-to-markdown`
- Generic Directivesの構文解析: `micromark-extension-directive`
- Generic Directivesのmdast変換と直列化: `mdast-util-directive`

初期実装では、`unified`、`remark-parse`、`remark-directive`を`clono`自身の変換パイプラインへ直接採用しない。将来これらを採用できるよう、解析と直列化を変換規則から分離する。

脚注など、入力に含まれるMarkdown拡張を専用のmdastノードとして保持する必要がある場合は、解析と直列化の両方へ対応する拡張を追加する。初期実装では、VFMで使用するGFM形式の脚注を保持するため、`micromark-extension-gfm-footnote`と`mdast-util-gfm-footnote`を使用する。

採用ライブラリと役割はこのADRで管理する。正確なバージョンは`package.json`と`package-lock.json`で固定する。

### 変換パイプライン

単一のMarkdown文書に対する基本的な変換を、次の段階に分ける。

```text
入力Markdown
  → mdastへの解析
  → 既知directiveの意味検証
  → AST変換
  → VFM向けMarkdownへの直列化
```

構文の解析、意味検証、AST変換、直列化は、それぞれ独立した責務として扱う。意味検証ではASTを変更せず、文書全体を検査する。エラーが一件でもある場合はAST変換を実行せず、部分的な出力Markdownも返さない。

組み込みの変換規則は、対象となるdirective名、許可するmdastノード型、意味検証、AST変換を対応付けられる内部境界を通して扱う。パーサー自身や単一の分岐処理へ、すべての変換規則を不可分に埋め込まない。内部境界の具体的なAPIは、実際の組み込み機能を実装しながら決定する。

### 未知のdirective

初期仕様では、読み込まれた組み込み規則または将来のプラグインによって登録されていないdirectiveをエラーとする。未知のdirectiveが一つでもあれば、既知のdirectiveに意味上の誤りがある場合と同様に、出力Markdownを生成しない。

既知かどうかの判定は、構文解析や個別の変換処理から分離する。将来、未知のdirectiveを警告しながら保持する方針、または警告せず保持する方針へ変更できる構造とするが、使用しない設定項目やCLIオプションは初期実装で先行して公開しない。

### 診断

既知のdirectiveに意味上の誤りがある場合と、未知のdirectiveを検出した場合は、可能な範囲で文書全体の問題を収集する。診断には最低限、次の情報を含める。

- 入力ファイル名
- 開始位置の行
- 開始位置の列
- directive名
- 問題の説明

診断コード、重要度、最終的な表示形式は、このADRでは決定しない。

### 出力形式とVivliostyleとの責務分担

`clono`の主要な出力形式には、VFMが処理できるMarkdownを採用する。`clono`は完成したHTMLを主要出力として生成せず、MarkdownからHTMLへの変換と組版をVivliostyleへ委譲する。

既存のMarkdownで表現できる構造は可能な限りMarkdownとして保持する。VFMへ渡すためにHTML構造が必要な箇所では、既知のdirectiveをmdastのraw HTMLノードへ変換し、標準Markdownと共存させる。動的な値をHTMLへ埋め込む場合は、出力先に応じて必要なエスケープを行う。

入力と出力のMarkdownには、空白、改行、属性値の引用方法などの文字列としての完全一致を要求しない。通常のMarkdownと、変換対象外として保持する構造について、再解析可能な意味と構造を保持する。

## 理由

- Generic Directivesの三種類で、`clono`が必要とするブロック範囲、単独ブロック、インライン指定を表現できる
- directive名が増えても用途ごとのパーサーを追加せず、同じ構文から生成したmdastを意味検証と変換の対象にできる
- mdastのノード型を使用することで、コードフェンスなどの変換対象外の構造を文字列置換より安全に区別できる
- mdastにはdirectiveの名前、属性、子要素、入力位置が保持され、ClojureScriptから直接操作できる
- 低レベルAPIだけで初期の解析、意味検証、変換、直列化を構成でき、現時点で`unified`の処理パイプラインを追加する具体的な必要性が確認されていない
- 独自の内部境界を設けることで、組み込み変換を実例として育ててから、必要な部分だけを将来のプラグインAPIとして公開できる
- VFM向けMarkdownを出力することで、標準MarkdownとVFMの機能を維持しながら、HTML変換と組版をVivliostyleへ委譲できる
- 既知の不正なdirectiveと未知のdirectiveを出力前にエラーとすることで、書籍制作に使用できない部分的な変換結果や、タイプミスを通常テキストとして残すことを防げる

## 技術検証

[Generic DirectivesとMarkdown ASTに関する調査](../research/markdown-ast.md)では、Generic Directivesの三種類が専用のmdastノードになり、名前、属性、子要素、入力位置をClojureScriptから参照できることを確認した。通常のMarkdown構造を保持した往復変換、未知のdirectiveの意味的保持、コードフェンス内の記法を変換対象にしないことも確認した。

[Markdown AST変換と出力方式に関する調査](../research/markdown-ast-transformation.md)では、解析、意味検証、AST変換、Markdown直列化を低レベルAPIで構成した。既知の不正なdirectiveがある場合に出力を生成せず、通常のMarkdown、コードフェンス、脚注を保持したまま、既知のdirectiveをraw HTMLへ変換できた。生成したMarkdownはVFM 2.7.0でHTMLへ変換できた。

これらの検証で使用した正確なライブラリバージョン、入力、期待結果、再現手順は、それぞれの調査記録とfixtureに保存する。

## 比較した候補

### 独自の構文とパーサー

Generic Directivesとは異なる独自構文を採用する場合、別の構文解析ライブラリまたは自前のパーサーが必要になる。既存のMarkdown構造との衝突やコード例の保護も`clono`側で扱う必要があり、現時点でそのコストに見合う要件がないため採用しない。

### 正規表現による文字列置換

前身のビルドスクリプトで成立した方式であり、小規模な変換は容易に追加できる。一方、Markdownの構造を認識せず、コード例の誤変換、変換規則同士の干渉、処理順序の複雑化を招くため採用しない。

### `unified`およびremarkの処理パイプライン

既存のプラグインエコシステムと、処理を段階的に構成する仕組みを利用できる。一方、将来の`clono`プラグインには、モジュールの読み込み、変換規則の登録、診断、文書全体の状態共有、互換性など、unifiedとは別に設計すべき責務がある。

初期の変換は低レベルAPIだけで成立し、既存のremarkプラグインを再利用する具体的な要件もないため、現時点では直接採用しない。

### 完成したHTMLを主要出力とする方式

変換結果をHTMLとして完全に制御できる一方、標準MarkdownとVFMが既に担えるHTML変換を`clono`側で再実装する範囲が広くなる。Vivliostyleとの責務分担に合わないため、主要出力には採用しない。

### mdast全体をClojureScriptのデータ構造へ変換する方式

ClojureScriptの標準的なデータ操作を適用しやすくなる一方、JavaScriptライブラリとの境界で相互変換が必要になり、ノードの同一性や変更の反映も考慮する必要がある。JavaScriptオブジェクトのままで必要な操作を実現できたため、初期実装では採用しない。

### 未知のdirectiveを保持する方式

ほかのツールとの組み合わせや、将来の拡張に利用できる。調査では、名前、属性、内容を再解析できる意味的保持が可能であることを確認した。

一方、VFM自身はGeneric Directivesを解釈せず、未知のdirectiveを通常テキストとしてHTMLへ出力する。また、Thunder Clawの次回作では、未知のdirectiveはタイプミスまたは変換規則の登録漏れである可能性が高い。初期仕様では安全性を優先してエラーとし、保持する方針は具体的な連携要件が生じた場合に追加する。

## 影響

- Generic Directives、mdast、必要なMarkdown拡張を扱うライブラリがproduction依存関係へ追加される
- 構文拡張は、解析と直列化の両方へ対応する設定を追加する必要がある
- 変換後のMarkdownでは、元の空白、改行、属性値の表現などが正規化される可能性がある
- 変換規則は、構文解析とは分離し、意味検証とAST変換を対応付けられる内部境界を通して追加する
- 外部プラグインを導入する場合は、プラグインを読み込んで変換規則を登録した後に、未知のdirectiveを判定する必要がある
- 初期仕様では、ほかのツールが処理するGeneric Directivesを同じ入力に含めるとエラーになる
- raw HTMLを生成する変換では、動的な値のエスケープと、VFM変換後の構造をテストする必要がある
- 完成したHTMLを主要出力として必要とする用途には、この決定だけでは対応しない

## 未確認事項

- 個別機能のdirective名、属性、内容モデル
- 変換後のHTML要素、class名、属性
- ASTの走査と変換規則の登録に使用する内部API
- 外部プラグインの公開API、探索、読み込み順序、依存関係、互換性、安全性
- 複数原稿をまたぐ情報の収集、解決、状態共有の方式
- 未知のdirectiveを警告または保持する設定の提供時期と公開方法
- 未知のdirective内部にある既知のdirectiveの扱い
- Generic Directivesとして認識されない構文誤りの検出
- 診断コード、重要度、最終的な表示形式
- 変換後のMarkdownと元の入力を対応付けるsource map
- ファイル出力の原子性
- 生成Markdownの整形方針
- Thunder Clawの実原稿で必要となる脚注以外のMarkdown拡張
- 完成したHTMLを副次的な出力形式として提供する必要性

## 見直す条件

次のいずれかが生じた場合は、この決定の該当部分を見直す。

- Generic Directivesでは必要な著者向け記法を、安全かつ実用的に表現できない場合
- mdastまたはmicromark関連ライブラリの変更により、必要な構造や入力位置を保持できなくなった場合
- JavaScriptオブジェクトをClojureScriptから直接操作することが、実際の変換処理で保守上の問題となった場合
- 既存のremarkプラグインを再利用する具体的な必要性が生じた場合
- 変換段階、変換順序、状態共有の管理が、低レベルAPIを使用する独自のパイプラインでは複雑になった場合
- 将来のプラグインAPIに、今回の内部表現または処理方式が適さないと判明した場合
- 未知のdirectiveを保持しなければ、必要な外部ツールとの連携を実現できない場合
- VFM向けMarkdownでは、必要なVivliostyle機能または後段ツールとの連携要件を満たせない場合
- 必要なMarkdown構造が解析または直列化によって失われる場合
