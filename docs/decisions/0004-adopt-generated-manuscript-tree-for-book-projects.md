# 0004: 書籍プロジェクトを生成済み原稿ツリーへ変換する

- 状態: 採用
- 決定日: 2026-08-25
- 最終更新日: 2026-08-31

## 背景

clono 0.2.0は、一つのMarkdownファイルをVFMが処理できるMarkdownへ変換する。一方、Thunder Clawの書籍制作では、前付、本文、付録、索引および後付を構成する複数の原稿を一定の順序で変換し、画像やHTMLなどの静的ファイルとともにVivliostyleへ渡す必要がある。

前身のビルドスクリプトは、Markdownだけを格納した入力ディレクトリから、同じ階層にある別のディレクトリへ変換済みMarkdownを出力していた。この方式では、両方のディレクトリ外に置いた画像などの相対パスを維持できる。しかし、原稿ツリー内に静的ファイルを置く構成では参照先が生成物に含まれず、正しく動作するディレクトリ配置が暗黙の前提になる。

書籍プロジェクト全体を複製する方式では、設定、テーマ、依存関係、キャッシュおよびPDFなど、clonoが管理する必要のないファイルまでコピー対象の判断が必要になる。clonoは書籍プロジェクトの同期ツールやVivliostyleの代替を目的としていないため、変換に必要な範囲を明確にする必要がある。

書籍プロジェクト変換は、CI上の空の作業環境で繰り返し実行される。一方、利用者が出力先を誤って指定した場合に、既存の重要なディレクトリを削除または置換してはならない。複数の原稿をすべて変換できた場合だけ新しい生成物を公開し、並行するビルドとの競合も検出する必要がある。

文字揃え、コラム、強制改ページなど、clonoが生成するHTML構造の一部は、npmパッケージ内の`styles/clono.css`にある基盤CSSを必要とする。書籍固有の利用者テーマから既定値を上書きできる状態を保ちながら、実行中のclonoと対応する基盤CSSをWebPubとPDFへ確実に適用する方法も決定する必要がある。

## 決定

### 設定と書籍構造

書籍プロジェクトのルートに`clono.config.mjs`を置き、ECMAScript Moduleのdefault exportとして設定オブジェクトを定義する。

設定には、入力原稿ルート、生成済み原稿ルートおよび書籍を構成する要素の掲載順を明示する。書籍構造の各要素は`type`を持つ。`document`は原稿パス、前付・本文・付録・後付の文書種別、および目次への掲載有無を持ち、`blank-page`は原稿間へ一ページ挿入する空白ページを表す。これらに暗黙の既定値を設けない。

原稿順序と文書種別の正本は`clono.config.mjs`とする。`vivliostyle.config.mjs`はこの設定をimportし、Vivliostyle CLIの`entry`などへ必要な形で変換する。同じ原稿一覧を両方の設定へ重複して記述しない。

`clono.config.mjs`は通常のJavaScriptとして実行し、サンドボックス化しない。利用者は信頼できる書籍プロジェクトの設定だけを実行する。

設定項目、値、パスおよび診断の詳細な契約は、[書籍プロジェクト仕様](../specifications/book-project.md)で管理する。

### 生成済み原稿ツリー

clonoは、入力原稿ツリーを相対パスの対応する生成済み原稿ツリーへミラーする。

- Markdownにはclonoの変換パイプラインを適用する
- HTML、画像など、その他の通常ファイルは内容を変えずコピーする
- ディレクトリ構造とファイル間の相対関係を維持する
- 書籍構造に空白ページが含まれる場合は、共通の空白ページHTMLを`_clono/pages/blank-page.html`へ生成する
- シンボリックリンクとその他の特殊なファイルは初期仕様で扱わず、検出した場合はエラーにする
- Vivliostyle設定、利用者テーマ、依存関係などは入力原稿ツリー外で管理し、書籍プロジェクト全体を複製しない

変換済みMarkdown、通過HTMLおよび静的ファイルからWebPubまたはPDFを生成する処理はVivliostyleへ委譲する。

### 出力先の保護

生成済み原稿ツリーのルートに`.clono-output.json`を置き、clonoが管理する出力であること、マーカー形式、入力原稿ルートおよび生成済み原稿ルートを記録する。

出力先が存在しない場合は作成し、空のディレクトリはclonoの管理対象として初期化する。一致する所有マーカーを持つ既存出力は再生成できる。所有マーカーのない空でないディレクトリ、または不正・不一致の所有マーカーを持つディレクトリは変更せずエラーにする。

すべての変換、コピーおよび検証をstagingディレクトリで完了してから、新しい生成物を正式な出力先へ公開する。公開前に出力先ごとの排他ロックを取得し、取得後に出力先の状態と所有マーカーを再確認する。並行する別のclonoプロセスが同じ出力先を扱っている場合は、既存出力を変更せずエラーにする。

所有マーカーと排他ロックは、誤指定と同じ規約に従うプロセス間の競合を防ぐための仕組みである。悪意ある利用者、ロックを無視する外部プロセス、プロセスの強制終了、OSまたはファイルシステムの障害に対するセキュリティ境界や完全な原子性とはしない。

### clono基盤CSSと利用者テーマ

`clono build`は、著者向け記法の使用状況にかかわらず、実行中のclonoに同梱された`styles/clono.css`を、生成済み原稿ツリーの次の固定パスへコピーする。

```text
_clono/styles/clono.css
```

`_clono/`はclonoの予約領域とし、入力原稿ツリー直下の同名パスと衝突する場合は、利用者の内容を上書きせずエラーにする。

利用者テーマは`clono.config.mjs`へ記述せず、`vivliostyle.config.mjs`で管理する。Vivliostyle設定ではclono基盤CSSを先、利用者テーマを後に指定する。初期仕様では、この設定を生成する機能や、clono設定をVivliostyle設定へ変換するヘルパーを提供しない。

clonoが生成するHTML構造には用途を示す固定classを付け、インラインスタイルを使用しない。基盤CSSは機能上必要な規則だけをclassセレクターで定義し、IDセレクターと`!important`を使用しない。これにより、通常のCSSカスケードに従って利用者テーマから上書きできる構造を維持する。

空白ページHTMLには名前付きページ`clono-blank`を使用する固定classを付ける。基盤CSSは指定一件につき一ページを生成するための構造までを担い、空白ページで残すノンブルと非表示にする柱は、利用者テーマの`@page clono-blank`で指定する。

### CLI

単一ファイル変換と書籍プロジェクト変換を相互排他的なオプションではなく、異なるサブコマンドとして扱う。

```text
clono transform <input> --output <output>
clono build
clono build <project>
```

決定時点の`clono <input> --output <output>`は`transform`サブコマンドへ移行する。npm公開前かつ実利用前であるため、旧形式との後方互換性は維持しない。

## 理由

- 入力原稿ツリーだけをミラーすることで、原稿と静的ファイルの相対関係を維持しながら、書籍プロジェクト全体の同期をclonoの責務に含めずに済む
- 書籍構造を一つの設定へ集約することで、変換対象、原稿順序、文書種別および目次掲載方針の二重管理を避けられる
- 空白ページを原稿内の記法ではなく書籍構造の要素とすることで、先頭、末尾および連続する位置を原稿順序として明示できる
- JavaScriptモジュールを設定に用いることで、clonoとVivliostyle設定の両方から同じ書籍構造を参照できる
- 存在しない出力先を作成できるため、CI上の空の作業環境で利用できる
- 所有マーカーにより、clonoが再生成してよい出力と利用者が管理するディレクトリを区別できる
- stagingと排他ロックにより、不完全な複数ファイル出力の公開と、同じ規約に従う並行ビルドによる競合を防げる
- 基盤CSSを生成済み原稿ツリーへコピーすることで、実行中のclonoとCSSのバージョンが一致し、Vivliostyleによるテーマパッケージの追加導入を避けられる
- 利用者テーマをVivliostyle設定へ残すことで、Vivliostyleが既に持つテーマ機能をclonoへ再実装せずに済む
- 固定class、低い詳細度および`!important`を使用しない基盤CSSにより、書籍固有のテーマから既定値を上書きしやすい
- サブコマンドに分けることで、単一ファイルと書籍プロジェクトで異なる引数、設定および出力契約を明確にできる

## 技術検証

[書籍プロジェクトの生成済み原稿ツリーに関する調査](../research/book-project-output-tree.md)では、Markdownと通常ファイルを相対パスのまま生成済み原稿ツリーへ出力し、同じ書籍構造を変換処理とVivliostyle設定から参照できることを確認した。所有マーカー、stagingおよび排他ロックを用いて、既存の所有済み出力を再生成し、所有していない出力と並行ビルドを既存内容の変更なしに拒否できた。

[Vivliostyleにおけるclono基盤CSSと利用者テーマの統合に関する調査](../research/vivliostyle-clono-stylesheet.md)では、npmパッケージをVivliostyleテーマとして読み込む方式と、基盤CSSを生成済み原稿ツリーの可視な予約領域へコピーする方式の両方が、WebPubとPDFで成立した。後者では追加のテーマパッケージ導入を必要とせず、基盤CSSを利用者テーマより先に適用し、利用者テーマから既定の文字揃えを上書きできた。

[Vivliostyleの空白ページに関する調査](../research/vivliostyle-blank-pages.md)では、共通のHTML資材を独立した`entry`として複数回参照し、各参照へ一意な`output`を割り当てることで、書籍の先頭、末尾および連続する位置へ指定一件につき一ページを挿入できた。名前付きページと利用者テーマにより、ページ番号を連続させたまま通常の柱を非表示にできた。

正確な検証環境、入力、依存関係、期待結果および再現手順は、各調査記録とfixtureに保存する。

## 比較した候補

### Markdownだけを別ディレクトリへ出力する

前身のビルドスクリプトで実績があり、入力と出力を同じ階層の兄弟ディレクトリに置けば、両方の外側にある画像などの相対パスを維持できる。一方、原稿ツリー内の静的ファイルが生成物へ含まれず、利用可能な配置に暗黙の制約が生じるため、標準方式には採用しない。

### 書籍プロジェクト全体を複製する

変換結果だけで独立した書籍プロジェクトを構成できる。一方、設定、テーマ、依存関係、キャッシュおよび既存生成物までコピー範囲と除外規則の対象になり、書籍プロジェクトの同期がclonoの責務へ加わるため採用しない。

### 入力原稿をその場で更新する

別の出力ツリーを必要としない一方、変換前の正本を変更し、失敗時の復旧やGit差分の分離を難しくする。変換前の原稿と生成物を明確に分ける方針に合わないため採用しない。

### Vivliostyle設定を書籍構造の正本にする

設定ファイルを一つにできる一方、clono固有の入力原稿ルート、生成済み原稿ルート、将来の生成文書などをVivliostyle設定へ持ち込むことになる。clonoが必要とする入力契約をVivliostyleの設定形式へ依存させず、Vivliostyle設定からclono設定をimportできるため採用しない。

### 所有確認なしで出力先を再生成する

実装は簡単になる一方、誤って指定した既存ディレクトリを削除または置換する可能性がある。CIでの再生成より利用者のファイル保護を優先するため採用しない。

### clonoをnpmテーマとして読み込む

Vivliostyle CLIのテーマ指定として技術的に成立し、生成済み原稿ツリーへCSSをコピーせずに済む。一方、実行中のclonoとは別にテーマパッケージの導入、バージョン固定、キャッシュおよびネットワーク要件が生じる。生成済み原稿ツリーはclonoが所有する成果物であり、対応するCSSを安全に含められるため、初期仕様では採用しない。

### npmパッケージ内CSSの絶対パスを指定する

追加のテーマパッケージ導入を避けられる可能性がある。一方、検証ではWebPubへ基盤CSSが収録されず、生成物の外側を指すリンクになった。配布可能なWebPubとして自立しないため採用しない。

### 利用者テーマをclono設定で管理する

clonoだけでテーマの指定を完結できる一方、Vivliostyleが既に持つテーマ機能をclono側へ再実装し、設定の二重管理を招く。利用者テーマはVivliostyleの責務であるため採用しない。

### Vivliostyle設定用ヘルパーを初期実装する

原稿一覧と基盤CSSをVivliostyle設定へ組み込みやすくなる。一方、初期仕様では`clono.config.mjs`を直接importし、固定パスを指定するだけで必要な構成を表現できる。実際の書籍制作を通じて反復箇所と必要なAPIを確認する前に公開インターフェースを固定しないため、具体的な必要性が生じるまで後回しにする。

## 影響

- 利用者は`clono.config.mjs`と`vivliostyle.config.mjs`を管理する必要がある
- 原稿一覧は`clono.config.mjs`だけに記述し、Vivliostyle設定から参照する
- `clono.config.mjs`は信頼できる書籍プロジェクトでだけ実行する必要がある
- 生成済み原稿ツリーには、変換済みMarkdownだけでなく、入力ツリーの通常ファイル、必要な空白ページHTML、所有マーカーおよびclono基盤CSSが含まれる
- 入力原稿ツリー直下の`_clono/`と`.clono-output.json`は予約され、利用者のファイルとして使用できない
- 生成済み原稿ツリーの再生成処理には、staging、backup、所有確認および排他ロックが必要になる
- シンボリックリンクを含む入力原稿ツリーには初期仕様で対応しない
- 利用者は、Vivliostyle設定でclono基盤CSSを利用者テーマより前に指定する必要がある
- 空白ページを使用する場合、利用者はVivliostyle設定で各空白ページ`entry`へ一意な`output`を割り当て、利用者テーマで`@page clono-blank`の柱とノンブルを指定する必要がある
- 設定ヘルパーを提供するまでは、書籍プロジェクトごとにVivliostyle設定との橋渡しを記述する必要がある
- `clono build`自体はWebPubまたはPDFを生成せず、生成済み原稿ツリーの公開までを担う
- 旧形式の単一ファイルCLIを利用している場合、`transform`サブコマンドへの移行が必要になる

## 未確認事項

- プロセスの強制終了後に残ったstaging、backupまたは排他ロックの検出と回復
- 原稿ツリー外にある静的ファイルをclonoで扱う必要性
- 空白ページ以外の生成文書を追加する場合の書籍構造の拡張方法
- 複数原稿をまたぐ情報の収集、解決および状態共有の方式
- entryごとに異なる利用者テーマを扱う必要性
- Vivliostyle設定用ヘルパーの必要性と公開API
- WindowsとLinux固有の許可ビット、ACLおよび拡張属性を将来保持する必要性

## 見直す条件

次のいずれかが生じた場合は、この決定の該当部分を見直す。

- Thunder Clawの実原稿で、生成済み原稿ツリー方式では維持できない相対参照が確認された場合
- 原稿ツリー外の静的ファイルを含む、独立した書籍プロジェクト全体の出力が必要になった場合
- 所有マーカー、stagingまたは排他ロックでは、利用者のファイルを十分に保護できない事例が確認された場合
- 複数OSで安全な出力先の置き換えを実現できない場合
- `clono.config.mjs`と`vivliostyle.config.mjs`の橋渡しが、実際の書籍制作で無視できない重複または保守負担になった場合
- 生成済み原稿ツリーへ基盤CSSを含めることが運用上の問題になった場合
- 利用者テーマからclono基盤CSSを上書きできない事例が確認された場合
- Vivliostyle CLIのテーマまたはWebPubへのファイル収録規則が変更された場合
