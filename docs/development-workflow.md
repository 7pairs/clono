# clono 開発フロー

- 状態: 有効
- 作成日: 2026-10-03
- 最終更新日: 2026-10-03

## 1. 目的と位置づけ

この文書は、clonoの作業計画、設計判断の記録、実装、調査、検証、レビュー、品質点検、リリースの進め方を定める。

開発全体の原則は、[プロジェクト憲章](project-charter.md)を正本とする。この文書は、Sora Driven Development（SDD）を具体的に運用するための手順を扱う。

ブランチとリリースの運用には、Sora Flowを採用する。

## 2. 作業計画と着手

### 2.1 計画の単位

作業計画と通常のPull Request（PR）は、原則として一対一にする。

調査、設計、実装など、関連する複数の計画をまとめて作成してよい。各計画は相互に参照し、前提と依存関係を示す。

後続の計画が存在することは、着手の許可を意味しない。先行する作業によって前提が変わった場合は、後続の計画を更新し、必要な再合意を行ってから着手する。

### 2.2 計画の内容と保存

作業計画は、プロジェクトオーナーへの説明と、作業範囲の約束を兼ねる。厳密なSDDツールのtasks形式は前提としない。以下を短く記載する。

- 目的と完了条件
- 対象と対象外
- 変更予定
- 検証方法
- レビューとコミットを判断しやすい作業単位

チャットで計画を相談し、合意した内容を、明示的な作成指示を受けてリポジトリへ保存する。実装は、計画への合意と明示的な着手指示を受けて行う。

計画単独の第三者レビューは必須としない。必要に応じて計画だけのレビューを行える。計画を含むPRのマージには、通常のレビュー条件を適用する。

### 2.3 作業単位の終了

「そら」は、指示された作業単位が完了したら、以下を説明して停止する。

- 変更内容と主要な処理の流れ
- 検証結果と残っている問題
- 記録した判断と計画からの差分

プロジェクトオーナーが内容を確認し、修正、コミット、次の単位への着手を判断する。

基本的に作業の区切りごとにコミットする。一つの区切りを、プログラムと文書など、複数のコミットに分けてよい。

### 2.4 計画の更新と保存

作業中の発見に合わせて計画を更新する。範囲変更は、憲章に定める再合意を経て反映する。

完了時には、結果、残った課題、関連する仕様・ADR・調査結果への参照を記載する。作業計画は完了後も保存するが、恒久的な仕様や判断理由の唯一の記録先にはしない。

PR本文に、対応する作業計画へのリンクを記載する。計画側からPRへのリンクは必須にしない。逆方向のリンク更新だけのために、追加のpushやPRを発生させないためである。

## 3. 記録の配置と更新

### 3.1 配置

文書と調査用フィクスチャは、以下を基本とする。

```text
docs/
  project-charter.md
  development-workflow.md
  carryover-notes.md
  plans/
  specs/
  decisions/
  research/
    0001-short-name/
      README.md
      fixtures/
```

`research`内の各`README.md`は、その調査の結果ドキュメントとする。

計画、仕様、ADR、調査には、種類ごとに独立した連番と短い英語名を付ける。たとえば、`plans/0001-short-name.md`、`decisions/0001-short-name.md`、`research/0001-short-name/README.md`のようにする。関連する記録は本文のリンクで結ぶ。

### 3.2 記録先の役割

| 記録先 | 内容 |
|---|---|
| 仕様 | 期待する振る舞い、記法、境界条件、具体例 |
| ADR | 設計上の選択と、その理由 |
| 作業計画 | 目的、範囲、完了条件、検証方法、進捗、結果、未解決事項 |
| 調査結果 | 調査した問い、条件、方法、観測結果、解釈、未確定事項 |

小さな判断も記録する。同じ論点に関する判断は、関連するADRへの追記など、一つの記録にまとめてよい。

長く必要な結論は、作業計画から仕様やADRへ反映する。調査結果に基づく採用判断も、仕様やADRに記録する。必要に応じて相互に参照し、説明の重複を避ける。

### 3.3 記録するタイミング

判断した時点で記録することを基本とし、作業単位の終了前に記録漏れを確認する。

記録に値する判断を、短いという理由で省略しない。必要な理由が伝わるなら、1行でもよい。

### 3.4 ヘッダ

各記録には、作成日と最終更新日を記載する。状態などの項目は、文書の用途に応じて設け、無理に統一しない。

- 憲章や開発フローなどの規範文書は、PRがマージされた後の状態を記載する。
- 作業計画は、更新時点の実際の状態を記載する。「計画済み・進行中・完了・中止」を基本とする。
- 調査の未確定事項は本文に明示する。
- レビューの進捗はPR側で管理する。
- 日付はマージ日ではなく、文書を作成・更新した日とする。更新時には最終更新日も確認する。

規範文書の状態更新だけを目的とする追加PRは作成しない。作業計画の完了時の更新は、当該PRに含める。

## 4. 調査と検証

### 4.1 調査の単位

調査が主目的の場合は、独立した作業計画とPRを作成する。

実装中に必要になった調査は、同じ計画・PRで扱ってよい。仕様や変更範囲を広げる場合は再合意する。

PRを分けるかどうかにかかわらず、将来必要になる結果と判断理由を記録する。

### 4.2 再実行と証拠

調査結果には、問い、入力、実行手順、ツールのバージョン、設定、必要な環境条件、観測結果、解釈、未確定事項を記載する。

再実行用のフィクスチャと手順を保存し、バージョン固定を基本として再生成できる条件を整える。再現性に制約がある場合は明示する。

生成物は原則として保存しない。ただし、結果のレビューや根拠の保存に必要なものは残してよい。

見た目の証拠は、確認箇所に絞ったスクリーンショットを優先し、入力、生成手順、ページや確認箇所との対応を示す。HTML構造やリンク先などの検証には、抽出結果など対象に適した証拠を用いる。

依存パッケージや一時的な生成物を丸ごと保存することは基本にしない。

### 4.3 検証方法と完了条件

検証方法は、変更内容とリスクに応じて選び、作業計画に記載する。

可能な限り、第三者が再実行できる自動テストにする。目視など自動化しにくい検証は、手順、着目点、判定基準を残す。

必要な検証が未実施または失敗している場合は、完了扱いにせず相談する。検証方法や完了条件を変更する場合は、再合意と理由を記録する。

自動化した検証をすべてCIで実行することは求めない。基本的な回帰テストをCIで実行することを基本とし、検証の目的、実行コスト、安定性に応じて対象と実行タイミングを定める。CIの対象外でも、作業計画で必要とした検証は省略しない。具体的な構成は、技術選定後に定める。

調査用フィクスチャをすべて通常のCIに含める必要はない。継続的に守るべき仕様を確認するものは、回帰テストへの移行を検討する。組版を伴う重い検証や環境依存の大きい検証は、必要な変更時やリリース前など、適切なタイミングを定める。

## 5. セッション間の継承

この文書における「セッション」は、共同開発者である「そら」が参加するCodexの会話・作業セッションを指す。

作業単位の完了後にセッションを切り替えることを基本とする。

途中で切り替える必要がある場合は、作業計画に以下を記録する。

- 完了した範囲と未完了の範囲
- 検証結果
- 未解決事項
- 次に着手できる範囲

判断理由は、関連する仕様やADRへ反映する。

次の「そら」は、憲章、開発フロー、対象の作業計画と関連記録を確認して再開する。計画に書かれた次の作業を、自動的な着手許可とは扱わない。

引き継ぎ専用の文書は極力作成しない。`carryover-notes.md`は初期整備のための例外とし、すべての項目を引き継いだ後に削除する。削除するPRには、反映先と引き継ぎ完了を記載する。

## 6. レビューとマージ条件

### 6.1 レビュアー

第三のレビュアーにはCodeRabbitを採用する。

無料で必要なレビューを利用できることを前提とし、有料化は別途相談する。適用プラン名や料金・制限を、恒久的な前提として固定しない。

制限に達した場合は、基本的に回復を待って手動で再実行する。1時間程度の待機は許容し、待ち時間が大きく延びた場合は運用を再検討する。

CodeRabbitを利用できない場合は、プロジェクトオーナーと相談し、レビュー用の別セッションの「そら」で代替する。第三者レビューは省略しない。

代替レビュアーも、実装時の説明だけに頼らず、仕様と変更内容を確認する。

### 6.2 依頼のタイミング

変更が揃い、必要な検証と「そら」の自己確認が完了してからPRを作成する。

CodeRabbitの自動レビューを基本とし、自動実行されない場合は手動で依頼する。PR作成後の軽微な修正による自動レビューも許容する。

### 6.3 指摘への対応

すべての指摘について、以下のいずれかで対応する。

- 修正する
- 理由を示して採用しない
- 現在の変更をマージしてよい理由と追跡先を示し、別の作業へ送る

対応内容を確認してから、GitHub上の会話をResolveする。AIの指摘をすべて採用することは求めない。

動作や設計に影響する修正では再レビューを依頼する。影響が明確で軽微な修正は、プロジェクトオーナーの確認で完了できる。

### 6.4 マージ条件

通常PRのマージには、以下を満たす必要がある。

- 作業計画の完了条件を満たしている
- 必要な検証を完了している
- 第三者レビューが実施されている
- 指摘への対応が完了し、未解決のレビュー会話がない
- 必要な仕様・判断理由・調査結果が記録されている
- PR本文から作業計画を参照できる
- プロジェクトオーナーが変更を確認し、マージを判断している

チェックの成功表示だけでなく、レビューが実際に行われたことを確認する。

リリース昇格PRは、9.2の条件を満たす場合に、レビュー済みの累積差分の再レビューを省略する。

## 7. 定期的な品質点検

製品コードやテストを変更する通常PRを3件マージするごとに、品質点検を行う。PRの大きさによる重み付けはせず、1件として数える。

以下は数えない。

- 文書だけのPR
- バージョン情報だけのリリース準備PR
- リリース昇格PR
- 定期点検に伴うリファクタリングPR

点検が完了するまでは、次の機能実装に着手しない。

点検では、以下を確認する。

- 責務の分担
- 重複と命名
- 処理の追いやすさ
- テストの分かりやすさ
- プロジェクトオーナーがコードを理解できているか

作業計画に、前回の点検、対象PR、確認内容、結果を記録する。

改善が必要なら、範囲と検証方法を合意し、明示的な着手指示を受けてリファクタリングする。原則として、機能追加や仕様変更を混ぜない。

改善不要でも、確認した観点と理由を記録したPRを作成する。点検完了後に件数をリセットする。

定期点検を待てない問題は、その時点で相談する。頻度は運用結果を踏まえて見直す。

## 8. Gitの運用

Git操作は、基本的にプロジェクトオーナーが担当する。「そら」は明示的に依頼された場合に行う。

通常の作業ブランチはPRごとに分け、作業計画に対応する以下の名前を使用する。

```text
plan/0001-short-name
```

コミットメッセージは、スコープを付けない軽量なConventional Commitsとし、型と日本語の件名を使用する。

```text
feat: 索引記法の変換を追加
fix: コードブロック内の独自記法を変換しないよう修正
docs: プロジェクト憲章を追加
```

通常PRとリリース昇格PRは、いずれもmerge commitで取り込む。作業単位ごとに判断したコミットと、レビューされた履歴を保持するためである。

## 9. Sora Flow

Sora Flowは、Git Flowをもとに、リリース準備の変更とレビューを`develop`側で完了させ、レビュー済みの内容を固定した`release`ブランチから`main`へ昇格させるclono固有のワークフローである。

リリース固有の変更も通常のレビュー経路を通し、昇格時の累積差分の再レビューを避ける。レビュー済みの内容を固定して`main`を安定した状態に保ち、リリース後の戻しマージを不要にする。

| ブランチ | 責務 |
|---|---|
| `main` | リリース済みの安定した内容を保持する |
| `develop` | 次のリリースに向けたレビュー済みの変更を統合する |
| `plan/番号-英語名` | 通常の変更やリリース準備を行う |
| `release/<version>` | リリース候補を固定し、`main`へ昇格させる一時的なブランチ |

通常の変更は、`develop`から作業ブランチを作り、計画、実装、検証、レビューを経て`develop`へ取り込む。

`main`や`release`では、ファイルを直接変更しない。

### 9.1 リリース準備

1. リリースするバージョンと内容を決定する。
2. リリース準備の作業計画を作成する。
3. `develop`から作業ブランチを作成する。
4. バージョン情報と、リリースに必要な文書などを更新する。
5. 通常のレビューと検証を経て、`develop`へマージする。

作業計画は準備PRまでを対象とし、その完了条件を満たした状態を準備PRに含める。

### 9.2 リリース候補の固定と昇格

リリース準備の取り込み後からリリース完了まで、`develop`への通常の変更を一時停止する。

1. `develop`から`release/<version>`を作成する。
2. `main`向けPRを作成し、タイトルに`[release]`を含める。
3. PR本文から準備計画とレビュー済みPR群を参照する。
4. CI、累積差分、レビュー済み内容との一致を確認する。
5. merge commitで`main`へマージする。
6. マージ結果の内容が固定した候補と一致することと、CIの結果を確認する。
7. マージコミットへ`v<version>`タグを付け、pushする。
8. GitHub上でタグの存在と参照先を確認する。
9. 既存タグからGitHub Releaseを作成する。
10. `release/<version>`を削除し、`develop`の通常変更を再開する。

昇格以降の実施状況は、昇格PR本文のチェックリストで管理する。昇格のためだけの作業計画は必須にしない。

すべての変更がレビュー済みであり、昇格時に新しいファイル変更が入らないことを条件として、累積差分の再レビューを省略する。[CodeRabbitの設定](../.coderabbit.yaml)は、`[release]`を含むタイトルの自動レビューを停止する。CIと最終確認は省略しない。

`[release]`は、この条件を満たす昇格PRだけに使用する。

リリース後に、`release`を`develop`へ戻すためだけのマージは行わない。リリース済みの内容はタグを正本として追跡し、リリースブランチを保存目的で残さない。

### 9.3 候補に問題が見つかった場合

昇格を停止し、通常の計画・PRで修正を`develop`へ取り込む。

レビューと検証を終えた後、`release`を更新後の`develop`へfast-forwardし、昇格PRのCIと最終差分を再確認する。候補の更新に伴い、確認対象も更新する。

`release`上で直接修正したり、未レビューの変更を取り込んだりしない。修正中も`develop`への通常の変更停止を維持する。

## 10. バージョンとGitHub Release

### 10.1 バージョン番号

セマンティックバージョニング2.0.0を基礎とする。

| 変更 | `1.0.0`未満 | `1.0.0`以降 |
|---|---|---|
| 後方互換性のない変更 | マイナーを上げる | メジャーを上げる |
| 後方互換性のある機能追加 | マイナーを上げる | マイナーを上げる |
| 後方互換性のある修正 | パッチを上げる | パッチを上げる |

上位の番号を上げる場合は、下位の番号を`0`に戻す。

互換性の判断対象は、利用者向けに公開・文書化した契約とする。記法、CLI、設定、プラグインAPI、出力構造など、利用者が依存してよい部分を仕様で明確にする。内部実装や、契約していない出力の細部は対象外とする。

バージョン情報の保存先と更新方法は、技術選定後に定める。ソース内のバージョン情報とタグの値は一致させる。

### 10.2 GitHub Release

すべての`v<version>`タグに対応するGitHub Releaseを作成する。Release作成時に新しいタグを暗黙に作らず、確認済みの既存タグを指定する。

タグはリリースされたソースと履歴の正本とし、GitHub Releaseは利用者向けの告知と説明を担う。

必要に応じて以下を記載する。

- 主要な機能追加、変更、修正
- 既知の制限
- 非互換変更と必要な移行方法
- 利用方法の変更と関連文書へのリンク

非互換変更を含む場合は、その変更内容と必要な移行方法を明記する。内部的なPR一覧は昇格PR側にまとめ、Releaseでは利用者に影響する内容を優先する。

Releaseの説明文は修正してよい。公開済みのタグは動かさず、コードの修正は新しいバージョンとしてリリースする。

配布物の生成、検証、添付、公開手順は、技術と配布方法の決定後に定める。

## 11. フローの更新

運用を変更する場合は、理由と影響を記録し、対話とレビューを経てこの文書を更新する。

CodeRabbitやCIの設定を変更した場合は、文書と実際の動作の整合性を確認する。

READMEとAGENTSから、この文書への導線を維持する。それらが未作成の間は、作成時に導線を追加する事項として引き継ぐ。
