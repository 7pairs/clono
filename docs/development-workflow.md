# clono 開発フロー

## 1. 目的と適用する方針

本文書は、clonoの開発における具体的な作業の進め方を定める。

「そら」は、開発者がCodex上で設定しているAIの人格を指す。「うみ」は、独立レビューを担当するCodexのサブエージェントの呼び名である。開発者とそらは、対話を通じて理解と合意を重ね、うみの独立レビューで成果物を確かめながら開発を進める。

三人の役割はSDDに従う。本文書の「二人」は開発者とそらを指し、合意と着手依頼、レビュー指摘の採否を二人で確認する。

開発の目的と優先順位はプロジェクト憲章、仕様検討から作業完了までの原則はSisters Driven Development（SDD）、Git戦略とリリースの原則はSora Flowに従う。

- [プロジェクト憲章](project-charter.md)
- [Sisters Driven Development](sisters-driven-development.md)
- [Sora Flow](sora-flow.md)

本文書では、これらの共通ルールを繰り返さず、clonoでの具体的な運用を定める。

clonoの配布ライセンスにはApache License 2.0（`Apache-2.0`）を採用する。ファイルの追加・更新・配布時は、[ライセンス方針](specs/licensing.md)に従って、適用範囲、第三者由来の内容、必要な表示を確認する。採用理由は[ADR](decisions/0001-adopt-project-license.md)、正式な条件は[LICENSE](../LICENSE)を参照する。

## 2. 文書と調査用ファイルの配置

### 2.1 文書

文書は、次の配置を基本とする。

| 配置 | 内容 |
|---|---|
| `docs/project-charter.md` | プロジェクト憲章 |
| `docs/sisters-driven-development.md` | SDD |
| `docs/sora-flow.md` | Sora Flow |
| `docs/development-workflow.md` | clonoの開発フロー |
| `docs/specs/` | 仕様・設計・テスト項目 |
| `docs/plans/` | 作業ごとの手順書と実施記録 |
| `docs/decisions/` | ADR |
| `docs/backlog.md` | 後続課題と現在の対応状態 |

仕様は、`book-index.md`のように対象の機能が分かる名前にする。

手順書とADRは、`0001-choose-development-environment.md`のように、連番と作業・判断の内容が分かる名前を組み合わせる。

手順書から関連する仕様やADRへリンクし、作業に必要な文書を辿れるようにする。

### 2.2 調査用ファイル

調査用の入力、コード、結果は、`research/`の下に、番号を付けず調査内容が分かる名前のディレクトリを作って配置する。手順書と調査資料の`README.md`から相互にリンクし、対応関係を保つ。

```text
docs/plans/0001-decide-project-license.md

research/project-license/
├── README.md
├── fixtures/
├── scripts/
└── results/
```

各ファイル・ディレクトリの役割は次のとおりとする。

| 配置 | 内容 |
|---|---|
| `README.md` | 調査の目的、再現方法、関連する手順書へのリンク |
| `fixtures/` | 調査に使う入力や再現例 |
| `scripts/` | 調査用の実行コード |
| `results/` | 保存する出力や測定結果 |

必要なファイル・ディレクトリだけを作成する。

調査の結論と作業記録は手順書、設計上の判断理由は必要に応じてADRに残す。`research/`には、その根拠を確認・再現するための材料を置く。

再現に必要な入力・コードと、比較や判断の根拠として残す結果を選んでGit管理する。再生成できる大量の出力やキャッシュは管理対象から外す。

## 3. 相談と手順書の準備

機能追加や修正の相談は、手順書なしで始められる。

新しい作業の目的と範囲を相談するときは、backlogの未対応課題も確認する。新しい機能と既存課題のどちらを優先するか、今回一緒に扱うものがあるかを二人で検討する。

目的と範囲が決まったら、次の流れで手順書を準備する。

1. チャットで手順書の案を示し、二人で議論する。
2. まとまった案を独立レビューにかける。
3. 指摘への対応を議論し、修正した場合は再レビューする。
4. 合意した手順書をファイルにする。
5. 開発者が作業開始を依頼する。

準備中のレビュー・修正・ファイル化にも、合意と着手依頼を区別する原則を適用する。手順5の作業開始の依頼は、手順書に定めた本作業への着手依頼を指す。

手順書を準備するための別の手順書は作らず、この準備の流れに従う。

手順書を準備する段階で調査・実験やファイル変更が必要になった場合は、相談の延長として勝手に進めず、作業として手順を合意し、着手依頼を受けてから実施する。

作業開始後に必要になった追加作業は、プロジェクト憲章第7節とSDD第9節に従う。

調査結果がなければ決められない手順の扱いは、SDDに従う。

## 4. Git操作とブランチ

### 4.1 操作の担当

ブランチ作成、コミット、push、PR作成、マージなどのGit操作は、基本的に開発者が担当する。

そらは、明示的に依頼された場合に限り、依頼された範囲の操作を行う。リモートへpushしない一時的なブランチの操作も同様とする。

工程の着手依頼だけでは、Git操作も依頼されたものと扱わない。

### 4.2 ブランチの命名

通常の作業ブランチは、手順書の拡張子を除いた名前に`plan/`を付ける。

```text
手順書：docs/plans/0001-add-book-index.md
ブランチ：plan/0001-add-book-index
```

リリース準備は専用の命名を使い、手順書との対応はPRから追えるようにする。

| 用途 | 名前 |
|---|---|
| 通常の作業 | `plan/<手順書名>` |
| リリース準備 | `chore/prepare-<version>` |
| リリース内容の固定と昇格 | `release/<version>` |
| バージョンタグ | `v<version>` |

一つの手順書から複数PRへ分ける必要が生じた場合は、その時点でブランチ名と対応関係を相談する。

develop向けPRとreleaseからmainへの昇格PRは、Sora Flowに従ってmerge commitでマージする。

## 5. 各手順の実施とコミット

各手順は、次の流れで進める。

1. 開発者の着手依頼を受ける。
2. 合意した作業と検証を実施する。
3. 独立レビューを行い、指摘を二人で検討する。
4. 必要な修正、検証、再レビューを行う。
5. 作業記録を更新し、変更内容と結果を説明する。
6. 開発者が内容を理解したことを確認し、コミットする。
7. 次の手順へ進む合意と着手依頼を受ける。

工程の区切りやレビューをまとめる場合は、SDDに従って手順書で事前に合意する。

開発者によるコミットは、その変更内容を理解したという意思表示として扱う。ただし、コミットしたことだけでレビューや作業全体の完了に代えない。

別々の手順を一つのコミットにまとめない。レビュー対応などでコミットが増えることは許容する。

手順書の状態は、記録時点で実施・検証・独立レビュー・二人の確認を終えた手順を示す。コミット待ちなどのGit操作の状態は含めず、コミットの事実はGit履歴で追う。次の手順への着手には、引き続きコミットと着手依頼を必要とする。

最後の手順まで確認が済んだ時点では、手順書に「全手順の実施・内部確認完了」と記録する。外部レビューと作業全体の完了状況は、対応するPRで確認し、その完了を手順書へ転記するためだけのコミットは行わない。

### 5.1 説明と報告

そらは、開発者が変更を理解してコミットを判断できるように説明する。次の項目を目安に、必要な内容を選ぶ。

- 変更内容と理由。
- 検証、独立レビュー、再レビューの結果。
- 予定から変わった点や残した課題。
- 差分を読むときに確認してほしい箇所。

不要な項目は省略し、理解に必要な説明は追加する。固定の長文報告や、手順書の内容の転記は求めない。

理解の程度は、憲章に定める基準に従う。

## 6. 独立レビューの運用

独立レビューには、「うみ」と呼ぶCodexのサブエージェントを使用する。この呼び名は独立レビューを担当する役割を表し、すべての工程で同じサブエージェントを使うことを意味しない。

工程ごとの初回レビューは、開発作業の会話履歴を引き継がない、新しいサブエージェントに依頼する。合意済みの仕様、判断理由、成果物、レビュー観点など、評価に必要な資料を渡す。

同じ成果物の再レビューは、原則として同じレビュアーに依頼する。修正後の成果物と、指摘への対応・採否の理由を共有する。

指摘の扱い、修正後の再レビュー、着手依頼の区切りはSDDに従う。

各工程の必須レビュー観点や、レビュアーの使い分けは、実際の運用から必要性を確認して調整する。

## 7. PR作成と外部レビュー

### 7.1 通常のPR

通常はローカルで各工程の作業、検証、独立レビュー、二人の確認とコミットを済ませてから、PRを作成する。

この時点は「PRレビューに出せる状態」であり、作業全体の完了とは区別する。

通常の作業PRはdevelopを取り込み先とし、おおむね一つの手順書を一つのPRで扱う。

PRタイトルは、手順書の最上位見出しから連番などを除いたものを基本とする。作業の切り出しや範囲変更で合わなくなった場合は、最終的な変更内容に合わせて調整する。

PR説明には、次の内容を必要な範囲で記載する。

- 変更の目的と主な内容。
- 検証とレビューの結果。
- 関連する手順書へのリンク。

詳しい経緯は手順書を参照し、全文をPR説明へコピーしない。

### 7.2 Draft PR

Draft PRは、必要性を二人で合意した場合に利用できる。作成する時期と目的は手順書に記載する。

Draft状態では外部レビューツールの自動レビューを起動せず、レビュー可能な状態へ切り替えたときに起動する方針とする。具体的な設定は、レビューツールの選定時に確認する。

CIの実行条件は、自動レビューの起動条件とは分けて決める。

Draft PRの作成は、後続工程への着手許可として扱わない。

### 7.3 指摘への対応とresolve

外部レビューの指摘も、採用・不採用・後回しを二人で判断し、理由を残す。修正した場合は、検証と再レビューで対応を確認する。

修正した内容は、開発者が理解してからコミットする。

レビュー会話のresolveは、レビューツールによる自動処理、または開発者の操作で行う。そらが操作する場合は、明示的な依頼を必要とする。

自動resolveされた場合も、それだけで二人の確認や作業全体の完了に代えない。

### 7.4 完了確認とマージ

外部レビューの対応まで含め、SDDの完了条件を満たしたことを二人で確認する。

マージ前には、必要なレビュー・検証と合意が済み、未解決のレビュー会話がないことを確認する。GitHubでは、未解決のレビュー会話があるPRをマージできない設定を用いる。

作業全体の完了とマージは区別し、マージは基本的に開発者が行う。

## 8. コミットと言語の方針

コミットメッセージは、英語の短い種類と日本語の件名を組み合わせる。

```text
feat: 索引語の読みを正規化する
docs: 開発フローを追加する
```

scopeは原則として付けず、付けることで対象が明確になる場合だけ使用する。複数の領域にまたがる変更を、無理に一つのscopeへ分類しない。

理由の補足が必要な場合は、コミットメッセージの本文に記述する。

文書とコードの言語は、次を基本とする。

| 対象 | 言語 |
|---|---|
| 仕様・設計・テスト項目・手順書・ADR | 日本語 |
| Issue・PRのタイトルと説明・レビュー | 日本語 |
| ファイル名・プログラムの識別子・コードコメント | 英語 |
| テストコードの説明文 | 英語 |
| AI向けの`AGENTS.md` | 英語 |

READMEは当面日本語を基本とし、英語版は必要になった場合に検討する。

日本語ドキュメントの作成・更新では、`AGENTS.md`に従って`yomiyasu`を使用する。チャットの会話と、`session-handoff`で作成・更新する引き継ぎ文書は対象外とする。

### 8.1 テストコードの命名と説明

ClojureScriptのテスト名前空間は、末尾を`-test`にする。テスト環境と実行方法は、[開発環境の仕様](specs/development-environment.md)を参照する。

`cljs.test`の`testing`の説明文と、`node:test`の`test`・`it`・`describe`の説明文には、次の共通方針を適用する。

- 英語で記述し、`When <condition or action>, then <observable result>`を基本形とする。
- 実装手順やテスト側の検査操作ではなく、対象の外から確認できる振る舞いを記述する。単体テストでは、関数に渡す入力や返り値も対象の外から確認できる振る舞いとして扱う。
- `When`と`Given`は大文字で始め、カンマの後の`then`は小文字にする。説明文の末尾にピリオドを付けない。
- 前提ごとにまとめると意図が伝わりやすい場合は、外側を`Given <context>`、内側を`When ..., then ...`とする。`Given`には状態や入力を記述し、セットアップの手順は書かない。
- `Given`によるグループ化は任意とする。意図を明確にできる場合は、内側の説明文が一つだけでも使用できる。
- 説明文を持つブロックの入れ子は、原則として`Given`と`When`の2段までとする。テストが大きくなった場合は、深い入れ子を追加せず、複数の`deftest`や`test`などへ分割する。

`cljs.test`では、必要に応じて外側と内側の`testing`を使う。`node:test`では、単独の`test`や`it`を基本形で記述し、グループ化する場合は外側の`describe`を`Given`、内側の`test`や`it`を`When ..., then ...`にする。

```clojure
(deftest command-result-test
  (testing "Given no arguments"
    (testing "When the command is evaluated, then usage is returned successfully"
      ...))
  (testing "Given an unknown argument"
    (testing "When the command is evaluated, then usage is returned as an error"
      ...)))
```

CLIの結合テストでは、実際のコマンド実行と出力を説明する。

```javascript
test('When the command receives no arguments, then usage is written to standard output', () => {
  // ...
});

describe('Given an existing generated file', () => {
  test('When the version is unchanged, then the generated file remains unchanged', async () => {
    // ...
  });
});
```

## 9. 後続課題の管理

後続課題は`docs/backlog.md`で一元管理する。手順書には当時の判断を残し、backlogには現在の対応状態を記載する。

各課題には、次を必要な範囲で記述する。

- 課題の内容。
- 後回しにした理由と、未対応のままにする影響。
- 状態。
- 関連する手順書・仕様・ADRへのリンク。

既存文書に説明があれば、重複して書かずリンクで参照する。優先度や期限は、決めた場合だけ追加する。

状態は「未対応・対応中・対応済み・見送り」を基本とする。対応済み・見送りの項目も削除せず、一覧の後ろに残す。

新しい作業の目的と範囲を相談するときは、未対応課題を見返す。今回扱う課題を二人で選び、手順書に含める。backlogへの記載だけでは着手を許可したものと扱わない。

対応後はbacklogを更新し、元の手順書には必要に応じて後続作業へのリンクを追記する。

対応済み・見送りの項目が増えた場合は、別ファイルへの切り出しを検討する。移動後も、関連文書から追えるリンクを保つ。

一つのファイルでは管理しきれなくなった場合や、全課題に優先度・期限などの管理が必要になった場合は、Issueへの移行を含めて管理方法を再検討する。

## 10. リリース運用

clonoのリリースにはSora Flowを採用する。リリース準備、developの凍結、mainへの昇格、タグ付け、公開、異常時の再試行・中止・取り下げは、Sora Flowに従う。

共通手順を本文書へ複製せず、clono固有の設定と操作を、技術選定の結果に応じて具体化する。

命名は次のとおりとする。

- リリース準備ブランチ：`chore/prepare-<version>`
- releaseブランチ：`release/<version>`
- バージョンタグ：`v<version>`

昇格PRの重複レビューを抑止する設定と、CIの実行条件は分けて定める。

公開処理については、一部公開後の状態確認、内容を変えない再試行の可否と方法、取り下げが必要になった場合の対象と対応も具体化する。

## 11. 技術選定後に具体化する事項

### 11.1 採用した実装環境

本体は可能な限りClojureScriptで実装し、Node.js上で実行する。ビルドにはshadow-cljsを使い、ESMを出力する。本ごとのJavaScript拡張はまず.mjsファイルとする。

利用時のNode.js対応範囲、開発用のNode.js・JDK、macOSを最初の動作確認対象とする方針と他OSの確認状況は、[実装環境の仕様](specs/implementation-environment.md)に従う。利用者にはビルド済みのJavaScriptを提供し、JDKやClojureScriptのビルド環境を要求しない構成とする。具体的な配布・インストール方法は今後決める。

Markdownは現行remark系でASTとして加工し、Markdownへ再出力してVFMでHTML化する。採用バージョンの基準、デバッグ補助、コラムとページ下部脚注の制約、条件付きで許容する依存リスクも同仕様を参照する。依存リスクの現在の対応状態と見直す時点は[backlog](backlog.md#依存の脆弱性への対応を見直す)で管理する。

採用理由と代替案は[ADR 0002](decisions/0002-choose-implementation-environment.md)、調査と検証の根拠は[検証資料](../research/implementation-environment/README.md)と、そこから参照する検証結果に記録している。調査用コマンドはその環境を再現するためのものであり、正式な製品の開発・検証コマンドとして扱わない。

### 11.2 開発・検証の基盤

正式な開発・検証コマンド、テスト、REPL、CIは[開発環境の仕様](specs/development-environment.md)に従う。セットアップとCLIの実行例は[README](../README.md#セットアップと検証)、引数・出力・終了コードは[CLIの仕様](specs/cli.md)を参照する。

ローカルとCIの共通検証は`npm run verify`とする。CIは`develop`・`main`向けのPRと両ブランチへのpushで実行し、Draft PRも対象とする。3OSの設定は実装済みで、GitHub Actions上での実行結果は[手順書0003](plans/0003-set-up-development-foundation.md)に対応する通常のPRで確認する。

### 11.3 未決定の事項

現時点では、次の内容は未決定とする。

- 正式なPRレビューツールと起動条件。
- リリース準備で更新するファイル。
- バージョン番号の更新規則と、後方互換性を保証する対象。
- タグの共有先、リリースの公開先と具体的な操作。
- リリース告知に含める変更・既知の制限・移行方法と、開発者向けの変更一覧との役割分担。
- 公開後の告知文の訂正方法。
- 配布物の生成・検証と、公開済みタグとの対応確認。
- 公開処理の再試行方法と、公開物の取り下げ方法。

正式なレビューツールが決まるまでは、CodeRabbitを暫定的に使用する。

Draft中の自動レビュー抑止、レビュー可能な状態へ切り替えた後のレビュー開始、昇格PRの重複レビュー抑止については、正式な選定時に設定方法と挙動を確認する。

未決定の公開・リリース手順や正式なPRレビューツールの設定が利用できることを前提にしない。各作業では、手順書で合意した検証を行う。

技術選定の手順書と関連文書は第12節から参照する。決定した内容は、開発フローの該当箇所へ反映する。

バージョン方針、互換性の対象、リリース告知、配布物の運用は、環境・仕様・公開方法が具体化してから決める。最初の開発環境選定ですべてを決め切る必要はない。

## 12. 最初に行う技術選定

最初のコードを追加する前に、配布ライセンスと適用範囲・表示方法を決定し、リポジトリに明示した。この作業は[ライセンス決定の手順書](plans/0001-decide-project-license.md)で扱った。決定した内容は、[ライセンス方針](specs/licensing.md)と[ADR](decisions/0001-adopt-project-license.md)を参照する。

実装言語・実行環境の採用判断は[選定の手順書](plans/0002-choose-implementation-environment.md)の手順4までに完了した。決定した内容は[実装環境の仕様](specs/implementation-environment.md)、判断理由は[ADR 0002](decisions/0002-choose-implementation-environment.md)を参照する。

正式な開発・テスト基盤、CI設定、最初の製品機能であるバージョン表示は[手順書0003](plans/0003-set-up-development-foundation.md)で扱う。現在の構成は第11.2節の仕様を参照する。正式なPRレビューツールは引き続き未決定である。実装環境の調査で使った組版スクリプトを、そのまま製品の機能として採用したものとは扱わない。

最初の機能と開発基盤のローカル検証は済んでいる。PRでは3OSのCIと外部レビューを確認する。

すべてを一度に決める必要はない。調査結果に応じて作業を分け、後続の手順を具体化する場合はSDDの条件に従う。

最初から予定している技術選定は、後回しにした課題としてbacklogへ重複登録せず、本文書と技術選定の手順書で追跡する。

技術選定後は、関連する手順書・仕様・ADRへのリンクを本節に残す。決定した運用は本文書の該当箇所に反映し、第11節の未決定事項を更新する。

## 13. 開発フローの更新と導線

開発フローは、運用経験や技術選定の結果に応じて、二人で合意して更新する。

レビューツールやCIなどの設定を変更する場合は、本文書の説明と実際の動作が一致していることを確認し、必要に応じて本文書も更新する。

READMEと`AGENTS.md`から本文書へのリンクを維持する。文書を移動した場合は、関連するリンクも更新する。

憲章・SDD・Sora Flowの説明を入口ごとに複製せず、本文書から参照できる状態を保つ。
