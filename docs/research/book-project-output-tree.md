# 書籍プロジェクトの生成済み原稿ツリーに関する調査

- 状態: 調査済み
- 調査日: 2026-08-24
- 最終更新日: 2026-08-28
- 検証環境:
  - OS: macOS 26.5.2
  - Node.js: 24.19.0
  - npm: 11.17.0
  - PDF生成: `@vivliostyle/cli` 11.1.0
    - CLIが依存する`@vivliostyle/vfm` 2.7.0
    - CLIが使用するVivliostyle.js 2.44.1
  - PDF検証: `mupdf` 1.28.0

## 背景

clono 0.2.0は、一つのMarkdownファイルを指定した出力ファイルへ変換できる。一方、Thunder Clawの書籍制作では、前付、本文、付録、索引および後付を構成する複数の原稿を一定の順序で変換し、Vivliostyleへ渡す必要がある。将来実装する相互参照と索引も、複数の原稿を一つの書籍として扱える基盤を必要とする。

前身のスクリプトは、Markdownだけを格納した入力ディレクトリから、同じ階層にある別のディレクトリへ変換済みMarkdownを出力していた。入力と出力の階層を揃えることで、原稿から書籍プロジェクト内の画像などを参照する相対パスを変更せず利用できた。

この方式はThunder Clawの当時の構成では簡潔だったが、画像がMarkdownと同じディレクトリまたはその子孫にある場合、Markdownだけを別のディレクトリへ移すと参照先が存在しなくなる。一方、書籍プロジェクト全体を複製すると、設定、テーマ、依存関係、キャッシュおよび生成物のコピー範囲と除外規則をclonoが管理する必要がある。

今回の調査では、書籍プロジェクト全体ではなく、Markdownとその相対参照に必要な静的ファイルを含む入力原稿ツリーだけを生成済み原稿ツリーへミラーする方式を検証した。

## 検討した出力単位

### Markdownだけを出力する

入力と出力を同じ階層の兄弟ディレクトリに置けば、両方の外側にある画像やテーマへの相対パスを維持できる。前身のスクリプトで実績があり、コピー対象も少ない。

ただし、原稿ツリー内に画像、HTMLまたはその他の静的ファイルがある場合は、そのままでは生成済みMarkdownから参照できない。正しく動作するディレクトリ配置が暗黙の前提となるため、汎用的な書籍プロジェクトの契約としては制約が強い。

### 書籍プロジェクト全体を出力する

変換結果だけで独立した書籍プロジェクトを構成できるが、`node_modules`、Vivliostyleの中間生成物、PDF、キャッシュなどを除外する規則が必要になる。利用者が管理する設定やテーマまで複製すると、正本と生成物の区別も曖昧になる。

clonoは書籍プロジェクトの同期ツールを目的としていないため、初期の一括変換基盤としては責務が広すぎる。

### 入力原稿ツリーをミラーする

書籍プロジェクト内に入力原稿ルートと生成済み原稿ルートを設け、入力原稿ルート以下の相対パスを保って出力する。

- Markdownにはclonoの変換を適用する
- 原稿と同じツリーにある画像、HTMLなどの通常ファイルは内容を変えずコピーする
- 書籍プロジェクトの設定、テーマ、依存関係は原稿ツリー外に置き、コピーしない
- Vivliostyleは生成済み原稿と、書籍プロジェクトに残したテーマを使用する

この方式なら、原稿と静的ファイルの相対関係を維持しながら、書籍プロジェクト全体の複製を避けられる。今回のfixtureでは、この方式を技術検証の対象とした。

## 技術検証

調査結果を再検証できるように、[検証用fixture](fixtures/book-project-output-tree/)をリポジトリ内へ保存している。このfixtureはclono本体から独立したNode.jsとnpmのプロジェクトであり、`package.json`と`package-lock.json`によって検証環境の依存関係を固定する。

fixtureは次の構成を持つ。

```text
project/
├── book.mjs
├── vivliostyle.config.mjs
├── manuscripts/
│   ├── chapter-one.md
│   ├── appendix.html
│   ├── images/
│   │   └── diagram.svg
│   └── nested/
│       └── chapter-two.md
├── build/
│   └── manuscripts/
└── themes/
    └── theme.css
```

`project/book.mjs`は、入力原稿ルート、生成済み原稿ルートおよび原稿順序を定義する。プロトタイプの一括変換処理と`vivliostyle.config.mjs`が同じ値をimportし、原稿一覧を二重管理せず利用できるか確認した。

`book.mjs`というファイル名、JavaScriptモジュール、exportする値とその構造は検証用の候補であり、clonoの設定仕様として採用したものではない。

### Markdownと静的ファイル

プロトタイプは入力原稿ツリーを再帰的に走査し、相対パスを保って生成済み原稿ツリーへ出力する。

- 拡張子が`.md`の通常ファイルには検証用変換を適用する
- その他の通常ファイルは内容を変えずコピーする
- ディレクトリは同じ相対位置へ作成する
- シンボリックリンクはエラーにする
- 原稿一覧に指定したファイルが生成されなかった場合はエラーにする

検証用のMarkdown変換は、`FIXTURE_SOURCE_TOKEN`を`FIXTURE_TRANSFORMED_TOKEN`へ置き換えるだけである。これはMarkdownと通過ファイルを区別するためのfixture固有の処理であり、clono本体の変換パイプラインを模擬または先行実装するものではない。

ルート直下のMarkdownは`images/diagram.svg`、ネストしたMarkdownは`../images/diagram.svg`を参照する。画像を同じ相対位置へコピーすることで、両方の参照を変更せずVivliostyleで処理できるか確認した。

HTMLは入力原稿ツリーから内容を変えずコピーし、Vivliostyleの独立した`entry`として使用した。テーマCSSは原稿ツリー外の`project/themes/`にだけ配置し、生成済み原稿ツリーへコピーしなかった。

### 出力先の所有権

出力先を繰り返し再生成できる一方、利用者が誤って指定したディレクトリの内容を削除しないよう、プロトタイプは生成済み原稿ツリーへ`.clono-output.json`を配置する。

検証用の所有マーカーは、次の情報を持つ。

```json
{
  "format": 1,
  "producer": "@clono/research-book-project-output-tree",
  "sourceRoot": "manuscripts",
  "outputRoot": "build/manuscripts"
}
```

プロトタイプは、次の条件で出力先を扱う。

| 出力先の状態 | 動作 |
| --- | --- |
| 存在しない | ディレクトリを自動作成して出力する |
| 空である | clonoの管理対象として初期化する |
| 期待する所有マーカーがある | 既存の生成物を新しい出力で置き換える |
| マーカーのない非空ディレクトリ | 既存内容を変更せずエラーにする |
| 不正または異なるマーカーがある | 既存内容を変更せずエラーにする |
| 入力と出力が同じ、または祖先・子孫として重なる | エラーにする |

所有マーカーは誤指定による破壊を防ぐための識別子であり、悪意ある利用者に対するセキュリティ境界ではない。後続の[書籍プロジェクト仕様](../specifications/book-project.md)では、初期形式として`.clono-output.json`、形式バージョン、producer、入力原稿ルートおよび生成済み原稿ルートを採用した。

### stagingと出力の置き換え

プロトタイプは、出力先と同じ親ディレクトリに一意なstagingディレクトリを作成し、Markdownの変換、静的ファイルのコピー、原稿一覧の検証および所有マーカーの生成を完了してから公開する。

公開前には、出力先の名前から決まるロックディレクトリを出力親ディレクトリへ排他的に作成する。ロック取得後に出力先の存在、空かどうか、および所有マーカーを再確認し、その状態を直後の公開処理へ渡す。ロックは公開が成功または失敗するまで保持する。

同じ出力先を扱う別のclonoプロセスがロックを保持している場合、後続の処理は既存出力を変更せず失敗し、作成済みのstagingを削除する。ロックは同じ規約に従うプロセス間の協調的な排他制御であり、ロックを無視して出力を変更する外部プロセスに対するセキュリティ境界ではない。

既存の所有済み出力がある場合は、それを一時的なbackupディレクトリへ移動し、stagingを正式な出力先へ変更してからbackupを削除する。stagingの公開に失敗した場合は、backupを元の出力先へ戻す。

今回の検証は、正常終了時の置き換え、古い生成物の除去、およびロックを保持する別のビルドを既存出力の変更なしに拒否できることを確認した。プロセスの強制終了、OSのクラッシュ、backupの削除失敗、残留したロックの回復、ロックを無視する外部プロセス、およびファイルシステムをまたぐ移動に対する完全な原子性や復旧は保証していない。

### Vivliostyleとの結合

`vivliostyle.config.mjs`は`book.mjs`の原稿一覧を読み、各パスを生成済み原稿ルート以下の`entry`へ変換する。テーマには、生成済み原稿ツリー外にある`themes/theme.css`を指定する。

生成した原稿ツリーからVivliostyle CLI 11.1.0でPDFを作成し、PDF内の文字列を自動検証した。

- ルート直下のMarkdownに検証用変換が適用されている
- ネストしたMarkdownにも検証用変換が適用されている
- 変換前の検証用文字列が残っていない
- コピーしたHTMLの見出しと本文が掲載されている
- コピーしたSVG内の文字列がPDFへ描画されている
- 三つの原稿見出しが`book.mjs`で指定した順序に一度ずつ掲載されている
- 各entryの固有見出しと同じページに、原稿ツリー外のテーマが生成する文字列が存在する

これにより、原稿ツリーだけをミラーし、設定とテーマを元の書籍プロジェクトに残す構成で、Vivliostyleが利用できる書籍を生成できた。

## 検証結果

生成済み原稿ツリー方式は、初期の書籍プロジェクト一括変換基盤として技術的に成立する。

- Markdownと同じツリーにある静的ファイルを相対位置のままコピーできる
- ネストした原稿を含め、画像参照の相対パスを変更する必要がない
- Vivliostyle設定とテーマを複製せず、生成済み原稿から利用できる
- 一つの書籍構造を変換処理とVivliostyle設定の両方から参照できる
- CI上の空の作業環境を想定し、存在しない出力先を自動作成できる
- 所有マーカーにより、clonoが生成した出力と利用者が管理するディレクトリを区別できる
- stagingで出力を完成させてから公開し、所有済み出力に古い生成物を残さず再生成できる
- 所有していない非空ディレクトリを変更せず拒否できる
- 排他ロックの取得後に所有権を再確認し、同じ規約に従う並行ビルドを既存出力の変更なしに拒否できる

Markdownだけを兄弟ディレクトリへ出力する方式は、特定の配置では引き続き成立する。しかし、原稿ツリー内の静的ファイルも扱える方式を標準とするなら、生成済み原稿ツリーのほうが暗黙の配置制約を減らせる。

書籍プロジェクト全体の複製は今回の要件に不要であり、設定、テーマ、依存関係および生成物の同期をclonoの責務へ含めない判断を支持する。

## 責務候補

### clonoが担う候補

- 書籍構造と原稿順序を一つの入力から読み取る
- 入力原稿ルートと生成済み原稿ルートを検証する
- Markdownへclonoの変換パイプラインを適用する
- 原稿ツリー内の通過ファイルを相対位置のままコピーする
- すべての原稿の診断と出力準備が完了してから生成物を公開する
- 出力先を自動作成する
- 所有マーカーとstagingを使い、利用者のファイルを保護する
- 原稿一覧と生成済みファイルの不一致、パスの重複および出力先の衝突を診断する
- 実行中のclonoに同梱された基盤CSSを、生成済み原稿ツリーの可視な予約領域へコピーする
- 基盤CSSの予約領域を定義し、入力原稿との衝突を診断する
- 将来、空白ページ、索引などの生成物を原稿順序へ組み込む

### Vivliostyleへ委譲する責務

- 生成済みMarkdownと通過HTMLをVFMまたはHTMLとして処理する
- 書籍構造から渡された`entry`を指定順に組版する
- 生成済み原稿ツリーのclono基盤CSSを利用者テーマより先に適用する
- 原稿ツリー外の利用者テーマを適用する
- 画像など、生成済み原稿から参照する静的ファイルを読み込む
- HTML、Web出版物またはPDFを生成する

### 利用者が管理する候補

- 変換前の原稿と、その相対参照に必要な静的ファイル
- 書籍固有のVivliostyle設定とテーマ
- clonoが生成しない表紙、奥付またはその他の書籍資材

基盤CSSと利用者テーマをVivliostyleへ順序付きで渡す方法は、後続の[clono基盤CSSと利用者テーマの統合に関する調査](vivliostyle-clono-stylesheet.md)で技術的に成立することを確認した。npmパッケージをテーマとして指定する方式と、生成済み原稿ツリーへ基盤CSSをコピーする方式の両方が成立した。その後に策定した[書籍プロジェクト仕様](../specifications/book-project.md)では、初期仕様として後者を採用した。

## CLIに関する関連方針

fixtureの作成前に、単一ファイル変換と書籍プロジェクト変換を相互排他的なオプションではなく、異なるサブコマンドとして扱う方針へ合意した。

```shell
clono transform manuscript.md --output build/manuscript.md
clono build
clono build path/to/book
```

- `transform`は一つのMarkdownファイルを変換する
- `build`はカレントディレクトリまたは指定した書籍プロジェクトを一括変換する
- 現在の`clono <input> --output <output>`との後方互換性は、npm公開前かつ実利用前であるため維持しない

この名称、引数および設定ファイルの探索方法はfixtureで検証していないが、後続の[書籍プロジェクト仕様](../specifications/book-project.md)で初期の公開契約を定めた。標準出力と診断の収集順序を含む詳細なCLI表示契約は、実装前に決定する。

## 未確認・未決定事項

- 空白ページを追加する場合の書籍構造の拡張方法
- 原稿ツリー外にある画像などの静的ファイル
- 複数OSにおけるファイルの許可ビット、タイムスタンプ、ACLおよび拡張属性
- clono本体のClojureScript変換パイプラインとの結合
- 複数原稿から診断を収集する順序と、診断がある場合の出力契約
  - 2026-08-28に[書籍プロジェクト仕様](../specifications/book-project.md)で、原稿間では変換計画の順、同じ原稿内では入力位置の順に診断を収集し、一件でも診断があれば部分的な変換計画を公開しないと決定した
- 文書全体の情報収集、相互参照、索引および生成文書を挿入する処理段階
- 複数OSにおけるディレクトリの置き換えと復旧
- ロックを無視して出力を変更する外部プロセスとの競合
- 強制終了後に残ったstagingまたはbackupの検出と回復
- 強制終了後に残ったロックの判定と回復
- `build`サブコマンドの標準出力と診断の収集順序

これらは生成済み原稿ツリー方式の成立性を妨げない。初期の公開契約は[書籍プロジェクト仕様](../specifications/book-project.md)で定め、残る事項は実装順序と具体的な需要に応じて仕様を追加する。

## 依存関係の監査

2026年8月24日にfixtureで`npm audit`を実行した結果、固定した開発依存関係に7件のmoderateと3件のhighが報告された。`npm audit --omit=dev`では0件だった。

Vivliostyle CLI、VFMおよびMuPDFは検証専用の開発依存関係であり、clono本体のproduction依存関係として追加したものではない。fixtureは外部から受け取った信頼できない入力の処理には使用しない。調査対象との対応を維持するため、監査結果だけを理由に固定バージョンを変更しない。

## 再現方法

[検証用fixtureのREADME](fixtures/book-project-output-tree/README.md)を参照する。fixture内で`npm ci`を実行した後、`npm run verify`で出力ツリーとPDFを再検証できる。

Vivliostyle CLIはPDF生成時にローカルのHTTPサーバーを起動する。実行環境がローカルポートの待ち受けを禁止している場合は、その制限を解除した環境で`npm run verify:pdf`を実行する必要がある。

## 再調査する条件

- Thunder Clawの実原稿で、原稿ツリー外の静的ファイルを相対参照する必要がある場合
- 書籍プロジェクト全体を独立した場所へ出力する必要が生じた場合
- Vivliostyle CLIの`entry`、設定ファイルまたはテーマの解決方法が変更された場合
- 設定を一元管理するために、今回のJavaScriptモジュール共有方式を利用できない場合
- WindowsまたはLinuxで、stagingと既存出力の置き換えが成立しない場合
- 所有マーカーでは利用者のファイルを十分に保護できない事例が確認された場合
- 実際の相互参照、索引または空白ページを生成済み原稿ツリーへ組み込めない場合
- 生成済み原稿ツリーのclono基盤CSSをWebPubへ収録できない場合
- 生成済み原稿ツリーへ基盤CSSを含めることが運用上の問題になる場合
