# 索引の読み正規化・分類・並べ替えに関する調査

- 状態: 調査済み
- 調査日: 2026-09-12
- 最終更新日: 2026-09-12
- 検証環境:
  - OS: macOS 26.6.2
  - Node.js: 24.19.0
  - npm: 11.17.0
  - JDK: Temurin 21.0.12
  - ClojureScriptビルド: shadow-cljs 3.4.12

## 背景

[Vivliostyleの索引に関する調査](vivliostyle-index.md)では、VFMとVivliostyle CLIに要件を満たす索引自動生成機能が確認できないこと、および、clonoが索引構造を事前生成すれば、紙面上のページ番号とPDF内部リンクをVivliostyleへ委譲できることを確認した。

Thunder Clawの前身スクリプトでは、索引項目とともに、濁音、半濁音、促音および音引きをあらかじめ除いた読みを著者が指定していた。

```text
[index:バックナンバー|はつくなんはあ]
```

この方法では並べ替え処理を単純にできる一方、著者が通常の読みとは異なる索引用の文字列を手作業で入力する必要がある。clonoでは、著者が`ばっくなんばー`のような自然な読みを指定し、機械処理用の`はつくなんはあ`を導出することで負担を減らしたい。

また、異なる読みから同じ並べ替えキーが生成される場合もある。たとえば、`一気（いっき）`と`五木（いつき）`の並べ替えキーはともに`いつき`となる。実行環境や入力順により結果が揺れないようにするには、並べ替えキーだけでなく、衝突時の比較規則も明示する必要がある。

## 調査目的

- 著者が指定した読みから、幅と表記体系の差を吸収した正規化済み読みを生成できるか確認する
- 濁点、半濁点、小書き仮名および音引きを処理した並べ替えキーを生成できるか確認する
- 英数字と五十音の行へ、正規化後の読みを決定的に分類できるか確認する
- 並べ替えキーが衝突した場合も、環境に依存しない順序を生成できるか確認する
- 同じ表示語の出現箇所を統合し、矛盾する読みを検出できるか確認する
- 初期候補で受理しない読みを、黙って並べ替えずに拒否できるか確認する

この調査は、索引の著者向け記法、許可文字の最終的な範囲、診断文言または実装APIを決定するものではない。読みを自動取得または推定する機能も対象外とする。

## 技術検証

調査結果を再検証できるように、[検証用fixture](fixtures/index-normalization/)をリポジトリ内へ保存している。このfixtureはclono本体から独立したClojureScriptおよびnpmプロジェクトであり、`package.json`と`package-lock.json`によって依存関係を固定する。

fixtureでは、次のデータ変換を純粋関数として試作した。

```text
著者が指定した読み
  → 正規化済み読み
  → 並べ替えキー
  → 分類
  → 項目の統合と並べ替え
```

Vivliostyle、VFM、Markdown AST、ファイルシステムおよびロケール依存の照合APIは使用していない。

## 読みの処理段階

著者が指定する読みと機械処理用の値を混同しないため、候補アルゴリズムでは次の二段階を分けた。

### 正規化済み読み

最初の段階では、次の処理だけを行う。

1. Unicode正規化形式NFKCへ変換する
2. カタカナの`ァ`から`ヺ`までを対応するひらがなへ変換する
3. 英字を小文字へ変換する

この段階では、濁点、半濁点、小書き仮名および音引きを保持する。これにより、著者が指定した読みの意味的な違いを残したまま、全角と半角、ひらがなとカタカナ、英字の大文字と小文字による表記ゆれを吸収できる。

`ヷ`、`ヸ`、`ヹ`および`ヺ`には、コードポイントを一定量ずらして得られる単一のひらがながない。この4文字は、それぞれ`わ`、`ゐ`、`ゑ`および`を`と結合濁点の組み合わせへ変換した。これにより、正規化済み読みでは濁点を保持し、並べ替えキーではほかの濁音と同じ処理で濁点を除去できる。NFKCによって`ヷ`となる半角の`ﾜﾞ`も、同じ正規化済み読みに変換できた。音引きの母音を求めるときは結合濁点を飛ばして直前のかなを参照するため、`ヷー`から`わあ`を生成できた。

| 入力 | 正規化済み読み |
| --- | --- |
| `バックナンバー` | `ばっくなんばー` |
| `ガゾウ` | `がぞう` |
| `ヷ` | `わ`と結合濁点 |
| `Ａｎｄｒｏｉｄ １４` | `android 14` |
| `Ｃ＋＋` | `c++` |

### 並べ替えキー

日本語の正規化済み読みに対して、次の順で追加の変換を行う。

1. 音引きを、直前のかなが表す母音へ展開する
2. 濁点と半濁点を除去する
3. 促音を含む小書き仮名を、対応する通常のかなへ変換する

| 正規化済み読み | 並べ替えキー |
| --- | --- |
| `ばっくなんばー` | `はつくなんはあ` |
| `こんぴゅーたー` | `こんひゆうたあ` |
| `がぞう` | `かそう` |
| `いっき` | `いつき` |

英数字の正規化済み読みは、追加変換せず、その値を並べ替えキーとして使用する。

音引きは直前のかなに依存するため、ほかの変換より先に展開する。fixtureでは、`ゅー`を`ゅう`へ展開してから`ゆう`へ変換することで、`コンピューター`から`こんひゆうたあ`を生成できた。

## 読みの入力範囲

初期候補では、入力として次のいずれかとなる読みを受理した。

- ひらがな、カタカナの`ァ`から`ヺ`まで、および音引きだけからなる日本語
- ASCII英数字から始まり、ASCII英数字、半角空白および`.+@#/_-`だけからなる英数字列

日本語をひらがな化した後は、各かなに後置される結合濁点または結合半濁点も受理する。結合記号だけの入力や、結合記号が連続する入力は受理しない。

全角の英数字と記号は、NFKCによって許可されたASCII文字へ変換できる場合に受理できた。表示語そのものが`.gitignore`のように記号から始まる場合も、読みへ`gitignore`を指定すれば英数字として分類できる。

次の入力は、意味が不明確な値を推測せずに拒否できた。

| 入力 | 拒否理由 |
| --- | --- |
| 空文字または空白だけ | 並べ替える読みがない |
| `索引` | 読みに漢字が含まれる |
| `androidあぷり` | 日本語と英数字が混在する |
| `.gitignore` | 分類可能な英数字から始まらない |
| `ーど` | 音引きの前に母音を導出できるかながない |
| `んー` | `ん`から音引きの母音を導出できない |

この範囲は、初期仕様で必要な入力を小さく定義するための候補である。技術用語で実際に必要となる文字が確認された場合は、表示語と読みの役割を区別したうえで拡張を検討する。

## 分類

並べ替えキーの先頭文字を使い、次の固定順で分類できた。

| 順序 | 分類 | 対象となる先頭文字 |
| --- | --- | --- |
| 1 | 英数字 | `a`から`z`、`0`から`9` |
| 2 | あ行 | あ、い、う、え、お |
| 3 | か行 | か、き、く、け、こ |
| 4 | さ行 | さ、し、す、せ、そ |
| 5 | た行 | た、ち、つ、て、と |
| 6 | な行 | な、に、ぬ、ね、の |
| 7 | は行 | は、ひ、ふ、へ、ほ |
| 8 | ま行 | ま、み、む、め、も |
| 9 | や行 | や、ゆ、よ |
| 10 | ら行 | ら、り、る、れ、ろ |
| 11 | わ行 | わ、ゐ、ゑ、を、ん |

分類前に濁点、半濁点および小書き仮名を正規化するため、`がぞう`はか行、`ぱす`はは行、`ゃく`はや行へ分類された。索引項目を持たない分類は生成結果から省略できた。

この固定分類はThunder Clawの初期要件を満たす候補であり、将来のユーザー定義分類を否定するものではない。

## 決定的な並べ替え

索引項目は、次のキーを順に比較した。

1. 固定された分類の順位
2. 並べ替えキー
3. 濁点、小書き仮名および音引きを保持した正規化済み読み
4. NFKCで正規化した表示語
5. 元の表示語
6. 原稿中の初出位置

文字列比較には`localeCompare()`や`Intl.Collator`を使用せず、Unicodeコードポイントを先頭から比較した。日本語として自然な辞書順全体を独自に再現するのではなく、索引用の読みを優先し、同じキーを持つ項目だけを環境に依存しない規則で整列するためである。

fixtureでは、入力順を意図的に並べ替えた場合も次の順序を生成した。

- 英数字: `Android`、`API`
- あ行: `一気（いっき）`、`五木（いつき）`
- か行: `画像（がぞう）`、`コラム（こらむ）`
- は行: `橋（はし）`、`箸（はし）`

`一気`と`五木`は並べ替えキーがともに`いつき`となるが、正規化済み読みの`いっき`と`いつき`を次の比較キーにすることで、常に`一気`、`五木`の順になった。`橋`と`箸`は読みも並べ替えキーも同じため、表示語のコードポイント順で安定した。

## 同じ表示語の扱い

同じ表示語かつ正規化済み読みが同じ項目は、一つの索引項目へ統合し、出現箇所を原稿中の順序で保持できた。全角と半角、カタカナとひらがな、英字の大文字と小文字だけが異なる読みも、正規化後に同じであれば統合できる。

同じ表示語へ異なる正規化済み読みが指定された場合は、一方を暗黙に選ばず、読みの競合として拒否できた。並べ替えキーが同じでも、正規化済み読みが異なる場合は競合になる。たとえば、同じ`橋`へ`はし`と`ばし`を指定した場合はエラーとなる。

異なる表示語が同じ読みを持つ場合は統合しない。`橋（はし）`と`箸（はし）`は別々の索引項目として残る。

今回の候補アルゴリズムにおける「同じ表示語」は、入力された表示語の文字列が一致することを意味する。表示語自体のUnicode正規化による統合は行わず、NFKCで正規化した表示語は並べ替えの補助キーにだけ使用した。

## 評価

著者が指定した自然な読みから、前身スクリプト相当の索引用並べ替えキーを機械的に生成できる見通しが立った。少なくともThunder Clawの初期要件である、幅、カタカナ、英字の大文字小文字、濁点、半濁点、促音、小書き仮名および音引きを処理できる。

正規化後の値を一つだけ使うのではなく、意味的な差を保持した正規化済み読みと、索引順のために情報を畳み込んだ並べ替えキーを分けることで、次を両立できる。

- 表記ゆれを吸収して同じ読みを判定する
- 並べ替えキーが衝突した項目を決定的に並べる
- 同じ表示語へ矛盾する読みが指定されたことを検出する
- 将来、読みの入力と自動取得を切り替えても、後段の分類と並べ替えを再利用する

候補アルゴリズムはClojureScriptとJavaScriptの標準機能だけで実装でき、正規化または照合のための追加ライブラリを必要としなかった。ロケールとICUの差にも依存しないため、clonoが対応する複数OSで同じ結果を生成しやすい。

## 仕様策定への示唆

今回の結果から、初期仕様では次の契約を採用できる見通しが立った。

- 著者が指定する読みと、clonoが導出する正規化済み読みおよび並べ替えキーを区別する
- 初期仕様では読みを必須とし、自動取得は後続候補とする
- 読みをNFKC、ひらがな、ASCII小文字へ正規化する
- 日本語の並べ替えでは、音引き、濁点、半濁点および小書き仮名を正規化する
- 英数字と五十音の行を固定順で出力し、空の分類は省略する
- 文字列の比較順を明示し、実行環境のロケールへ委譲しない
- 同じ表示語と読みを持つ項目は統合し、出現箇所を原稿順に保持する
- 同じ表示語へ異なる正規化済み読みが指定された場合は診断する
- 異なる表示語は、読みが同じでも別の索引項目として保持する

索引の著者向け記法、入力位置を含む診断、書籍全体からの収集および生成先の索引文書は、後続の仕様と結合検証で定める。

## 成立条件と未確認事項

今回の結果は、索引項目へ読みが明示されていることを前提とする。次の事項は検証していない。

- 索引記法から表示語、読みおよび入力位置を取得するMarkdown AST処理
- 読みを省略した場合の自動生成
- 漢字の読み推定、形態素解析または外部辞書との連携
- 初期候補に含まれない英字、記号、空白または仮名の扱い
- ユーザーが分類単位と分類順を変更する設定
- 階層索引、ページ範囲、索引項目間の相互参照または主要ページの強調
- 書籍プロジェクト全体からの索引項目収集と出現順の決定
- 索引Markdownの生成、およびVivliostyle用設定との統合
- Thunder Clawの実際の項目数を使った複数ページの索引
- Windows、LinuxおよびNode.js 22系で同じ結果になること

Unicodeコードポイント順は、並べ替えキーと正規化済み読みが同じ場合の決定性を保証するための補助規則であり、一般的な日本語辞書の並べ替え規則を完全に再現するものではない。実原稿で不自然な順序が確認された場合は、追加の比較キーまたは明示的な並べ替え指定を検討する。

## 再調査する条件

- 初期仕様で許可する読みに、今回の候補アルゴリズムで扱えない文字が必要になった場合
- 読みを任意にし、自動取得または推定する場合
- ユーザー定義の分類または並べ替え規則を導入する場合
- Unicode正規化方式、比較規則または対応する実行環境を変更する場合
- 実原稿で、候補となる分類または並べ替えが著者の期待と一致しない例が見つかった場合
- 索引項目の統合単位を、表示語の文字列一致以外へ変更する場合
