# VivliostyleおよびVFMの機能調査計画

- 状態: 調査中
- 作成日: 2026-08-07

## 1. 背景

clonoは、Vivliostyle Flavored Markdown（VFM）による書籍制作に、出版物で必要となる表現力と文書横断機能を加えるためのツールである。

[プロジェクト憲章](../project-charter.md)では、VFM、HTML、CSSおよびVivliostyleの機能で十分に実現できる場合はそれらを優先し、独自記法を必要最小限にすることを定めている。また、ページ脚注、文書横断参照および索引などの技術的な難所は、仕様確定や大規模な実装より先に小さく検証する。

本調査は、現行のVFMおよびVivliostyleで対象機能を実現できる範囲と、clonoが担当すべき範囲を明らかにするために行う。

clonoとVivliostyleの責務分担は、[ADR 0001](../decisions/0001-distribution-and-build.md)に従う。本調査のためにVivliostyle CLIを実行することは、clono本体からVivliostyle CLIを起動するという製品上の責務変更を意味しない。

## 2. 目的

本調査では、プロジェクト憲章で対象とした各制作能力について、次の事項を判断できる状態を目指す。

- VFMの既存記法だけで実現できるか
- Raw HTMLおよびCSSで実現できるか
- Vivliostyleが期待するHTMLおよび紙面を生成できるか
- clonoによる補助が必要か
- clonoによる処理が必要な場合、その処理単位が局所、ファイルまたは書籍のいずれか
- 独自記法を検討する価値があるか
- 追加の技術検証が必要か
- 現時点では実現困難か

本調査は、各機能の詳細仕様や最終的な記法を決定するものではない。

## 3. 必須成果物

本調査の必須成果物は次のとおりとする。

1. 本文書へ追記する調査結果、根拠、制約および未解決事項
2. `research/vivliostyle-capabilities/`に置く再現可能な最小サンプル

調査用サンプルは、clono本体から独立したnpmプロジェクトとして管理する。直接利用する依存パッケージのバージョンを固定し、`package-lock.json`をコミットする。

サンプルから生成するPDF、HTML、キャッシュおよび`node_modules`は原則としてコミットしない。紙面上の問題を文章だけで説明できない場合に限り、小さなスクリーンショットを`docs/research/assets/`へ保存できる。

## 4. 対象外

本調査では次の事項を決定しない。

- clono独自記法の最終構文
- CLIオプションの最終的な名前と構造
- 設定ファイルの有無と完全なスキーマ
- 入力および出力ディレクトリの最終仕様
- 日本語索引の詳細な照合および整列規則
- 大規模な書籍に対する性能最適化
- 増分ビルドの方式
- 全OSでの詳細な互換性
- npm公開手順
- 安定版の後方互換性方針

調査結果からアーキテクチャ上の決定が必要になった場合も、本調査内で暗黙に決定せず、別途議論してADRへ記録する。機能の詳細仕様も、調査完了後に別途作成する。

## 5. 調査環境

### 5.1 バージョン方針

調査開始日時点の最新安定版を使用する。beta、RC、nightlyおよび未公開版は対象外とする。

- 直接利用する依存パッケージは正確なバージョンで固定する
- 推移的依存関係は`package-lock.json`で固定する
- `@vivliostyle/vfm`単体のバージョンと、Vivliostyle CLIが内部で利用するVFMのバージョンを区別して記録する
- 調査開始後に新しいバージョンが公開されても、原則として調査途中では更新しない
- 調査結果に影響する重大な修正が公開された場合は、元の結果を残したうえで追加検証する

### 5.2 標準条件

- OS: macOS
- Node.js: 24.19.0
- パッケージマネージャー: npm
- 文字コード: UTF-8
- 改行コード: LF
- 原稿言語: 日本語
- ページサイズ: A5
- 組方向: 横書き
- 段組み: 一段組み
- テーマ: 装飾を抑えた検証専用CSS

最初の調査ではクロスプラットフォーム検証を行わない。OS依存が疑われた場合に限り、追加環境で検証する。

## 6. 調査方法

各対象機能について、次の順序で調査する。

1. 実現したいHTMLまたは紙面上の結果を明記する
2. 現行VFMの既存記法と生成HTMLを確認する
3. Raw HTMLおよびCSSだけで実現できるか確認する
4. 必要に応じて最小サンプルを作成し、VivliostyleでHTMLまたはPDFを生成する
5. 入力、生成HTML、中間生成物および最終PDFのうち、機能に関係するものを確認する
6. 実現できる範囲、制約、未確認事項および失敗条件を記録する
7. clonoが担当すべき範囲を分類する

コマンドが正常終了しただけでは機能を実現できたと判定しない。期待するHTML構造または紙面上の結果まで確認する。

### 6.1 根拠の優先順位

複数の情報が食い違う場合は、次の順序で評価する。

1. 固定した調査環境での最小サンプルによる再現結果
2. 対象バージョンの公式ドキュメント
3. 関連する標準仕様
4. VivliostyleおよびVFMのソースコードまたは公式テスト
5. 公式IssueおよびDiscussion
6. その他の記事

公式ドキュメントに対応が記載されていても再現できない場合は、「文書上は対応しているが、調査環境では再現できない」と記録する。動作しても公式に文書化されていない場合は、安定した機能であると断定しない。

### 6.2 判定分類

各対象機能を次のいずれかに分類する。

| 分類 | 意味 |
|---|---|
| clono不要 | VFM、HTML、CSSまたはVivliostyleの既存機能で十分に実現できる |
| 文書化のみ | 既存機能の利用方法を案内すればよく、変換は不要 |
| 補助変換 | 既存機能で実現できるが、執筆体験を改善する局所的な変換に価値がある |
| ファイル単位 | 一つのMarkdownファイル全体を対象とした意味解決が必要 |
| 書籍単位 | 複数ファイルの順序、識別子または参照を対象とした意味解決が必要 |
| 追加検証 | 結論を出すために別の技術検証が必要 |
| 実現困難 | 現行環境では実制作に必要な品質で実現できない |

判定には、根拠の強さを高、中または低の確信度として併記する。

## 7. サンプル作成規則

- 一つのサンプルでは原則として一つの疑問だけを検証する
- 改ページなど必要な現象が確実に発生する最小限の原稿量を用意する
- 検証対象と関係のない装飾や機能を含めない
- 共通CSSにはページサイズ、組方向および基本書体など、本当に共通する指定だけを置く
- 通常ケースのIDにはASCIIを使い、日本語IDは専用ケースで検証する
- コード、表、脚注などの複合ケースは、個別機能を確認した後に別サンプルとして作成する
- ディレクトリ名、ファイル名、設定内の識別子およびスクリプト名は英語で記述する
- 原稿と調査説明には、目的に応じて日本語を使用する
- 実行コマンドと目視確認項目を各サンプルから確認できるようにする
- 生成物を手修正して成功扱いにしない

サンプルは、調査結果の根拠として実行確認が必要な項目に作成する。公式記法の存在と単純な挙動を確認するだけで十分な項目には、必ずしも個別サンプルを要求しない。

## 8. 調査対象

### 8.1 局所的な表現

次の機能について、VFMの既存記法、Raw HTML、CSSおよびVivliostyleの対応状況を確認する。

- 空行または紙面上の意図的な空白
- 強制改行
- 強制改ページ
- 段落の右寄せ
- 定義リスト
- コラムなどの囲み枠

特に次の点を確認する。

- ソース上の空行と紙面上の余白を区別できるか
- 改ページをclassおよびCSSで表現できるか
- 定義リスト内で複数段落やコードを扱えるか
- 囲み枠内でMarkdownを解釈できるか
- 囲み枠が複数ページにまたがる場合の組版結果

### 8.2 ページ脚注

次の点を最小サンプルで確認する。

- VFMの脚注が生成するHTMLと配置
- Vivliostyleによるページ脚注の対応状況
- `float: footnote`
- `::footnote-call`
- `::footnote-marker`
- 脚注番号を付与する主体
- 長い脚注がページをまたぐ場合
- 一ページに複数の脚注がある場合
- 表、リストおよび囲み枠内から参照する場合
- 脚注内で利用できるMarkdown
- 生成HTML上の参照関係

### 8.3 IDとキャプション

見出し、画像、表およびコードリストについて、次の点を確認する。

- VFMによる自動IDの生成規則
- 明示的なIDを指定する既存手段
- 日本語見出しと同名見出しのID
- ID重複の扱い
- `figure`、`figcaption`および`caption`の生成方法
- 参照対象のどの要素へIDを付与するか
- Markdown画像および表で表現できる範囲
- fenced code blockとIDおよびキャプションの共存
- 複数ページへまたがる表、図およびコードの組版結果

### 8.4 番号付けと相互参照

章、節、小節、図、表およびコードリストについて、次の点を確認する。

- CSS countersで番号を生成できる範囲
- `target-counter()`、`target-counters()`および`target-text()`の対応状況
- 参照先が後続ファイルにある場合
- 章ごとの番号リセット
- 番号なし見出し、前付、付録および後付
- 番号だけの参照
- 番号と見出しタイトルを含む参照
- 参照をリンクとして出力する方法
- 存在しないID、重複IDおよび種別が異なるIDの検出
- CSSで生成した番号と、検査可能なVFM Markdownとの関係

### 8.5 索引

次の点を最小サンプルで確認する。

- 索引語をHTML上でマークする方法
- 索引語のページ番号を取得する方法
- 後続ページおよび複数ファイルへの参照
- 同一ページにある重複ページ番号の扱い
- 索引から本文へのリンク
- 親項目および子項目を表現できる可能性
- 表示語と読みを分離できる可能性
- ページ範囲を表現できる可能性
- 見出し、脚注、表およびコード内の索引語

本調査では、日本語索引の最終的な整列規則を決定しない。まず、索引語を収集して正しいページ番号を出力できるかを優先して確認する。

### 8.6 Directiveと独自記法

Generic Directives Proposalおよび関連実装について、次の点を確認する。

- text、leafおよびcontainer Directiveの対応状況
- 属性、classおよびIDの表現
- Directiveのネスト
- Directive内部のMarkdown
- Markdown AST上のノード表現
- Markdownへ再出力した場合の保持
- 未知のDirectiveの保持
- ソース位置情報
- コードブロック内での扱い
- Raw HTMLと比較した可読性
- VFMまたは周辺ツールとの将来的な構文衝突の可能性

特定のDirective構文を採用する判断は、本調査の結果を用いた仕様検討で行う。

### 8.7 Markdownの往復性

代表的なVFM原稿をASTへ変換し、意味上の変更を加えずにMarkdownへ戻した場合について、次の点を最小サンプルで確認する。

- VFM固有記法
- Raw HTML
- Directive
- コメント
- 改行と空白
- 箇条書きと強調
- 表
- 脚注
- コードブロックのフェンスと言語指定
- ソース位置情報
- 未知の構文
- ファイル全体に発生する不要な整形差分

意味が同じでも大部分の行へ不要な差分を発生させる方式は、変換結果の検査可能性と執筆体験を損なうものとして評価する。

### 8.8 Vivliostyleの書籍構成との統合

書籍単位の意味解決に必要な章順およびファイル構成について、次の点を確認する。

- Vivliostyle CLIが原稿ファイルと順序を受け取る方法
- Vivliostyleの設定から章順を再利用できるか
- publication manifestを利用できるか
- globおよびディレクトリ指定の挙動
- テーマとCSSの指定方法
- 画像、CSSおよび原稿間の相対パス
- 中間生成物を別ディレクトリへ出力した場合のパス解決
- clonoとVivliostyleで章順および設定を二重管理せずに済むか
- watchモードおよび増分ビルドと組み合わせられるか

## 9. 調査の優先順位

技術的不確実性と他機能への影響を考慮し、次の順序で調査する。

1. 調査環境、依存バージョンおよび共通A5テーマの固定
2. ページ脚注
3. 索引のページ番号
4. Markdownの往復性
5. Vivliostyleからの章順取得
6. ID、番号付けおよび相互参照
7. Directive
8. 局所的な表現

調査途中で前提が崩れた場合は、残りの項目を機械的に進めず、本計画と優先順位を見直す。

## 13. 調査結果

### 13.1 ページ脚注: 最小ケース

[最小の脚注サンプル](../../research/vivliostyle-capabilities/cases/footnotes/minimal/README.md)で、同一のGFM風脚注一件をVFMの未指定、`pandoc`、`dpub`および`gcpm`モードで比較した。

| モード | HTML | PDF |
|---|---|---|
| 未指定 | `pandoc`とバイト単位で一致 | 重複するため生成しなかった |
| `pandoc` | 文書末の`section[role="doc-endnotes"]`に脚注を集約し、参照と戻りリンクを出力 | 本文の直後に文末脚注として配置 |
| `dpub` | `aside.footnote[role="doc-footnote"]`と参照および戻りリンクを出力 | `float: footnote`によりページ下部へ配置 |
| `gcpm` | 参照位置へ`span.footnote[role="doc-footnote"]`を出力 | `float: footnote`によりページ下部へ配置し、番号はVivliostyleが生成 |

この最小ケースでは、VFM 2.7.2とVivliostyle CLI内蔵VFM 2.7.0の脚注に関係するHTML構造に差は確認できなかった。三つのPDFはいずれもA5の一ページとして生成され、紙面上の欠落、文字化け、重なりおよび切れはなかった。

単純なページ脚注は、clonoによる独自記法やHTML変換を行わず、VFMの`dpub`または`gcpm`モードとCSSで実現できる。最小ケースだけを対象とした暫定分類は「clono不要」、確信度は高とする。

ページ脚注全体の分類は「追加検証」、確信度は高とする。複数脚注、長い脚注、複数参照、脚注内のMarkdown、各種ブロック内からの参照、番号制御およびリンクの違いを確認してから採用方式を判断する。

また、PopplerによるPDF検査では`pandoc`と`dpub`にname tokenの長さに関する警告が出た。紙面とテキスト抽出への影響は確認できなかったが、リンクまたは名前付き遷移先との関係を追加確認する。

### 13.2 ページ脚注: 複数の短い脚注

[複数の短い脚注サンプル](../../research/vivliostyle-capabilities/cases/footnotes/multiple-short/README.md)で、同じページから三件の短い脚注を参照した場合の`dpub`および`gcpm`モードを比較した。

| 項目 | `dpub` | `gcpm` |
|---|---|---|
| HTML上の脚注 | 原稿末尾の三つの`aside.footnote` | 各参照位置の三つの`span.footnote` |
| 番号 | VFMがHTMLへ1、2、3を出力 | Vivliostyleが1、2、3を生成 |
| 参照関係 | 参照と脚注本体をリンクで相互参照 | 明示的なリンクなし |
| PDF上の順序 | 参照順と一致 | 参照順と一致 |
| PDF上の配置 | 同じページの脚注領域 | 同じページの脚注領域 |

両モードとも脚注領域の区切り線は一本だけ生成され、三件の脚注に欠落、重なり、切れおよび順序の乱れはなかった。VFM 2.7.2とVivliostyle CLI内蔵VFM 2.7.0の脚注に関係するHTML構造にも差は確認できなかった。

一ページ内の複数の短いページ脚注について、暫定分類は「clono不要」、確信度は高とする。複数ページでは`dpub`の脚注本体が参照位置と異なる場所にあることが配置へ影響する可能性があるため、次に参照ページと脚注ページの対応を検証する。

Popplerによる`dpub`のPDF検査では、最小ケースと同じname tokenの長さに関する警告が出た。脚注数に伴って警告も増えたことから、リンクまたは名前付き遷移先との関係を引き続き未解決事項とする。

### 13.3 ページ脚注: 参照ページとの対応

[脚注の参照ページサンプル](../../research/vivliostyle-capabilities/cases/footnotes/reference-page/README.md)で、一ページ目と二ページ目から一件ずつ脚注を参照し、二件の脚注定義を原稿末尾にまとめた場合の`dpub`および`gcpm`モードを比較した。

| 項目 | `dpub` | `gcpm` |
|---|---|---|
| HTML上の一件目の脚注本体 | 二ページ目の本文より後 | 一ページ目の参照位置 |
| HTML上の二件目の脚注本体 | 二ページ目の本文より後 | 二ページ目の参照位置 |
| PDF上の一件目の脚注 | 参照と同じ一ページ目 | 参照と同じ一ページ目 |
| PDF上の二件目の脚注 | 参照と同じ二ページ目 | 参照と同じ二ページ目 |
| ページをまたぐ番号 | 1、2と連続 | 1、2と連続 |

両モードとも二ページのPDFを生成し、各脚注を対応する参照と同じページの脚注領域へ配置した。各ページの区切り線は一本で、欠落、文字化け、重なり、切れおよび番号の乱れはなかった。

`dpub`の脚注本体はHTML上では二件とも二ページ目の本文より後にあるが、PDF上では参照ページへ分かれた。したがって、少なくとも本ケースではHTML上の脚注本体の位置だけで紙面上の脚注ページが決まるわけではない。Vivliostyleによる対応付けの内部機構は本結果だけから断定しない。

原稿末尾に脚注定義をまとめた複数ページの原稿についても、暫定分類は「clono不要」、確信度は高とする。clonoが脚注定義を参照位置へ移動したりページを判定したりする必要は確認されなかった。`dpub`と`gcpm`の両方を候補として残し、次に長い脚注の配置と分割を検証する。
