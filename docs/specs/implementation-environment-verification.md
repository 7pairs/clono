- 状態：手順2の計画と手順3の検証成果物は、独立レビュー・二人の確認完了。手順4の追加検証計画は指摘対応・再レビュー・二人の確認を終え、追加検証成果物も独立レビュー・二人の確認完了。
- 対応する作業：[選定の手順書](../plans/0002-choose-implementation-environment.md)の手順2〜3と、手順4の[コラム内脚注の追加検証](#10-手順4の追加検証コラム内脚注)。

## 1. 目的と検証の範囲

[調査結果](../../research/implementation-environment/README.md)をもとに、ClojureScriptによる前処理CLIを、開発者が理解して保守できる構成で実現できるか確認する。

検証用の入力・記法・API・コマンドは、本書で定める小さな題材のためのものとする。製品の仕様や公開APIとして確定しない。候補の不成立も比較結果として残し、動かすためだけに検証範囲を広げない。

手順1後の相談で、Pandoc風のMarkdown記法から、参照元のページ下部に脚注を配置できることを必須条件として確認した。章末・文書末に注を集めるだけでは、この条件を満たさない。脚注を含む出力はHTMLの構造とPDFの配置を確認する。

## 2. 環境と依存の固定

### 2.1 実行環境

手順3の実行環境はmacOSとする。実行時にOSのバージョンとCPU、Node.js・npm・JDK・PDF確認ツールのバージョンを記録する。Windows・Linuxは今回、公式資料上の対応とパス処理上の制約を確認する範囲とし、実行済みとは扱わない。三つのOSを実行するCIは後続の整備で扱う。

| 対象 | 検証で使うもの | 確認する点 |
|---|---|---|
| Node.js | 24.22.0 | 手順1の候補を固定する。正式な最低対応バージョンは決めない |
| JDK | Eclipse Temurin 21.0.12 | shadow-cljsの開発・ビルド用。利用環境へは持ち込まない |
| npm | Node.js 24.22.0の実行環境で使うバージョンを記録 | lockfileを作成し、実際に解決した依存を固定する |
| PDF確認 | Popplerのpdftotext・pdftoppm | 文字列のページと位置、レンダリングしたページ画像を確認する |
| フォント | macOSのヒラギノ系を指定し、実際の埋め込みフォントを記録 | 字形差で判断が変わらないようにする |

手順2でNode.js 24.22.0とnpm 11.19.1への切り替えを確認した。Temurin 21.0.12の配置、pdftotext・pdftoppmのコマンドの存在も確認済みである。JDK・PDFツールの動作と依存の準備は未確認のため、手順3の環境確認で不足を解消し、解消できない場合は環境不成立として報告する。別のバージョンへ無断で置き換えない。

### 2.2 パッケージ

調査時に確認したバージョンを使用する。インストールとlockfileの作成は手順3で行う。

| 役割 | パッケージとバージョン |
|---|---|
| ビルド | shadow-cljs 3.5.7。同ツールのClojureScript 1.12.145を使用し、個別に上書きしない |
| 現行Markdown AST | unified 11.0.5、remark-parse 11.0.0、remark-directive 4.0.0、remark-gfm 4.0.1 |
| 現行HTML出力 | remark-rehype 11.1.2、rehype-stringify 10.0.1 |
| Markdown再出力 | remark-stringify 11.0.0 |
| 比較対象と後段変換 | @vivliostyle/vfm 2.7.2 |
| 組版 | @vivliostyle/cli 11.3.3。実際に解決されたVivliostyle.jsのバージョンも記録する |

ASTの操作はJavaScriptオブジェクト・配列と既存のAPIを基本とし、この検証のためにAST操作用ライブラリを増やさない。テストにはNode.js組み込みのnode:testとnode:assert/strictを使う。これは調査用の選択であり、製品の正式なテスト環境の選定ではない。

VFM内部のunified 9・remark-parse 8などはVFM自身の依存として扱い、現行remark系へ強制統一しない。間接依存はlockfileで固定する。取得に必要なネットワークや書き込みの許可は実行時の環境に従い、手順2の計画作成中にはインストールしない。

## 3. 比較する構成と順序

### 3.1 ビルド方式

最初に同じ小さなClojureScript処理を、二つの出力で比較する。

| ID | 構成 | 比較対象 |
|---|---|---|
| B-ESM | shadow-cljsの`:target :esm`・`:runtime :node`、npm依存に`:js-provider :import`を使用 | NodeのESM起動、REPL、外部ESM依存、実行時の拡張読み込み |
| B-CJS | shadow-cljsの`:target :node-script`、出力拡張子は`.cjs` | Node向け起動、REPL、ESM依存の読み込み方、実行時の拡張読み込み |

両方について開発用・配布用ビルドを確認する。実行時にパスが決まる拡張は動的importで読み込み、共通の小さなJavaScriptの読み込み関数が必要なら、その責務を読み込みとエラーの受け渡しに限定する。Node.js 24.22.0のrequireで読み込めるESM依存はそのまま利用する案も確認し、同期読み込みの制約を記録する。

ここでは固定したASTの小さな値を渡すだけとし、本全体やPDFの検証を両ビルド方式で繰り返さない。成立性と連携処理の少なさから、後続の比較を実行する方式を暫定的に一つ選び、理由を記録する。正式な採用は手順4で判断する。

どちらも成立しない場合、原因と対策の負担を共有する。標準のcljs.mainなど別のビルド方法を試す場合は、検証計画を追加で合意してから進める。

### 3.2 Markdownと脚注

選んだビルド方式で、次の経路を比較する。

| ID | 経路 | 確認する役割 |
|---|---|---|
| M-HTML | 現行remark系で解析・変換し、remark-rehypeからHTMLへ出力 | ディレクティブ、H1の加工、標準の脚注出力と必要な追加処理 |
| M-MD | 現行remark系で解析・変換し、Markdownへ再出力した後、VFMでHTMLへ変換 | VFMの脚注機能を利用しながら、前処理をASTで行えるか |
| V-BASE | 同じ通常MarkdownをVFMで直接HTMLへ変換 | VFMの既存動作を比較の基準にする。ディレクティブの製品実装は追加しない |

M-HTMLの脚注はremark-gfmとremark-rehypeの既存出力から確認する。標準出力が末尾注になる場合は、その結果を不足として記録する。VFMの脚注ハンドラーを現行remarkへ移植したり、汎用的な独自脚注処理を追加したりはしない。採用に必要な追加処理が分かれば、手順4で負担を判断する材料とする。

M-HTMLでは、入力にある検証用HTMLと生成するHTMLノードを保持するため、remark-rehypeとrehype-stringifyの`allowDangerousHtml`を有効にする。元のHTMLを再解析してAST上で加工することは、今回の必須条件にしない。

M-MDとV-BASEではVFMの`dpub`と`gcpm`を比較する。`pandoc`も対照として一度実行し、ページ下部脚注と混同していないことを確かめる。V-BASEでディレクティブを認識しないことは、VFMの不具合と扱わない。

M-MDでは独自ディレクティブを通常のMarkdownまたはHTMLノードへ変換してから再出力し、未変換の記法を後段のVFMへ残さない。コラムをHTMLにする場合は内部もHTMLへ変換し、開始・終了タグの間にMarkdown文字列を置くだけの処理は使わない。通常の脚注定義はVFMへ渡すMarkdownとして保持する。コラム内の脚注も同じ方法で保持できるとは仮定せず、別に確認する。

この段落の条件は、手順3で比較した構成に適用した。手順4では、[第10節](#10-手順4の追加検証コラム内脚注)に限ってコラムの出力方法の例外を設け、追加検証する。

現行remarkとVFMのパーサーを同じprocessorに混在させたり、VFMの内部パーサーを交換したりはしない。構成の不成立を隠すために原稿の正規表現置換を追加しない。

### 3.3 最小の本への接続

成立した経路で、二章分の処理、設定の共有、VivliostyleのPDF生成を確認する。失敗した経路は失敗箇所と未実行項目を記録し、すべての項目を無理に実行できる形へ作り替えない。

## 4. 入力と期待結果

### 4.1 本の構成

検証用の`fixtures/book/book.json`に、章の順序とファイルを次の順で定義する。ファイル名の順ではなく、この順序を唯一の定義とする。

| 順序 | 原稿 | H1 |
|---|---|---|
| 1 | `chapters/z-first.md` | `導入` |
| 2 | `chapters/a-second.md` | `実践` |

拡張パス、出力先、章扉画像の対応もこの設定に置く。VFM向けの生成先一覧を設定から導出し、`vivliostyle.config.js`が同じ定義を読み取る。章の配列を別ファイルへ手で複製しない。元の設定形式を製品仕様として固定する意図はない。

章番号とタイトルは、H1の表示を差し替える前に収集する。第1章から第2章への前方参照と、第2章から第1章への後方参照を入れる。

### 4.2 独自記法と標準Markdown

検証用の記法は次とする。属性の名前や値は今回の題材に限定する。

````markdown
# 導入

次は:chapter[chapters/a-second.md]を参照する。
索引語は:index[非同期処理]とする。

::pagebreak

:::column
**強調した説明**と普通の本文。

- 項目A
- 項目B

`コード内の :chapter[chapters/a-second.md] は置換しない`
:::

```text
:chapter[chapters/a-second.md]
::pagebreak
:::column
```
````

期待結果は次のとおりとする。

- インラインの章参照だけを`第2章 実践`へ変換する。
- 改ページは専用のHTML要素とCSSで表し、後続の短い識別文字列が次ページへ移る。
- コラムは`div.column`として出力し、内部に強調、段落、二つのリスト項目、インラインコードを保持する。
- コード内・コードブロック内の同じ記法は文字列として保持する。通常本文中のコロンも変換しない。
- 索引項目は二章から集め、章番号・ファイル・行位置を含む一覧へ出す。索引ページやページ番号の生成は行わない。

索引語`非同期処理`は両章に一回ずつ置き、一覧では章順に二件確認する。収集と変換を分け、後ろの章の情報を先に処理する章からも利用できることを確かめる。

### 4.3 JavaScriptの拡張

初期状態では通常のH1を出す。外部の`title-image.mjs`へ変更したときだけ、元の見出しを非表示で残し、`div.chapter-title`と章扉画像を含む構造に変える。さらに`title-text.mjs`へ差し替え、目に見える別の章扉構造へ変わることを確認する。

本体のビルド後に拡張ファイルを変更し、CLIを新しいプロセスとして起動し直す。本体成果物のハッシュが変わらず、出力が切り替わることを確認する。プロセス内のホットリロードは求めない。

検証APIは、標準のJavaScriptオブジェクトでノードと章情報を受け取り、ノードまたはPromiseを返す小さな関数とする。具体的な渡し方はこの題材内に限定し、公開APIにしない。拡張側にClojureScriptのマップ操作やトランスパイルを要求しない。

同期成功、Promise成功、同期throw、Promiseのrejectを用意する。失敗時は終了コードを非0にし、拡張ファイル名と原因のメッセージを確認できるようにする。原稿由来のエラーでは原稿ファイルと位置を確認する。未処理のrejectを残さない。

### 4.4 ページ下部脚注

原稿は通常の参照式を使い、ページ下部脚注を実現するためのspanを著者に書かせない。

```markdown
PAGE_ONEの本文に脚注を置く。[^first]

[^first]: NOTE_ONE。**強調**と[リンク](https://example.com/)を含む短い注。

<h2 class="probe-next-page">PAGE_TWO</h2>

PAGE_TWOにも脚注を置く。[^second]

[^second]: NOTE_TWO。こちらも短い注。
```

A5、余白18mm、本文10ptを基本とし、`probe-next-page`に`break-before: page`を指定して二ページに分ける。外部URLのリンク先は取得しない。

| 比較 | 設定・期待する出力 | 確認 |
|---|---|---|
| VFM dpub | 参照と`role="doc-footnote"`を持つ注本文 | 脚注化のための独自CSSを加えずPDFを確認する |
| VFM gcpm | `span.footnote` | `.footnote { float: footnote; }`と番号表示用CSSを明示してPDFを確認する |
| VFM pandoc | 文書末尾の注一覧 | 対照。必須条件を満たした出力には数えない |
| M-HTML標準出力 | 現行remark系が生成するHTML | 実際の構造・PDFを記録し、ページ下部脚注を満たすか判定する |

必須の成功条件は、NOTE_ONEがPAGE_ONEのページ下部に、NOTE_TWOがPAGE_TWOのページ下部に一回ずつ表示され、本文中の参照番号との対応が分かることとする。本文中への注本文の露出、欠落、意図しない重複、章末の一覧だけの出力は不成立とする。

HTMLでは参照先、注本文、強調・リンクの保持を確認する。PDFではテキストと座標を取得し、注が参照と同じページで本文より下にあり、注の上端が本文領域の下三分の一にあることを確認する。これは短い検証入力に対する判定とする。さらに各ページを画像化して、脚注領域、番号、重なり、文字欠けを目視する。テキストに注が存在することだけで合格にしない。

同じ参照式をコラム内にも一つ置き、脚注との共存を確認する。本文だけでは成立してもコラム内で成立しない場合は制約として分けて記録し、二人で許容可否を判断する。さらに長い注と同じ注への複数参照を補助例として確認するが、分割規則やページをまたぐ重複参照の完全対応まで製品仕様として確定しない。

GCPMの番号用CSSは、公式の脚注ガイドで説明される`::footnote-call`・`::footnote-marker`とfootnoteカウンターを使う。DPUB向けの脚注番号生成と二重適用しない。

T09では、コピー先にビルドツールとCLJSソースを含めず、PATHをNode.jsと必要なシステムコマンドに限定し、JAVA_HOMEとCLASSPATHを除外する。Java起動を検出して失敗する検証用の代替コマンドをPATH先頭に置き、ビルド用の元ディレクトリを参照していないことも確認する。これはmacOS上での分離確認であり、JDKが一切入っていない別OSの実行実績にはしない。

原稿がエラーの場合にVivliostyleへ進まないことは、二つのコマンドを`&&`で連続実行して確認する。CLI内へVivliostyleを組み込む必要はない。

## 6. 実装と検証の進め方

手順3では、各題材を小さく区切って進める。

1. 環境と依存を準備し、ビルドと外部ツールの起動を確認する。この部分の失敗は環境不成立として扱う。
2. T01〜T03のテストを先に書く。構文・モジュール解決の失敗を除き、期待する振る舞いの欠如で失敗することを確認してから検証用処理を書く。両ビルド方式を比較する。
3. 暫定的に選んだビルド方式で、T04〜T07の期待値を先にテストへ書き、失敗理由を確認してから題材を実装する。
4. T08は先にHTMLの構造をassertする項目とPDFの目視項目を用意する。既存ツールだけで実行できるV-BASEや標準のM-HTMLは、現状をそのまま観測する。失敗するように既存ツールを改変しない。
5. T09の分離先で成立した構成を実行し、T10を二人で確認する。

既存ツールの挙動観測、REPL・source mapの手動確認、PDFの組版確認は、テストが先に失敗する方式の対象外とする。独自に書く変換処理とエラー処理には、振る舞いの欠如を検出する確認を行う。

## 10. 手順4の追加検証：コラム内脚注

### 10.1 目的と範囲

手順4の採用判断に先立ち、現行remarkで解析・加工したコラムを、内部のMarkdownと脚注定義を保ってVFMへ渡し、参照元ページの下部に脚注を配置できるか確認する。

手順3ではコラム内部を先にHTMLへ変換したため、内部の脚注が末尾注になった。完了済みの手順3の実施記録と結果は残し、今回の結果を追加して比較する。コラム内のページ下部脚注は、対応の負担を確認して採否を判断する。成立しない場合も、理由と必要な対応を整理すれば追加検証を終えられる。

対象は、コラム内の強調・リスト・コード・短い脚注と、前後の通常本文との共存とする。コラムの入れ子、同じ脚注への複数参照、長い脚注の分割規則、汎用プラグインAPIは対象外とする。

### 10.2 検証する方法と停止条件

既存の「現行remark → Markdown再出力 → VFM」を使う。手順4の追加検証に限り、[3.2節](#32-markdownと脚注)の条件の例外として、コラムの開始・終了を表すHTMLとMarkdownの子要素を分けて再出力する方法を検証する。内部を丸ごとHTML化せず、VFMが脚注を処理できる形で渡せるか確認する。

HTMLで囲まれた部分をVFMがMarkdownとして解析するかは未確認であり、成立を前提にしない。この方式を製品に採用することも意味しない。成立しない場合は、既存APIで扱える局所的な別案があるかを確認する。

新しい依存、パーサーの改造、汎用の脚注変換が必要になった時点で止め、理由と必要な対応を相談する。成功するまで検証範囲を広げない。

環境と依存は手順3と同じものを使い、ESMで検証する。独自の変換処理はClojureScriptを基本とし、既存コード全体の移植は行わない。元原稿は変更せず、別の場所へ出力する。

### 10.3 入力と期待結果

| 題材 | 確認すること |
|---|---|
| コラム単体 | 強調・リスト・コードを保持し、短い脚注がページ下部に一回表示される |
| 通常本文とコラムが混在する二ページ | ページごとに本文とコラムへ別々の脚注を置き、すべて参照元ページの下部に表示される。コラム前後の本文も正しく残る |
| 脚注定義をコラム外に置く例 | 参照はコラム内、定義は後方の通常本文側に置いても解決できる |
| コード内の記法 | コード中のコラム記法や脚注らしい文字列が変換されない |

コラム単体の例では脚注定義もコラム内に置き、定義を外に置く例と区別する。各脚注には別々の識別子を使う。

HTMLでは、コラムの囲み、Markdown要素、脚注参照と注本文の対応を確認する。PDFでは、短い注が参照と同じページの本文領域の下三分の一にあり、番号が対応することを、4.4節と同じ座標検査と全ページの画像で確認する。欠落・意図しない重複・重なり・文字欠けも確認する。

脚注モードは既存のdpub・gcpmを比較し、それぞれのCSS条件を維持する。片方だけ成立した場合も違いを記録し、両方の成功を完了条件にはしない。

### 10.4 実施の順序

1. 入力と期待値を用意し、現在の処理ではコラム内脚注がページ下部に出ないことを確認する。
2. 変換処理のテストを先に書き、期待する構造が欠けて失敗することを確認してから、最小限の処理を実装する。
3. 再出力したMarkdown、VFMのHTML、PDFの順に確認する。
4. 既存の自動テスト10件と、通常本文のdpub・gcpm脚注を再確認する。実行依存や起動方法を変えた場合は、Java不要の分離確認も行う。
5. 必要な独自処理、その理由と負担を説明し、開発者の理解を確認する。

既存ツールの挙動観測とPDF確認には、失敗させてから実装する順序を適用しない。独自に書く変換処理では、期待する振る舞いの欠如を検出する。
