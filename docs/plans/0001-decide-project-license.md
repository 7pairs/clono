# 配布ライセンスと適用範囲を決め、リポジトリに明示する

- 状態：進行中（手順1完了）

## 1. 目的

clonoの配布ライセンス、適用範囲、著作権・ライセンス表示の方法を決定し、最初のコードを追加する前にリポジトリへ明示する。

再利用者が条件と元の作者を把握でき、悪意のない再利用に伴う行き違いを減らせる状態を目指す。

予定する配置とブランチは次のとおりとする。

実施方法は、[プロジェクト憲章](../project-charter.md)・[SDD](../sora-driven-development.md)・[Sora Flow](../sora-flow.md)・[開発フロー](../development-workflow.md)に従う。

調査資料は番号なしの内容名で配置し、本手順書から調査資料へ、調査側の`README.md`から本手順書へリンクして対応関係を保つ。

調査資料の配置規則の変更は合意済みであり、本作業では手順1から適用する。開発フロー第2.2節への反映は、手順3で行う。

手順書の合意・独立レビュー・ファイル化は、本作業に先立つ準備として行う。作業ブランチの用意と本手順書のコミットは開発者が行い、明示的な着手依頼を受けてから手順1を開始する。

## 3. 合意済みの選定条件

- 商用利用、改変、ソース非公開での組み込み・再配布を許容する。
- GPL系は候補から外す。
- MITとApache License 2.0を比較し、希望を満たさない点が見つかった場合だけ候補を広げる。
- clono側でライセンスを決められるコード・文書・サンプル・調査用コードには、原則として同じライセンスを適用する。
- 第三者の権利やライセンスが関わるものは、その条件に従って区別する。
- 開発者本人の名義は`HASEBA Junya (7pairs)`とする。
- 管理する各ソースファイルには、原則として著作権・ライセンス表示を入れる。
- 第三者由来のファイル、生成物、コメントを書けない形式は、それぞれに適した扱いを決める。

悪意ある相手への対抗策を網羅することや、すべてのライセンスから最適なものを探すことは目的にしない。

## 4. 対象範囲と対象外

### 対象範囲

- 候補ライセンスの調査・比較。
- 適用範囲と例外の確認。
- 著作権表示、ファイル単位の表示、年の扱いの決定。
- ADR、ライセンス方針、ライセンス全文の作成。
- READMEでの案内。
- 合意した方針に基づく、既存ファイルへの必要な表示。
- 開発フローへの決定事項と参照先の反映。
- 各工程の検証・独立レビューと、PRの外部レビューへの対応。

### 対象外

- 本体・サンプル・動作確認用コードの追加。
- 実装言語、実行環境、依存ライブラリの採用。
- CIやライセンス自動検査の導入。
- 配布・リリースの実施。

将来採用する依存ライブラリとの整合性は、実際の採用時に確認する。今回の決定だけで、未選定の依存ライブラリまで確認済みとは扱わない。

## 5. 共通の進め方

各手順は、着手依頼を受けてから実施する。

成果物の検証・独立レビューを行い、指摘への対応を二人で判断する。修正した場合は再レビューする。開発者が内容を理解してコミットした後、次の手順への合意と着手依頼を受ける。

手順1〜5は別々のコミットとして扱い、まとめない。レビュー対応などでコミットが増えることは許容する。

手順書の状態は、記録時点で実施・検証・独立レビュー・二人の確認を終えた手順を示す。コミット待ちなどのGit操作の状態は含めず、コミットの事実はGit履歴で追う。次の手順への着手には、引き続きコミットと着手依頼を必要とする。

手順5までの確認が済んだ時点では、「手順1〜5の実施・内部確認完了」と記録する。外部レビューと作業全体の完了状況は、対応するPRで確認し、その完了を文書へ転記するためだけのコミットは行わない。この状態管理方針の開発フローへの反映は、手順3で行う。

日本語文書は`yomiyasu`で推敲する。ただし、採用ライセンスの公式本文や引用文は、推敲によって書き換えない。

## 6. 作業手順

### 手順1：候補と既存ファイルを調査する

**作業**

- MITとApache License 2.0の公式本文・公式の適用案内を確認する。
- 合意済みの利用・再配布条件、表示義務、変更したファイルの扱い、特許に関する規定、管理の手間を比較する。
- 既存ファイルに、第三者由来の内容や個別のライセンス表示がないか確認する。
- 本文から確認できる条件と、解釈・追加確認が必要な点を区別する。

**成果物**

`research/project-license/README.md`に、比較結果、参照URL・確認日、既存ファイルの確認結果、本手順書へのリンクを記録する。内容が長くなる場合は、同じ調査ディレクトリ内の別文書に分け、READMEから参照する。`fixtures/`や`scripts/`などの下位ディレクトリは、必要な場合だけ作成する。

**検証・レビュー観点**

- 各比較項目が公式資料に対応しているか。
- 利用の許可と、再配布時の条件を混同していないか。
- 著作権表示の保持と、作者の紹介・宣伝を混同していないか。
- 第三者の権利を一律に開発者本人のものとして扱っていないか。
- 不明な点を推測で確定していないか。

**区切り**

比較結果と残る疑問を二人で確認する。候補を広げる必要があれば、その理由と追加調査の範囲を合意してから進める。

### 手順2：採用方針と表示方法を決める

**作業**

調査結果をもとに、次を二人で決定する。

- 採用するライセンス。
- コード・文書などへの適用範囲と例外。
- `HASEBA Junya (7pairs)`を用いる著作権表示。
- 年の記載・更新方法。
- ソースファイルのヘッダ書式。
- 生成物やコメントを書けない形式への表示方法。
- 第三者由来の内容を追加するときの確認・表示方法。

**成果物**

- ADR：比較した案、採用理由、見送った理由、影響を記録する。
- `docs/specs/licensing.md`：適用範囲、表示例、例外、今後の追加・更新時に守る方針を記述する。

調査資料は根拠、ADRは判断理由、ライセンス方針は現在の運用を担う。重複する説明は参照でつなぐ。

**検証・レビュー観点**

- 合意済みの希望を満たしているか。
- 公式本文にない制限や義務を、ライセンス条件として追加していないか。
- 名義・年・表示方法が一貫しているか。
- 例外の扱いを後続の作業者が判断できるか。

**区切り**

採用ライセンスと運用方針に合意する。未解決の問題が採用判断に影響する場合は、文書への適用へ進まない。

### 手順3：ライセンスと案内をリポジトリへ反映する

**作業**

- 採用ライセンスの公式本文を、必要な記入箇所を除いて改変せず配置する。
- 合意した著作権表示を記載する。
- READMEに、ライセンス、名義、適用範囲、例外の確認先を案内する。
- 既存ファイルへの必要な表示を、手順2の方針に従って反映する。
- 開発フローに、決定したライセンス方針と関連文書への参照を加える。
- 開発フロー第12節を、コード追加前にライセンスを決定する今回の順序に合わせて更新する。
- 開発フロー第2.2節を、調査資料は番号なしの内容名で配置し、手順書との相互リンクで対応を保つ規則へ更新する。
- 開発フローに、手順書の状態は実施・内部確認の進捗を示し、外部レビューと作業全体の完了状況はPRで確認する方針を反映する。コミット待ちの記載や、完了を転記するためだけのコミットは求めない。

READMEを新規作成する場合は、今回必要な案内と開発フローへの導線を中心とし、未決定の機能や導入方法を説明しない。

**成果物**

ライセンス全文、README、必要な既存ファイルの表示、更新した開発フロー。

**検証・レビュー観点**

- ライセンス全文が公式本文と一致しているか。
- ライセンス名、識別子、名義、年、適用範囲に不一致がないか。
- 第三者の表示を削除・上書きしていないか。
- 必要なリンクが辿れるか。
- 本体コードや、合意していない環境設定を追加していないか。

### 手順4：全体の整合性と整理の要否を確認する

**作業**

- 調査結果、ADR、ライセンス方針、ライセンス全文、README、開発フローの整合性を確認する。
- 説明の重複や、参照先の分かりにくさを見直す。
- 今回コードを追加していないことと、コード構造への影響を確認する。
- 構造の見直し対象がなければ、その判断を記録する。
- 整理が必要なら、理由・範囲・検証方法を合意してから実施する。

**成果物**

見直し結果と、必要に応じた文書の整理。後続課題が生じた場合は、理由と影響を記録し、`docs/backlog.md`で管理する。

**検証・レビュー観点**

- 利用者が再利用条件と元の作者を把握できるか。
- 新しいソースを追加するときに、表示方法を判断できるか。
- 調査結果と採用判断を混同していないか。
- 今回必要な判断を、後続課題へ先送りしていないか。
- 今回の範囲を超える改善を取り込んでいないか。

### 手順5：PRレビューに出せる状態を確認する

**作業**

- 本手順書の実施記録と、各手順の検証・レビュー結果を確認する。
- 差分全体、文書間のリンク、表記の整合性を確認する。
- 必要な日本語文書の推敲と静的検査を行う。
- 開発者が変更内容、選定理由、運用上の注意点を理解できているか確認する。
- PR説明に記載する概要・検証結果・関連文書を整理する。
- PR提出前の確認結果を、本手順書の実施記録に追記する。
- 手順書の状態を「手順1〜5の実施・内部確認完了」とし、外部レビューと作業全体の完了状況は対応するPRで確認する旨を記載する。

**成果物**

PRレビューに出せる状態の変更一式と、PR提出前の確認結果を追記した手順書。手順5の確認結果の記録を、この手順のコミットに含める。

**区切り**

開発者による確認とコミット後、PRを作成する。PR作成・pushは開発者が行い、そらが操作する場合は明示的な依頼を必要とする。

## 7. 外部レビューと完了条件

PRでは、暫定運用中のCodeRabbitによる外部レビューを受ける。

指摘の扱いは二人で判断し、修正した場合は検証と再レビューを行う。修正内容を開発者が理解してからコミットする。

次を二人で確認して、作業全体を完了とする。

- ライセンスの採用理由をADRから追える。
- 適用範囲、例外、名義、年、表示方法が決まっている。
- 必要なライセンス本文・表示・案内がリポジトリに反映されている。
- 開発フローに、決定事項と参照先が反映されている。
- 本体・サンプル・動作確認用コードを追加していない。
- 合意した検証、独立レビュー、必要な再レビュー、外部レビューが済んでいる。
- 指摘と残した課題の扱いが決まっている。
- 実施記録が揃い、開発者が内容を理解している。

マージ前には、未解決のレビュー会話がないことも確認する。作業完了とマージは区別し、マージは基本的に開発者が行う。
