# 0003 最小限の開発基盤とバージョン表示を実装する

- 状態：手順1〜4の実施・内部確認完了（手順5以降は未着手）。CIのGitHub Actions上での実行確認は通常のPRで行う。

## 1. 目的

最初の製品機能としてバージョン表示を実装し、今後の機能を開発・検証できる最小限の基盤を整える。

ClojureScriptのソース変更から、ビルド、テスト、CLIの実行、CIでの確認までを一通り行える状態にする。

## 2. 前提と対象範囲

実装言語・実行環境は、既存の[実装環境仕様](../specs/implementation-environment.md)に従う。調査用コードやコマンドを、そのまま製品の構成として採用したものとは扱わない。

### 今回扱うもの

- 製品コード、テスト、ビルド設定の配置。
- 開発用・配布用のビルド。
- 正式なテスト環境と開発・検証コマンド。
- REPLとテストの継続実行。
- バージョン表示と、最小限の引数処理。
- macOS・Windows・LinuxでのCI。
- 生成物や開発ツールのキャッシュを除外する`.gitignore`。
- 開発方法と、今回実装するCLIの使い方の文書化。

### CLIの合意済みの範囲

- `--version`を指定すると、バージョン番号を表示して正常終了する。
- 初期バージョンは`0.0.0`とし、番号の管理元を一つにする。
- 引数なしでは短い使い方を表示する。
- 未知の引数はエラーとして扱う。
- 開発用コマンドと、ビルドしたCLIの直接実行を可能にする。

出力の具体的な書式、出力先、終了コード、複数の引数を指定した場合の動作は、手順1で具体化する。

### 今回扱わないもの

- Markdown変換、索引、章参照、出力の差し替えなどの製品機能。
- 製品の設定形式と公開する拡張API。
- `--help`と`-v`の追加。
- インストール方法、npm公開、リリースの自動化。
- 将来の採番規則と互換性方針。
- 正式なPRレビューツールの選定。
- VSCode・Calva専用の設定。

将来`--help`を追加する際は、引数なしの案内との統合を検討する。

[backlog](../backlog.md)の依存リスクは今回の主対象に含めない。ただし、依存更新や利用条件の変更が見直し条件に該当する場合は、対応範囲を相談する。

各手順は、[開発フロー](../development-workflow.md)に従って進める。着手依頼を受けて作業・検証・独立レビューを行い、指摘を二人で検討する。必要な修正・再レビューと記録更新を終え、開発者が内容を理解したことを確認してからコミットする。次の手順には、合意と着手依頼を受けてから進む。

## 5. 作業手順

### 手順1：開発基盤とCLIの仕様・設計・検証項目を決める

**作業**

必要な公式資料と既存の検証結果を確認し、次を具体化する。

- テストツールと、CLJSの処理・CLI全体を確認するテストの分担。
- ソース、テスト、ビルド成果物の配置。
- 開発用・配布用ビルドと、CLIの起動方法。
- バージョン番号の管理元と、表示へ反映する方法。
- ビルド、テスト、REPL、テスト継続実行のコマンド。
- CLIの出力書式、標準出力・標準エラー、終了コード、引数の組み合わせ。
- CIの実行基盤、起動条件、各OSの実行環境。
- 生成物・キャッシュと、管理対象として残す設定の区別。

新規に採用する依存やツールは、用途、保守状況、ライセンス、費用、採用済み環境との適合性を確認する。

テスト項目には、正常系と不正な引数に加え、配布用ビルドの直接実行、バージョン番号の管理元との一致、テスト失敗の検出を含める。

**成果物**

開発環境とCLIの仕様・設計、入力・期待結果・実行方法を含む検証項目。選定理由と根拠資料。

**検証・レビュー**

合意済みの範囲との一致、テストの過不足、構成の単純さ、OS固有の前提、調査用コードとの境界を確認する。

**二人の確認**

採用する構成と検証項目に合意してから、環境整備とテストコード作成へ進む。

実験なしでは決定できない事項が見つかった場合は、その実験の手順と確認地点を具体化し、合意してから実施する。

### 手順2：開発・テスト環境を整える

**作業**

製品機能の実装は手順3で行う。この手順では、接続確認に必要な最小限のコードだけを用意する。

**成果物**

ビルド・テスト設定、開発コマンド、依存の固定情報、`.gitignore`、接続確認の記録。

**検証・レビュー**

ローカルで開発用・配布用のビルド、REPLの接続・評価、テストの継続実行を確認する。テストの意図的な失敗が、実行結果と終了コードに反映されることも確認する。

設定とコマンドが手順1の設計に一致し、特定の端末や未管理ファイルに依存していないかレビューする。

**二人の確認**

各コマンドの役割と、失敗時の確認方法を共有する。

### 手順3：バージョン表示と最小限の引数処理を実装する

**作業**

**成果物**

### 手順2：開発・テスト環境を整える

- 実施結果：ルートに`package.json`・`package-lock.json`・`shadow-cljs.edn`、開発コマンド、Node.js・SDKMANの版指定、`.gitignore`を追加した。CLJSの単体テスト、Node.jsのCLI起動テスト、ESMの開発用・配布用ビルド、REPL用ビルドを接続した。CLI本来の引数処理とバージョン表示は未実装であり、仮コードで接続だけを確認した。
- バージョン情報の生成：先にテストと空の生成関数を用意し、ファイルが生成されないことと、不正な入力を拒否しないことにより7件が失敗することを確認した。その後に生成処理を実装し、7件の成功を確認した。管理元の欠落、不正なJSON、番号の欠落・型・空文字列を拒否する。D09では内容と最終更新時刻の不変を確認し、同じ内容を常に上書きする変更を一時的に入れると失敗することも確認した。
- 使用環境：macOS arm64、Node.js 24.22.0、npm 11.19.1、Temurin 21.0.12+8、shadow-cljs 3.5.7。端末の既定JDKは25だったため、検証コマンドに`JAVA_HOME`と`PATH`を指定して21を使用した。既定の設定は変更していない。
- ビルド・テスト：`npm ci`と`npm run verify`を実行した。生成処理7件、CLJSの接続確認1件・2アサーション、開発用・配布用CLIの起動確認2件が成功した。ビルド警告は0件。配布用のsource map生成も確認した。これらは製品CLIのC01〜C09・C11〜C12を確認したものではない。
- 失敗検出：D02・D03として、単体テストとCLI起動テストの期待値を一時的に変え、それぞれのコマンドと`verify`が非0になることを確認した。D04では構文エラーを一時的に追加し、コンパイル失敗後に既存のテスト成果物を実行しないことを確認した。C10のビルド接続確認では番号を空にし、開発用・配布用とも生成処理で停止することを確認した。検証用の変更はすべて元に戻した。
