# 0002 実装言語・実行環境を選定する

- 状態：手順1〜3の実施・内部確認完了
- 外部レビューと作業全体の完了状況は、対応するPRで確認する。

## 1. 目的

ClojureScriptを第一候補として、clonoの用途への適合性と、開発者が理解して保守できるかを確認し、実装言語・実行環境・ビルド方法を決定する。

ClojureScriptを使いたいという希望を選定理由に含める。多少の不便だけで候補から外さず、回避策と負担を確認する。用途を実現できない、または特殊な処理によって理解・保守が難しくなる重大な問題が見つかった場合は、代替案を検討する。

## 2. 前提と対象範囲

### 利用形態

- Markdown原稿を入力とするCLIを、Vivliostyleのビルド前に実行する。
- 出力は元原稿と別の場所へ保存する。
- 出力形式は、Vivliostyleとの接続と加工のしやすさを調査して検討する。Markdown・HTMLのどちらかに事前固定しない。
- 利用者にはNode.jsを前提とし、JDKやClojureScriptのトランスパイル環境を要求しない。
- 本体の開発環境では、JDKなどの追加ツールを許容する。費用が発生する場合は採用前に確認する。
- macOSを最優先とし、Windows・Linuxでの実行と将来のCI検証も考慮する。

### 適合性を確認する用途

| 用途 | 確認する内容 |
|---|---|
| 独自記法 | インライン、中身のないブロック、中身のあるブロックをASTで扱えるか |
| コラム | 強調・リストなどのMarkdownを内部で使えるか。制限があれば内容を確認する |
| 出力の差し替え | JavaScriptの拡張ファイルで、H1など標準要素の出力を変更できるか |
| 章参照・索引 | 複数の原稿から情報を集め、別の原稿や出力に利用できるか |
| 本の構成 | clono側で指定したファイルと順序をVivliostyle側から参照し、二重定義を避けられるか |
| 原稿と生成物 | 元原稿を保持し、出力先を分けても画像などの参照を扱えるか |

対象は今後Thunder Clawが制作する本とする。『Androidを 実機で テストしろ!!』の制作で使用した前処理スクリプト（以下「旧スクリプト」）の記法との互換性は求めない。コラムの入れ子も対象外とする。開発の背景は[プロジェクト憲章第1節](../project-charter.md#1-目的)を参照する。

利用者による新しい記法・処理の追加は将来の希望として扱う。今回は拡張方式を完成させず、将来の追加を難しくする制約がないか確認する。

### 今回扱わないもの

- 索引・章参照・コラムなどの製品機能としての実装。
- 全機能の仕様、最終的な独自記法、公開する拡張APIの確定。
- 正式なテスト環境、CI、PRレビューツールの選定・整備。
- 公開・リリース手順の整備。
- ClojureScript全般の習得。

検証に必要な依存ライブラリや実行方法は今回扱う。検証用の選択と、本体への正式採用は区別する。

## 3. 採用判断の基準

次を確認して、採用の可否を二人で判断する。

1. 代表的な用途を実現できる根拠がある。
2. ビルド済みの成果物を、利用者がNode.jsで実行できる。
3. JavaScriptの拡張を、本体や拡張のトランスパイルなしで利用できる。
4. 開発者が、処理の流れ、データの受け渡し、エラーの扱い、修正箇所を理解できる。
5. ビルド・デバッグ・依存関係の管理に伴う負担が許容できる。
6. OSごとの制約と、未検証の事項が明確になっている。

理解の確認は、そらによる説明だけでは完了としない。検証コードを一緒に読み、開発者自身の理解と保守への手応えを確認する。

## 5. 作業手順

各手順では、[開発フロー](../development-workflow.md)に従い、着手依頼、作業・検証、独立レビュー、必要な再レビュー、二人の確認、記録更新、コミットを区切る。

### 手順1：公式資料を調査し、検証候補を整理する

**作業**

ClojureScriptからNode.js向けCLIを作る方法と、関連するビルド手段を調査する。JavaScriptとの連携、非同期処理、例外、デバッグ、依存パッケージの利用方法を確認する。

併せて、Markdownの解析・変換、ディレクティブ、標準要素の加工、Vivliostyleとの接続に利用できる候補を調べる。VFMとの関係や、扱える記法の違いも確認する。

公式資料を根拠とし、参照URL・確認日・対象バージョンを残す。主要な依存候補の保守状況、ライセンス、OS対応、費用も確認する。

**成果物**

調査資料、検証に使う候補、その選定理由、実行確認が必要な疑問の一覧。

**検証・レビュー**

公式資料に記載された事実と推測を区別し、対象用途の見落としがないか確認する。候補を増やすこと自体を目的にしない。

**二人の確認**

小さな検証へ進める候補を選ぶ。重大な問題が見つかった場合は、追加調査や代替案の範囲を相談する。

### 手順2：検証方法とテスト項目を具体化する

**作業**

手順1の結果をもとに、検証に使うツール・バージョン・入力・期待結果・実行方法を決める。題材は次を基本とする。

- Node.jsで動く最小のCLI。
- 強制改ページと、Markdownを含むコラムの解析・変換。
- JavaScriptの拡張によるH1の出力差し替え。
- 複数ファイルからの章情報・索引項目の収集と、収集結果の利用。
- 本の構成の共有と、生成物をVivliostyleで処理する最小の接続確認。

通常の本文やコードブロックの誤変換、非同期処理、拡張内のエラー、元原稿の保持、相対パスも確認項目に含める。

各題材は採用判断に必要な最小のものとし、製品向けの汎用設計を持ち込まない。

**成果物**

入力例・期待結果・確認方法を含む検証計画とテスト項目。実行するOSと、資料確認にとどめるOSを明記する。

**検証・レビュー**

期待結果が判定可能か、用途を十分に代表しているか、機能実装へ範囲が広がっていないかを確認する。

**二人の確認**

テストコードを書く前に独立レビューを行い、検証計画とテスト項目に合意する。

### 手順3：小さな検証を実施する

**作業**

手順2で合意した検証を実施する。動作を検証するコードでは、期待する動作の欠如によってテストが失敗することを確認してから、検証用の処理を実装する。

ビルドや外部ツールの接続確認など、上記の順序に適さないものは、手順2で合意した方法に従う。

本体の開発環境と利用環境を区別し、ビルド済みの成果物とJavaScriptの拡張を、開発用ツールに依存せず実行できるか確認する。

**成果物**

検証コード・入力・実行結果・再現方法と、分かった制約。失敗した結果も判断の根拠として残す。

**検証・レビュー**

期待結果との一致、元原稿の保持、エラー情報、再現性を確認する。実行していないOSを動作確認済みと扱わない。

**二人の確認**

検証コードを題材に、Clojureと異なる点、JavaScriptとの連携、特殊な処理の必要性を確認する。理解が難しい場合は、説明や検証コードの分け方を見直す。

### 手順4：採用方針を決定する

**作業**

調査と検証の結果を、採用判断の基準に照らして検討する。

実装言語・実行環境・ビルド方法と、開発用ツール・利用者の前提を決める。Node.jsなどの対象バージョンと、OSごとの確認状況も整理する。

多少の不便として許容するもの、回避が必要な問題、後続で判断するものを区別する。採用判断に必要な疑問が残る場合は、追加検証を相談する。

**成果物**

ADRと、採用環境を記述する仕様文書。

**検証・レビュー**

採用理由を根拠から追えるか、未検証事項を保証していないか、理解・保守の負担を過小評価していないかを確認する。

**二人の確認**

採用する構成と許容する制約に合意する。重大な問題が残る場合は、採用を確定せず次の調査を相談する。

### 手順5：決定事項を開発文書へ反映する

**作業**

開発フロー第11〜12節などに、決定事項と関連文書への参照を反映する。READMEには、今回確定した範囲で必要な案内を追加する。

調査用コマンドと、今後正式に用意する開発・検証コマンドを区別する。未整備のテスト環境やCIが利用できるようには記載しない。

**成果物**

更新した開発文書と関連する参照。

**検証・レビュー**

ADR・仕様・調査結果との整合性、リンク、記載したコマンドの適用範囲を確認する。必要な日本語文書を`yomiyasu`で推敲する。

### 手順6：構造と文書全体を見直す

**作業**

調査コード・設定・文書を含む全体を確認し、重複、不要な複雑さ、説明不足、製品コードとの混同がないかを見直す。

整理が必要な場合は、理由・範囲・検証方法を二人で合意してから実施し、検証とレビューを行う。整理不要の場合も判断を記録する。

後続課題が生じた場合は、理由・影響とともにbacklogで管理する。既に予定されているテスト環境やCIの選定を、未対応課題として重複登録しない。

**成果物**

見直し結果、必要に応じた整理と後続課題。

**検証・レビュー**

今回の選定に必要な判断を先送りしていないか、無関係な改善を含めていないかを確認する。

### 手順7：PRレビューに出せる状態を確認する

**作業**

差分全体、実施記録、検証・レビュー結果、文書の参照、ライセンス表示を確認する。開発者が選定理由と制約を理解していることを確認し、PR説明に必要な内容を整理する。

**成果物**

PRレビューに出せる変更一式と、最終確認の記録。

**検証・レビュー**

合意した範囲を満たし、未解決事項の扱いが明確か確認する。手順1〜7の確認後、手順書を「全手順の実施・内部確認完了」とする。

## 6. 調査結果を受けて具体化する事項

検証に使うツール、記法、入力・期待結果、コマンド、OS別の実行方法は、候補の対応状況を調べるまで確定できないため、手順2で具体化する。

手順1では資料調査までを行い、未合意の環境構築や検証コードの作成には進まない。手順2の成果物を独立レビューし、二人で合意するまで手順3に着手しない。

採用する構成とバージョンは、調査・検証を経て手順4で決定する。

## 7. 外部レビューと完了条件

PRでは暫定運用中のCodeRabbitによる外部レビューを受ける。指摘への対応、再レビュー、完了確認、Git操作は開発フローに従う。

次が揃ったことを二人で確認して、作業全体を完了とする。

- 必要な文書更新、構造の見直し、検証、レビュー、記録が済んでいる。

外部レビューと作業全体の完了状況はPRで追跡し、その転記だけを目的とする追加コミットは行わない。
