# 0005 採番・参照・目次を既存機能で実現できる範囲を調べる

- 状態：手順2Aの実施・検証・独立レビュー・二人の確認は完了。手順3ではページ側の採番方式を使う。手順3・4は未着手。

## 1. 目的

見出し、図、表、コードリストの採番と参照、目次の生成について、CSS・Vivliostyle・VFMの既存機能で満たせる範囲と不足を調べる。

見出しの出力を差し替えた場合も含め、既存機能に任せる処理と、clonoで補う必要がある処理を判断できる状態にする。

要件の出発点は、[旧前処理スクリプトの要件整理](../../research/legacy-preprocessor/results/requirements.md#12-要件に結び付けた後続の確認事項)のT03～T05とする。

## 2. 前提と対象範囲

[開発フロー](../development-workflow.md)と、そこから参照する憲章・SDD・Sora Flowに従う。Markdownの処理経路は、[実装環境の仕様](../specs/implementation-environment.md)を維持する。

### 必須要件として確認するもの

| 対象 | 確認する内容 |
|---|---|
| 見出し | 章・節・項の採番、番号だけの参照、見出し本文だけの参照、番号と見出し本文を組み合わせた参照 |
| 番号なし見出し | 目次への掲載と見出し本文の参照。番号だけの参照は対象外 |
| 目次 | 掲載対象の見出し番号・見出し本文・ページ番号・リンク。番号なし見出しには番号を表示しない |
| 図・表・コードリスト | 種類ごとの採番・キャプション・番号参照。本文と付録の両方を対象にする |
| 複数原稿 | 原稿をまたぐ参照、本文と付録の区別、原稿順の変更に伴う番号と参照の更新 |
| 見出しの出力差し替え | 文字を残してHTML構造を変える場合と、章タイトルを画像で見せる場合の採番・参照・目次掲載の維持 |

参照は、参照先より前に書く場合と後に書く場合、同じ原稿内と別原稿の場合を確認する。

調査例の採番は、次を基本にする。

- 本文：`第1章`、`1.1`、`1.1.1`。
- 付録：`付録A`、`A.1`、`A.1.1`。
- 図・表・コードリスト：種類ごとに章単位で採番する。

これは調査用の基準であり、製品の表記や設定形式を確定するものではない。

### 条件付きの希望として確認するもの

- 見出し番号の表記を変更できること。
- 目次へ載せる見出しの階層を変更できること。
- 本文中の見出し・図・表・コードリスト参照に、参照先へのリンクを付けられること。

番号表記の変更が難しければ固定を許容する。目次の掲載階層は、変更が難しければH2までの固定を許容する。本文中の参照先ページ番号は求めない。

### 評価する出力

PDFを主な評価対象とし、表示内容、参照先、目次のページ番号を確認する。リンクはPDF内のリンク情報と、閲覧時の移動先を確認する。

生成HTMLや中間Markdownは、情報がどの段階で付与・保持されるかを調べる材料にする。通常のブラウザーでのHTML表示は合否条件に含めない。

### 今回扱わないもの

- clonoの製品実装。
- 独自記法、設定形式、公開する拡張APIの確定。
- 本全体の入出力・章順共有の詳細設計。
- 索引、脚注・コラムなどとの全体的な組み合わせ検証。
- 見出し以外の要素の出力差し替え。
- 前作のデザインの完全再現、旧記法との互換性。
- 全機能の実装順、配布・公開方法の確定。
- CIの案内など、今回の調査に直接関係しない文書の更新。

複数原稿の検証に必要な最小限の構成と組版設定は、調査用として用意する。

対象バージョン、調査用環境の構成、依存リスクの再評価条件への該当有無も確認する。この手順では変換・組版実験を行わない。

- 対象バージョンに適用できる根拠と、未確認の推測を区別していること。

### 手順2：標準的な出力で採番・参照・目次を検証する

**作業**

調査環境と小さな原稿を用意し、採用済みのMarkdown処理経路を通して組版する。

見出しの差し替えを加える前の構成で、次を検証する。

- 番号付き・番号なし見出し、目次、見出しへの参照。

- 原稿順を変更したときの採番と参照の更新。
- 番号表記・目次掲載階層の変更と、本文中の参照リンクの可否。

不足がある場合は、失敗した最小例と、どの段階で情報が足りなくなるかを記録する。調査用の補助処理を使った場合は、既存機能だけで成立した結果と区別する。

**成果物**

**検証・レビュー**

独立レビューでは、再現方法、期待値との対応、原稿順変更後の結果、既存機能と補助処理の区別を確認する。

**二人の確認**

### 手順2A：ページ側のカウンターで章開始値の補助を省けるか検証する

**追加する理由**

手順2の完了後、開発者から[公式チュートリアルのカウンター設定](https://vivliostyle.org/ja/tutorials/configure-counters-running-heads/)を提示された。同資料は、`@page :first`で本全体の章カウンターを初期化し、`@page :nth(1)`で各原稿の最初のページに対して加算する方法を紹介している。手順2ではこの方法を検証していなかったため、見出し差し替えの前に独立した手順として追加する。既存の手順番号と実施記録は維持する。

手順2で確認したのは、各HTMLのbodyでカウンターを初期化するCSSでは章番号が戻り、開始値の補助で成立したことである。この結果から、章開始値の補助が必須だとは判断しない。手順2の測定結果を残した上で、追加の方式と比較する。

**作業**

公式資料と採用版の実装を確認し、文書側とページ側のカウンターの関係、ページセレクターの適用範囲、`target-counter()`で取得される値を整理する。実行環境は手順2と同じものを使用し、資料の説明と採用版での実測を区別する。新しい設定・API・実行場所が既存の依存リスクの再評価条件に当たるかは、第3節の方針に従って確認する。

手順2の原稿と独立した期待値・検査コードを使い、ページ側で章を数える比較構成を追加する。本文・付録・番号なし原稿の区分を、クラスや名前付きページなどでCSSへ伝えることは許容する。一方、原稿順から算出した章の数値を、HTML・CSS・組版設定へ原稿ごとに渡す補助は使わない。本全体での固定値による初期化とは区別する。

既存のbodyによる章カウンターの初期化やH1での加算が競合しないよう、比較構成のCSSで変更箇所を明示する。図・コードのID配置、表キャプション、複合インラインH1の補助は維持し、章開始値の補助を省いた影響と混同しない。新しい補助が必要になった場合は内容と理由を記録する。

次の項目を検証する。

| 項目 | 期待する結果・確認方法 |
|---|---|
| 章の継続 | 本文2章を第1章・第2章として数え、複数ページにわたる原稿でも原稿途中では加算しない。前後の原稿への参照も一致する |
| 番号なし原稿と目次 | はじめに・目次・おわりにを本文や付録の章数に含めない。番号なし見出しは目次と本文参照を維持する |
| 本文と付録 | 本文は数値、付録はAからの英字で独立して数える。節・項・図・表・コードリストにも対応する章番号を使う |
| 原稿順の変更 | 本文2章の交換と付録2章の交換を別々に試し、章番号・参照・目次順を更新する。原稿ごとの章開始値を追加していないことも確認する |
| 参照値とリンク | 手順2の200参照・24件の番号付き説明を照合する。同一／別原稿・前方／後方の参照、同名IDへの参照、各参照位置のPDF注釈と宛先を確認する。原稿内の異なるページでも章番号が一致することを確認する |
| 目次と表記 | 基準・本文交換・付録交換・目次H3まで・区切り変更の5構成を確認する。目次の項目・順序・番号・本文・ページ番号・ファイルとIDへのリンクを独立した期待値と照合する |

ページを基準に章を数えることによる制約も記録する。今回の「1原稿1章」の成立を、複数章を含む任意の原稿や任意のページ構成へ一般化しない。成立しない場合は最小例と観測結果を残し、章開始値の補助を維持する必要があるか判断する材料にする。

**成果物**

公式資料・採用版の確認内容、比較用CSSと必要な調査コード、構成別の検証結果、章開始値の補助を省ける条件と制約。既存の結果を上書きせず、調査資料に追加する。

**検証・レビュー**

生成HTML・CSS・設定に原稿ごとの章開始値が注入されていないことを確認する。PDFの文字・行ごとのリンク注釈・宛先を自動照合し、生成した全ページの表示も目視する。基準構成では、目次と本文中の代表的な同一／別原稿へのリンクを実際にたどり、到着先を確認する。

独立レビューでは、ページ側と文書側のカウンターの区別、番号なし原稿・本文・付録の数え方、原稿順と複数ページへの対応、独立した期待値との照合、章開始値を別の形で注入していないこと、結論と実測の対応を確認する。内容確認・レビュー・記録更新・コミットは第5節と同じ区切りで行う。

**二人の確認**

ページ側の方式で章開始値の補助を省けるか、残る情報・補助・制約は何かを確認する。結果を踏まえ、手順3で使う採番方式を合意してから、手順3への着手依頼を受ける。

### 手順3：見出しの出力差し替えとの組み合わせを検証する

**作業**

手順2の検証例と、手順2Aの結果を踏まえて合意した採番方式を使い、次の2種類の見出し差し替えを調べる。

1. 文字を残し、HTML構造を変える。
2. 章タイトルを画像で見せる。

番号、見出し本文、IDなどの情報をどこに保持すれば、採番・参照・目次掲載を維持できるかを確かめる。

差し替え後も、複数原稿、本文と付録、原稿順変更の条件で確認する。図表・コードリストの採番と参照にも影響がないかを確かめる。

任意のHTML構造で動くという保証は求めず、検証した構造と維持に必要な条件を記録する。拡張APIは設計しない。

**成果物**

2種類の差し替え例、組み合わせの検証結果、保持すべき情報と構造上の制約。

**検証・レビュー**

差し替え前後の番号・参照本文・目次・リンク先を期待値と照合し、PDFも確認する。

独立レビューでは、見た目だけで成立と判断していないか、情報の重複表示や参照先のずれがないか、限られた検証例を一般化していないかを確認する。

**二人の確認**

差し替えの成立条件と制約を確認し、本ごとのデザインを扱う上で残る課題を共有する。

### 手順4：責務分担と残る課題をまとめ、全体を見直す

**作業**

T03～T05と各検証結果を照合し、次を整理する。

- 既存機能に任せられる処理と、その成立条件。
- clonoで補う必要がある処理と、その理由。
- 条件付きの希望について、実現できる範囲と制約。
- 未確認事項と、結論を出すために不足している情報。

資料の説明、実行結果、設計上の提案を区別する。実現できなかった場合も、試した範囲と限界を残す。

調査コードと既存の調査資料の構成を見直し、再現・理解のために整理が必要か判断する。修正する場合は、範囲と検証方法を二人で合意する。

今回の調査とは別に追跡すべき課題が見つかった場合はbacklogへ記録する。既存の要件や確認事項を重複登録しない。

**成果物**

責務分担の結論、制約と未確認事項、全体の見直し結果、必要な後続課題。

**検証・レビュー**

- 対象要件のすべてに、結果か未確認の理由があること。
- 結論を資料・入力・実行結果まで辿れること。
- 必須要件と条件付きの希望を混同していないこと。

- 文書の相互リンク、日本語、ライセンス表示、差分に問題がないこと。

**二人の確認**

調査結果をもとに、既存機能とclonoの責務分担を判断できるか確認する。次の実装や調査の範囲は、今回の結果を受けて別途相談する。
