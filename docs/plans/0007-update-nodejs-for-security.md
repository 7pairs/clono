# 0007 セキュリティ対応としてNode.jsを24.22.1へ更新する

- 状態：手順1の事前調査とnpmの追加調査、独立レビュー、内容確認を完了。任意改善1件を採用・反映し、補足後の独立再レビューも指摘なしで完了済み。npm 11.21.1へ移行する基本方針を確認済み。具体的な移行方法・利用条件・変更範囲の合意と、後続手順の修正は未実施。手順2～4は未着手。

## 1. 目的

Node.jsのセキュリティリリースに対応し、開発用固定版と最低対応版を24.22.1へ更新する。

既存の製品機能・開発基盤が更新後も動作することを確認し、現在の推奨環境と過去の調査環境を区別して記録する。

更新理由の出発点は、[Node.js 24.22.1のリリース情報](https://nodejs.org/en/blog/release/v24.22.1)と[セキュリティ告知](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)とする。

## 2. 対象範囲

既存の環境と検証条件は、[実装環境の仕様](../specs/implementation-environment.md)、[開発環境の仕様](../specs/development-environment.md)、[CLIの仕様](../specs/cli.md)を参照する。依存リスクと再評価条件は[backlog](../backlog.md)で確認する。

### 今回扱うもの

- 開発用Node.js固定版の24.22.1への更新。
- 最低対応範囲の`>=24.22.1 <25`への変更。
- npm 11.19.1の継続使用に関する既知の問題の確認。
- バージョン指定と、現在の環境を説明する文書の更新。
- 依存導入、ビルド、テスト、CLIの分離実行、REPLの確認。
- PR上での3OSのCIと外部レビューの確認。
- 今回の変更を踏まえた構造の見直し。

npmは確認結果に支障がなければ11.19.1を維持する。JDKとnpm依存の採用版は変更しない。

### 今回扱わないもの

- 製品機能の追加。
- npm依存の一括更新と、既存backlogの脆弱性対応全体の解消。
- 過去の調査の全面的な再実験。
- 過去の実測結果・環境情報・ハッシュの書換え。
- PRレビューツールの代替方針や、呼称・公開情報に関する運用整理。
- 公開・リリース方法の整備。
- マシン全体の既定環境の変更。

対象外の変更が必要になった場合は、理由と影響を整理し、範囲を合意してから進める。

## 3. 過去の調査記録の扱い

過去の調査資料にあるNode.js 24.22.0は、実施当時の環境として保持する。過去の版を厳密に要求する調査スクリプトも、一括置換しない。

現在の環境では版の確認で停止する入口があることと、過去の固定版を現在の推奨環境として案内しないことを、必要な再現案内へ追記する。

新しい版での再実験が必要と判断した場合は、元の記録を保持したまま、目的・対象・保存先を別途相談する。

## 4. 作業の進め方

各手順は[開発フロー](../development-workflow.md)に従い、着手依頼、作業・検証、独立レビュー、指摘対応と必要な再レビュー、二人の確認を行う。開発者がコミットし、次の手順への着手を依頼してから進む。

初回の独立レビューは、作業中の会話履歴を引き継がないサブエージェントに依頼する。再レビューは原則として同じレビュアーに依頼する。

Git操作とPR作成・マージは開発者が担当する。

手順1～4の事前確認、環境の変更、検証、構造の見直しと判断の結果は、本手順書の第8節へ実施記録として残す。参照した根拠、実行環境・コマンド・結果、必要な失敗と対応、未確認事項を記録し、既存文書と重複する説明は参照に置き換える。

## 5. 作業手順

### 手順1：更新内容と環境を確認する

**作業**

- 公式のリリース情報・セキュリティ告知から、対象版と修正内容を確認する。
- npm 11.19.1について、公式の公開情報と、必要に応じて同梱依存のアドバイザリを確認する。
- 現在のNode.js・npm・JDK、環境管理方法、バージョン指定箇所を確認する。
- 現行仕様・設定と、過去の調査記録を区別して更新対象を一覧にする。
- [backlog](../backlog.md)の再評価条件と照合する。

npmの確認では、利用中の版・利用条件に対して更新を必要とする既知の情報があるかを判断する。脆弱性が存在しないことの証明は求めず、確認日・参照先・判断根拠・残る不明点を記録する。

事前調査でnpmの同梱依存に確認が必要な情報が見つかったため、第8節の[追加調査計画](#手順1内の追加調査計画npmの継続使用と更新候補の比較)に従い、更新候補との比較を先に行う。追加調査に着手する前に、事前調査結果と追加調査方針をまとめて独立レビューし、必要な指摘対応・再レビューと二人の確認を行う。

**判断地点**

npmの更新が必要、または利用への影響を判断できない問題が見つかった場合は、対応範囲を相談する。npmの継続使用と更新対象が確認できてから手順2へ進む。

**成果物・レビュー観点**

事前確認の結果、更新対象、環境切替方法、検証項目。更新理由と対象範囲が対応し、過去の記録を変更対象へ混ぜていないことを確認する。

### 手順2：環境とバージョン指定を更新する

**作業**

- プロジェクトで使用するNode.jsを24.22.1へ切り替える。
- npm 11.19.1と、既存のJDKを使用していることを確認する。
- `.node-version`を更新する。
- `package.json`の最低対応範囲と、lockfile内の対応する情報を更新する。
- README、[実装環境](../specs/implementation-environment.md)・[開発環境](../specs/development-environment.md)の仕様など、現在の利用環境を説明する箇所を更新する。
- 必要な過去調査の再現案内へ、現在の環境との違いを追記する。

lockfileの更新では、必要なメタデータの変更と、依存の解決結果の変更を区別する。意図しない依存更新が発生した場合は、原因を確認する。

既存CIが`.node-version`を参照していることを確認し、設定変更が必要な場合だけ修正する。

**成果物・レビュー観点**

更新した環境・設定・文書。開発用固定版と最低対応版が一致し、npm・JDK・依存の採用版や過去の実測記録を意図せず変更していないことを確認する。

### 手順3：ローカルで製品と開発基盤を検証する

**作業**

Node.js 24.22.1とnpm 11.19.1を使い、次を確認する。既存の検証条件は[開発環境の仕様](../specs/development-environment.md)と[CLIの仕様](../specs/cli.md)に従う。

| 対象 | 確認内容 |
|---|---|
| 依存導入 | 既存lockfileから`npm ci`が成功する |
| 共通検証 | `npm run verify`が成功する |
| ビルド・CLI | 開発用・配布用ビルドと既存のCLI結合テストが成功する |
| 分離実行 | 既存仕様の条件に従い、配布用出力だけを別の作業場所から実行できる |
| REPL | 起動し、ClojureScriptの式を評価して終了できる |
| 環境・差分 | 実際の環境を記録し、意図しない設定・依存・生成物の変更がない |

`npm run verify`に含まれる検査は重複実行せず、分離実行とREPLなど、含まれない項目を補う。

検証用の一時変更や生成物は、管理対象のファイルへ残さない。公開する記録には、不要な個人環境情報を含めない。

**判断地点**

失敗した場合は、環境切替・既存の問題・更新による変化を切り分ける。対応範囲を超える変更が必要なら、検証結果を成功扱いにせず相談する。

**成果物・レビュー観点**

実行環境、コマンド、結果、失敗と対応の記録。確認した範囲と未確認範囲が明確であり、過去の調査結果を更新後の検証結果として扱っていないことを確認する。

### 手順4：構造を見直し、結果と残る事項を整理する

**作業**

- 今回の変更を踏まえ、既存部分を含めて構造を確認する。
- バージョン指定の重複、文書と設定の不一致、更新作業で生じた整理の必要性を検討する。
- リファクタリングの要否を判断する。
- 更新理由、採用環境、検証結果、過去調査の扱い、残る事項を整理する。
- 現在の仕様・README・本手順書の記録をそろえる。

構造の見直しは、必ずコードを変更する工程とはしない。修正が必要なら、理由と範囲を二人で合意し、検証とレビューを行う。

**成果物・レビュー観点**

構造の見直し結果と最終記録。不要な変更を増やさず、設定・実測・説明が整合していることを確認する。

外部レビューと作業全体の完了状況はPRに残す。

### 手順1：更新内容と環境の事前確認

#### Node.jsの更新理由

公式の[24.22.1リリース情報](https://nodejs.org/en/blog/release/v24.22.1)は、2026-10-21のセキュリティリリースと明記している。[セキュリティ告知](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)と照合し、次の修正を確認した。

| 対象 | 確認した修正 |
|---|---|
| DNS | NULを含む名前が途中で切り詰められる問題（CVE-2026-105482、High） |
| TLS | 非正規形・全角数字等のIPアドレスに関する証明書検証（CVE-2026-106069・106072・105483、High） |
| Brotli | 不正な圧縮入力による領域外書込み（CVE-2026-111497、High） |
| HTTP | Keep-Alive接続で送信前の応答を受理する問題（CVE-2026-105481、Medium） |
| crypto・権限モデル | スナップショットの乱数キャッシュ（CVE-2026-106074、Medium）とrealpathSyncの権限確認（CVE-2026-106073、Low） |
| 同梱依存等 | OpenSSL 3.5.9、c-ares 1.34.9、Undici 7.30.1、証明書等の更新 |

Node.jsの更新理由は確認できた。ただし、更新後の動作は未検証。Node.js内蔵Undiciの更新と、npm CLIが独自に同梱するUndiciの更新は別であり、Node.jsだけを更新しても後者の修正は保証されない。

[npm 11.19.1のリリース情報](https://github.com/npm/cli/releases/tag/v11.19.1)、[npm CLIの公開アドバイザリ](https://github.com/npm/cli/security/advisories)、実際に導入された依存のバージョンを確認した。npm CLI自身のアドバイザリ一覧だけでは、同梱依存の問題を除外できない。

#### 残る3件の発生条件と利用経路

以下のコードのパスは、npm 11.21.1の公式配布物内の`package/`を基準とする。呼出し元と入力の確認は静的なコード調査であり、攻撃入力の実行や3OSでの実測は行っていない。

GHSA-4qv8-2p9j-2685は、EventSource接続先からの応答によって、パーサーが保持する状態が増大する問題。EventSourceを利用することが発生条件になる。

**Undiciのfetchで過剰なcontent-encodingを受ける際のDoS**

GHSA-xjj6-f33q-929cは、悪意のある応答元が多数のcontent-encodingを指定し、本文送信前に接続を閉じることで、fetchの例外を処理していてもプロセスを終了させられる問題。

`node_modules/node-gyp/lib/download.js:19`は、同梱Undiciの`fetch()`を呼び出す。`node_modules/node-gyp/lib/install.js`から、Node.jsのヘッダー、チェックサム、Windows用ライブラリ等の取得に使われる。この呼出し経路は存在するため、npm全般で未使用とは判断しない。

一方、通常のレジストリ・tarball取得は、`node_modules/pacote/lib/remote.js`から`npm-registry-fetch`、`make-fetch-happen`、`minipass-fetch`へ進む。この経路と、node-gypのUndici利用は区別する。

今回の利用については、次を確認した。

- ルートのpackage.jsonとlockfileに固定された13依存について、導入済みpackage.jsonの版がlockfileと一致している。各依存には`preinstall`・`install`・`postinstall`がなく、ルートと各依存の直下に`binding.gyp`もなかった。lockfileにも`hasInstallScript`・`gypfile`の指定はない。

以上から、確認した現在の依存構成と既存コマンドでは、node-gypのダウンロードへ進む条件がないと判断する。ただし、別の依存導入、ネイティブ拡張の追加、`npm rebuild`やnode-gypの直接実行まで許容する判断ではない。今後それらを行う場合は、この問題を再評価する。既存の導入物を読み取った調査であり、クリーンな`npm ci`による再確認は手順3に残る。

**ip-addressのIPv6ゾーン文字列解析による処理時間の増大**

GHSA-rxp7-6hxx-x8q5は、`new Address6()`と`Address6.isValid()`が長さを制限する前にゾーン識別子を正規表現で処理するため、特定の長い入力で同期処理時間が増大する問題。

[公開アドバイザリ](https://github.com/advisories/GHSA-rxp7-6hxx-x8q5)では、多数の`%`の後に改行文字を含む入力により、正規表現の照合が繰り返され、入力長の二乗に比例する処理時間がかかると説明されている。

配布物でip-addressを読み込む実装は、SOCKS用の`node_modules/socks/build/client/socksclient.js`と`node_modules/socks/build/common/helpers.js`だった。前者の3箇所は、応答から固定長16バイトを取り出し、`Address6.fromByteArray()`でIPv6へ変換する。後者の`ipToBuffer()`は、`net.isIPv6()`による検証に通った文字列だけを`new Address6()`へ渡す。`@npmcli/agent`にも依存宣言はあるが、そのlib内には直接の読込み・呼出しはなかった。

[Node.js 24.22.1の実装](https://github.com/nodejs/node/blob/v24.22.1/lib/internal/net.js)では、`net.isIPv6()`が許容するゾーン識別子は、区切りの`%`に続く英数字と`-`・`.`・`:`に限られる。ゾーン識別子内で`%`や改行文字を繰り返す入力は、この検証を通らない。そのため、上記の危険な入力は`new Address6()`へ渡されないと判断する。この根拠は、入力長の上限ではなく文字種の制限にある。

SOCKSプロキシはnpmの通信経路に関係し得るが、確認した呼出し元には、任意長の未検証文字列をそのまま該当APIへ渡す経路は見つからなかった。この入力制限を、今回の利用範囲で発生条件を満たさないと判断する根拠とする。SOCKSの設定・応答を含む実行試験や、将来の別の呼出し元まで確認したものではない。

採用を合意した場合は、Node.js 24.22.1側のnpmを11.21.1へ切り替え、CIの`npm install --global npm@11.19.1`も更新する必要がある。README・現在の環境を説明する仕様・本手順書の対象範囲と手順2～3も、合意内容に合わせる。ルートのnpm依存の採用版、JDK、過去の実測環境は変更しない。lockfileはNode.jsの最低対応範囲に必要なメタデータだけを変更する予定とし、依存の解決結果に差分が出たら原因を確認する。

CIで最初にnpmを更新するコマンドは、更新前のnpmで動く。今回候補から外れた12件について、更新前の全呼出し経路の安全性までは調べていない。公式レジストリから固定版を導入する移行操作にも旧版のリスクが残るため、更新後の3件に関する判断だけで移行操作まで安全と扱わない。これも採用時の確認事項とする。

npm 11.19.1をそのまま継続する案より、11.21.1への更新を今回の範囲へ加える案を推奨する。12件が対象バージョンから外れ、残る3件には、現在の利用範囲で発生条件を満たさないと判断する根拠が得られたため。ただし、依存として残る問題が修正されたわけではなく、更新後の実行結果も未確認である。
