# 0007 セキュリティ対応としてNode.jsを24.22.1へ更新する

- 状態：未着手。草稿の独立レビューと二人の内容確認を終え、開発者の依頼でファイルへ反映した。

## 1. 目的

Node.jsのセキュリティリリースに対応し、開発用固定版と最低対応版を24.22.1へ更新する。

既存の製品機能・開発基盤が更新後も動作することを確認し、現在の推奨環境と過去の調査環境を区別して記録する。

更新理由の出発点は、[Node.js 24.22.1のリリース情報](https://nodejs.org/en/blog/release/v24.22.1)と[セキュリティ告知](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)とする。

## 2. 対象範囲

既存の環境と検証条件は、[実装環境の仕様](../specs/implementation-environment.md)、[開発環境の仕様](../specs/development-environment.md)、[CLIの仕様](../specs/cli.md)を参照する。依存リスクと再評価条件は[backlog](../backlog.md)で確認する。

### 今回扱うもの

- 開発用Node.js固定版の24.22.1への更新。
- 最低対応範囲の`>=24.22.1 <25`への変更。
- npm 11.19.1の継続使用に関する既知の問題の確認。
- バージョン指定と、現在の環境を説明する文書の更新。
- 依存導入、ビルド、テスト、CLIの分離実行、REPLの確認。
- PR上での3OSのCIと外部レビューの確認。
- 今回の変更を踏まえた構造の見直し。

npmは確認結果に支障がなければ11.19.1を維持する。JDKとnpm依存の採用版は変更しない。

### 今回扱わないもの

- 製品機能の追加。
- npm依存の一括更新と、既存backlogの脆弱性対応全体の解消。
- 過去の調査の全面的な再実験。
- 過去の実測結果・環境情報・ハッシュの書換え。
- PRレビューツールの代替方針や、呼称・公開情報に関する運用整理。
- 公開・リリース方法の整備。
- マシン全体の既定環境の変更。

対象外の変更が必要になった場合は、理由と影響を整理し、範囲を合意してから進める。

## 3. 過去の調査記録の扱い

過去の調査資料にあるNode.js 24.22.0は、実施当時の環境として保持する。過去の版を厳密に要求する調査スクリプトも、一括置換しない。

現在の環境では版の確認で停止する入口があることと、過去の固定版を現在の推奨環境として案内しないことを、必要な再現案内へ追記する。

新しい版での再実験が必要と判断した場合は、元の記録を保持したまま、目的・対象・保存先を別途相談する。

## 4. 作業の進め方

各手順は[開発フロー](../development-workflow.md)に従い、着手依頼、作業・検証、独立レビュー、指摘対応と必要な再レビュー、二人の確認を行う。開発者がコミットし、次の手順への着手を依頼してから進む。

初回の独立レビューは、作業中の会話履歴を引き継がないサブエージェントに依頼する。再レビューは原則として同じレビュアーに依頼する。

Git操作とPR作成・マージは開発者が担当する。

手順1～4の事前確認、環境の変更、検証、構造の見直しと判断の結果は、本手順書の第8節へ実施記録として残す。参照した根拠、実行環境・コマンド・結果、必要な失敗と対応、未確認事項を記録し、既存文書と重複する説明は参照に置き換える。

## 5. 作業手順

### 手順1：更新内容と環境を確認する

**作業**

- 公式のリリース情報・セキュリティ告知から、対象版と修正内容を確認する。
- npm 11.19.1について、公式の公開情報と、必要に応じて同梱依存のアドバイザリを確認する。
- 現在のNode.js・npm・JDK、環境管理方法、バージョン指定箇所を確認する。
- 現行仕様・設定と、過去の調査記録を区別して更新対象を一覧にする。
- [backlog](../backlog.md)の再評価条件と照合する。

npmの確認では、利用中の版・利用条件に対して更新を必要とする既知の情報があるかを判断する。脆弱性が存在しないことの証明は求めず、確認日・参照先・判断根拠・残る不明点を記録する。

**判断地点**

npmの更新が必要、または利用への影響を判断できない問題が見つかった場合は、対応範囲を相談する。npmの継続使用と更新対象が確認できてから手順2へ進む。

**成果物・レビュー観点**

事前確認の結果、更新対象、環境切替方法、検証項目。更新理由と対象範囲が対応し、過去の記録を変更対象へ混ぜていないことを確認する。

### 手順2：環境とバージョン指定を更新する

**作業**

- プロジェクトで使用するNode.jsを24.22.1へ切り替える。
- npm 11.19.1と、既存のJDKを使用していることを確認する。
- `.node-version`を更新する。
- `package.json`の最低対応範囲と、lockfile内の対応する情報を更新する。
- README、[実装環境](../specs/implementation-environment.md)・[開発環境](../specs/development-environment.md)の仕様など、現在の利用環境を説明する箇所を更新する。
- 必要な過去調査の再現案内へ、現在の環境との違いを追記する。

lockfileの更新では、必要なメタデータの変更と、依存の解決結果の変更を区別する。意図しない依存更新が発生した場合は、原因を確認する。

既存CIが`.node-version`を参照していることを確認し、設定変更が必要な場合だけ修正する。

**成果物・レビュー観点**

更新した環境・設定・文書。開発用固定版と最低対応版が一致し、npm・JDK・依存の採用版や過去の実測記録を意図せず変更していないことを確認する。

### 手順3：ローカルで製品と開発基盤を検証する

**作業**

Node.js 24.22.1とnpm 11.19.1を使い、次を確認する。既存の検証条件は[開発環境の仕様](../specs/development-environment.md)と[CLIの仕様](../specs/cli.md)に従う。

| 対象 | 確認内容 |
|---|---|
| 依存導入 | 既存lockfileから`npm ci`が成功する |
| 共通検証 | `npm run verify`が成功する |
| ビルド・CLI | 開発用・配布用ビルドと既存のCLI結合テストが成功する |
| 分離実行 | 既存仕様の条件に従い、配布用出力だけを別の作業場所から実行できる |
| REPL | 起動し、ClojureScriptの式を評価して終了できる |
| 環境・差分 | 実際の環境を記録し、意図しない設定・依存・生成物の変更がない |

`npm run verify`に含まれる検査は重複実行せず、分離実行とREPLなど、含まれない項目を補う。

検証用の一時変更や生成物は、管理対象のファイルへ残さない。公開する記録には、不要な個人環境情報を含めない。

**判断地点**

失敗した場合は、環境切替・既存の問題・更新による変化を切り分ける。対応範囲を超える変更が必要なら、検証結果を成功扱いにせず相談する。

**成果物・レビュー観点**

実行環境、コマンド、結果、失敗と対応の記録。確認した範囲と未確認範囲が明確であり、過去の調査結果を更新後の検証結果として扱っていないことを確認する。

### 手順4：構造を見直し、結果と残る事項を整理する

**作業**

- 今回の変更を踏まえ、既存部分を含めて構造を確認する。
- バージョン指定の重複、文書と設定の不一致、更新作業で生じた整理の必要性を検討する。
- リファクタリングの要否を判断する。
- 更新理由、採用環境、検証結果、過去調査の扱い、残る事項を整理する。
- 現在の仕様・README・本手順書の記録をそろえる。

構造の見直しは、必ずコードを変更する工程とはしない。修正が必要なら、理由と範囲を二人で合意し、検証とレビューを行う。

**成果物・レビュー観点**

構造の見直し結果と最終記録。不要な変更を増やさず、設定・実測・説明が整合していることを確認する。

## 6. PRでの確認

ローカルの全手順の実施・独立レビュー・二人の確認を終えた段階で、本手順書を「全手順の実施・内部確認完了」とする。

開発者がPRを作成した後、次を確認する。

- macOS・Windows・LinuxのCIが、Node.js 24.22.1とnpm 11.19.1で成功する。
- 外部レビューの指摘を二人で判断し、必要な修正・検証・再レビューを終える。
- 未解決のレビュー会話がなく、必要な確認と合意が済んでいる。

CIが失敗した場合は、原因に応じて必要な手順へ戻る。ローカル検証の成功だけで、3OSのCI確認を完了したとは扱わない。

外部レビューと作業全体の完了状況はPRに残す。

## 7. 完了条件

- 開発用固定版が24.22.1、最低対応範囲が`>=24.22.1 <25`になっている。
- npmの継続使用に関する確認を終え、合意した環境で検証している。
- ローカルの共通検証・分離実行・REPL確認が成功している。
- PR上の3OSのCIが成功している。
- 構造の見直し、必要な文書更新、独立レビュー、外部レビュー対応、二人の確認を終えている。
- 過去の実測記録を保持し、現在の環境との違いを説明している。

マージ操作は、作業全体の完了確認後に開発者が行う。
