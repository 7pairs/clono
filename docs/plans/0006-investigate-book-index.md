# 0006 索引を既存機能で実現できる範囲を調べる

- 状態：手順1の実施・検証・独立レビュー・再レビュー・二人の確認完了。JIS本文の確認と厳密な適合判定は、合意に基づき復旧後へ保留。手順2・3・4A・4B・5は未着手。

## 1. 目的

索引の生成、読み順の並べ替え、参照先ページ番号の表示について、Vivliostyle・VFM・関連する既存ツールで満たせる範囲と不足を調べる。

前作の執筆時点で不足していた機能が、現在も不足しているとは仮定しない。既存機能に任せられる処理を確認し、clonoで補う必要がある情報や処理を判断できる状態にする。

要件の出発点は、[旧前処理スクリプトの要件整理](../../research/legacy-preprocessor/results/requirements.md)のF23・F24、N05・N06、T08～T10と、本手順書の範囲相談で確認した希望とする。

## 2. 前提と対象範囲

[開発フロー](../development-workflow.md)と、そこから参照する憲章・SDD・Sora Flowに従う。採用済みの[Markdown処理経路](../specs/implementation-environment.md)は維持する。

### 必須要件として確認するもの

| 対象 | 確認する内容 |
|---|---|
| 索引情報 | 著者が指定した語と読み、出現箇所を索引の生成に利用できること |
| 索引生成 | 複数原稿から索引情報を集め、同じ項目の参照先をまとめた平坦な一覧を作れること |
| 並べ替え | 著者が指定した読みに基づいて項目を並べられること |
| ページ番号 | 索引項目の出現ページを列挙できること |
| レイアウト | ユーザーCSSで列数などを変更できること |
| 内容保持 | 索引情報の指定によって、本文の語やコード内の記法例を意図せず変えないこと |

本全体のページ番号は通しの連番とし、ローマ数字などへの切り替えは扱わない。

本文の表記と索引に載せる名前を分ける機能や、異なる表記を一つの索引項目へまとめる機能は、今回の要件に含めない。

### 条件付きの希望として確認するもの

- 自然な読みを受け取り、並べ替えに必要な正規化を支援できること。
- 可能ならJISの日本語文字列照合順番に準拠できること。
- 正規化すると同じ読みになる異なる語についても、照合順序を確認できること。
- 同じ索引項目が同じページに複数回出現した場合、ページ番号を一つにまとめられること。

著者が指定した読みと、並べ替えのために導出した情報は区別する。漢字から読みを自動推定する機能は求めない。

JISについては、該当する規格、版、適用範囲を調査で特定する。一般的な日本語ソートが動いたことや、少数の例が一致したことだけで、規格への準拠を結論しない。

条件付きの希望が満たせない場合も、必須要件への影響と分けて整理する。

### 評価する出力

索引の表示とページ番号はPDFを主な評価対象とする。生成HTMLや中間Markdownは、語・読み・参照先などの情報が、どの段階で保持・処理されるかを確認する材料にする。

索引から本文へのリンクを既存機能が提供する場合は、その有無と確認範囲を記録する。リンクの提供を新たな必須要件にはしない。

### 今回扱わないもの

- clonoの製品実装。
- 製品の入力記法、設定形式、拡張APIの確定。
- 階層構造のある索引と、項目間の「○○を参照」などの誘導。
- 連続するページ番号の範囲表記。
- 前作の記法やデザインの再現。
- 本全体の入出力・章順共有の詳細設計。
- 脚注・コラム・見出し差し替えなどとの全体的な組み合わせ検証。
- 製品の依存更新、配布・公開方法の決定。
- 今回の調査と直接関係しない既存文書の整備。

階層化は今回の対象外とするが、将来の採用を見送る判断ではない。将来のためだけの拡張機構も、今回設計しない。

### 手順2：索引の必須機能を検証する

**作業**

採用済みのMarkdown処理経路に、索引情報の収集と一覧生成に必要な最小限のAST処理を加える。

本文には出現箇所を識別するIDを、巻末索引には項目ごとの参照リンクを生成する。ページ番号はCSSの`target-counter()`で表示する。

調査用の入力は、次の記法を使用する。

```markdown
:index[位置情報]{reading="いちじょうほう"}
```

この記法を製品の入力仕様として確定しない。

索引項目は、調査用に次の規則で扱う。

- 語と読みが完全一致する指定を、同じ索引項目へまとめる。
- 同じ語に異なる読みが指定されていた場合は、不一致として検出する。
- 不一致の診断では、両方の原稿名・位置・読みを示す。
- 読みの比較結果が同じでも、語が異なる項目は統合しない。
- 読みは英字の語も含めて明示し、指定漏れを検出する。
- 元の語・読みと、並べ替えに使う情報を区別する。

並べ替えには手順3と共通の`Intl.Collator`を使い、この手順では基本的な読み順を確認する。

**検証用原稿と期待値**

本文A・本文B・巻末索引の3原稿で、4項目・7出現箇所を用意する。強制改ページとページの識別文字を使い、参照先とノンブルを照合できる構成にする。

| 通しページ | 出現箇所 |
|---|---|
| 1：本文A | 位置情報を2箇所、Androidを1箇所 |
| 2：本文A | テストを1箇所 |
| 3：本文B | 位置情報・テスト・APIを各1箇所 |
| 4以降 | 巻末索引 |

語・読みと、集約前の期待ページ番号は次のとおりとする。索引項目は表の順に並ぶことを確認する。

| 項目 | 読み | ページ番号 |
|---|---|---|
| Android | あんどろいど | 1 |
| 位置情報 | いちじょうほう | 1, 1, 3 |
| API | えーぴーあい | 3 |
| テスト | てすと | 2, 3 |

この手順では、同じページ番号の重複を許容する。

PDFは次の4構成を基本とする。

1. 基準の原稿順、索引2列。
2. 本文A・Bを交換、索引2列。
3. 基準の原稿順、索引3列。
4. 基準の原稿順、索引4列。

本文の順序を交換した場合は、本文Bが通し1、本文Aが通し2・3となる構成にする。位置情報は`1, 2, 2`、テストは`1, 3`となることを確認する。

別の小さな変換例で、次も確認する。

- 「橋」「箸」のような、同じ読みの異なる項目の保持。
- 同じ語への異なる読みの指定と、読みの指定漏れの検出。
- 索引指定のない語を自動登録しないこと。
- 通常の本文・強調・インラインコード・コードブロック内の記法例の保持。

**成果物**

調査用原稿・CSS・AST補助・索引生成処理、検査コード、構成別の結果、実行環境、再現方法を用意する。

**検証・独立レビューの観点**

- 4項目・7出現箇所を、収集側から独立した期待値と照合していること。
- 各参照の原稿・ID・表示ページ番号・対象ページのノンブルが一致すること。
- 原稿順と列数を変えても、項目や参照を失わないこと。
- 項目の同一性と、照合上の同順位を混同していないこと。
- 不一致を原稿上で修正できる診断情報があること。
- 元原稿を変更せず、通常の内容やコード内の記法例を保持すること。

収集結果・生成HTML・PDFを別々に検査する。PDFは画像化して表示も確認する。また、手順4Aで利用する参照先のページ対応を、PDFから取得できるか観測する。

**二人の確認**

必須機能の成立範囲、補助処理の量、診断内容、本文保持、PDFから取得できる情報を確認する。

### 手順3：読みの比較結果と情報の保持を検証する

**作業**

次の設定を最初の比較候補とする。

```javascript
new Intl.Collator('ja', {
  usage: 'sort',
  sensitivity: 'variant',
  numeric: false,
  ignorePunctuation: false,
});
```

著者が指定した元の読みを渡し、清濁・小書き・仮名種別の違いを事前に消さない。

指定した設定、`resolvedOptions()`、Node.js・ICU・CLDR・Unicodeの版を記録する。

**比較項目**

| 比較例 | 確認する内容 |
|---|---|
| あい・あお・いち | 基本の読み順 |
| は・ば・ぱ | 清濁の比較結果 |
| あー・あぁ・あゝ・ああ | 長音・小書き・繰返しの比較結果 |
| ああ・アア | 平仮名・片仮名の区別 |
| いちじょうほう・いちしようほう | 前作の手動変形前後の比較結果 |
| が（U+304C） ／ か＋結合濁点（U+304B U+3099） | Unicode上の異なる表現の扱い |
| `テスト` ／ `ﾃｽﾄ` | 全角・半角の仮名 |
| `ガ` ／ `ｶﾞ` | 濁点を含む全角・半角の仮名 |
| `API` ／ `ＡＰＩ` | 半角・全角の英字 |
| `api` ／ `API` | 英字の小文字・大文字 |
| `2` ／ `２` | 半角・全角の数字 |
| `API2` ／ `API10` | 複数桁の数字を含む語 |
| `APITest` ／ `API-Test` | ハイフンの有無 |
| `C` ／ `C++` | 記号が付いた技術用語 |

各組の元の文字列を加工せず比較し、前・後・同順位の結果を記録する。細かな順序にJIS準拠の合否は付けない。比較結果が同順位でも、異なる語を索引項目として統合しないことを確認する。

基本の読み順と、元の語・読み・項目の保持には合否を付ける。細かな順序は観測結果として保存し、JISへの適合判定には使わない。

同順位の項目は、その構成で指定した原稿順、各原稿内の出現順を維持する。これをJISの規則や製品の最終仕様とは扱わない。

**成果物**

比較用データ、比較処理と検査コード、比較結果、同順位となった組み合わせ、入力保持の検査結果、JIS本文確認後に再検討する事項を用意する。

**検証・独立レビューの観点**

- 基本の読み順が、事前に定めた期待値と一致すること。
- 元の語・読みを保持し、異なる索引項目を誤って統合しないこと。
- 観測結果と、規格に基づく期待値を区別していること。
- `Intl.Collator`の実行結果を、そのままJISの正解として扱っていないこと。
- 同順位の扱いと、実行環境への依存を記録していること。

**二人の確認**

実際に区別できたもの、同順位になったもの、用途上の不足を確認する。

別の既存実装を比較する必要がある場合は、対象と導入方法を相談する。JIS本文が未確認であることだけを理由に、別ランタイムや独自の照合エンジンを追加しない。

### 手順4A：ページ集約の方式と負担を確認する

**作業**

手順2のPDFと、既存のPDF検査用ライブラリを使い、参照先を原稿・ID・物理ページへ対応付ける。

その対応から、同じ索引項目・同じページの参照をまとめ、集約後に残すリンクの一覧を作る。この手順では、索引の再生成と再組版を接続しない。

**成果物**

参照先とページの対応、集約前後のリンク一覧、必要な処理・依存・再組版工程の整理、手順4Bの実施または見送りの判断材料を用意する。手順4Bを実施する場合は、具体化した検証計画も成果物と独立レビューの対象に含める。

**検証・独立レビューの観点**

- 同じ項目・同じページの重複だけをまとめ、別ページの参照を失わないこと。
- 別原稿の参照先を取り違えないこと。
- ページ対応が得られない参照を、黙って除外しないこと。
- 追加依存、Vivliostyle内部構造への依存、処理の複雑さを説明できること。
- 実現可能性と、実装・運用の負担を分けて評価していること。
