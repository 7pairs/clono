# 0006 索引を既存機能で実現できる範囲を調べる

- 状態：手順書の合意・独立レビュー完了。全手順未着手。

## 1. 目的

索引の生成、読み順の並べ替え、参照先ページ番号の表示について、Vivliostyle・VFM・関連する既存ツールで満たせる範囲と不足を調べる。

前作の執筆時点で不足していた機能が、現在も不足しているとは仮定しない。既存機能に任せられる処理を確認し、clonoで補う必要がある情報や処理を判断できる状態にする。

要件の出発点は、[旧前処理スクリプトの要件整理](../../research/legacy-preprocessor/results/requirements.md)のF23・F24、N05・N06、T08～T10と、本手順書の範囲相談で確認した希望とする。

## 2. 前提と対象範囲

[開発フロー](../development-workflow.md)と、そこから参照する憲章・SDD・Sora Flowに従う。採用済みの[Markdown処理経路](../specs/implementation-environment.md)は維持する。

### 必須要件として確認するもの

| 対象 | 確認する内容 |
|---|---|
| 索引情報 | 著者が指定した語と読み、出現箇所を索引の生成に利用できること |
| 索引生成 | 複数原稿から索引情報を集め、同じ項目の参照先をまとめた平坦な一覧を作れること |
| 並べ替え | 著者が指定した読みに基づいて項目を並べられること |
| ページ番号 | 索引項目の出現ページを列挙できること |
| レイアウト | ユーザーCSSで列数などを変更できること |
| 内容保持 | 索引情報の指定によって、本文の語やコード内の記法例を意図せず変えないこと |

本全体のページ番号は通しの連番とし、ローマ数字などへの切り替えは扱わない。

本文の表記と索引に載せる名前を分ける機能や、異なる表記を一つの索引項目へまとめる機能は、今回の要件に含めない。

### 条件付きの希望として確認するもの

- 自然な読みを受け取り、並べ替えに必要な正規化を支援できること。
- 可能ならJISの日本語文字列照合順番に準拠できること。
- 正規化すると同じ読みになる異なる語についても、照合順序を確認できること。
- 同じ索引項目が同じページに複数回出現した場合、ページ番号を一つにまとめられること。

著者が指定した読みと、並べ替えのために導出した情報は区別する。漢字から読みを自動推定する機能は求めない。

JISについては、該当する規格、版、適用範囲を調査で特定する。一般的な日本語ソートが動いたことや、少数の例が一致したことだけで、規格への準拠を結論しない。

条件付きの希望が満たせない場合も、必須要件への影響と分けて整理する。

### 評価する出力

索引の表示とページ番号はPDFを主な評価対象とする。生成HTMLや中間Markdownは、語・読み・参照先などの情報が、どの段階で保持・処理されるかを確認する材料にする。

索引から本文へのリンクを既存機能が提供する場合は、その有無と確認範囲を記録する。リンクの提供を新たな必須要件にはしない。

### 今回扱わないもの

- clonoの製品実装。
- 製品の入力記法、設定形式、拡張APIの確定。
- 階層構造のある索引と、項目間の「○○を参照」などの誘導。
- 連続するページ番号の範囲表記。
- 前作の記法やデザインの再現。
- 本全体の入出力・章順共有の詳細設計。
- 脚注・コラム・見出し差し替えなどとの全体的な組み合わせ検証。
- 製品の依存更新、配布・公開方法の決定。
- 今回の調査と直接関係しない既存文書の整備。

階層化は今回の対象外とするが、将来の採用を見送る判断ではない。将来のためだけの拡張機構も、今回設計しない。

## 3. 調査環境と資料

採用済みの環境を比較の基準にしつつ、調査時点のVivliostyle Core・CLI・VFMの公式資料、更新履歴、公式の実装例を確認する。

利用できる機能について、次を区別して記録する。

- 基準のバージョンで利用できる機能。
- 新しいバージョンで追加された機能。
- 提案・開発中など、公開版での利用を確認できない機能。

必要に応じて対象版のソースコードと、関連する既存ツール・ライブラリの一次資料を確認する。最新版への更新を調査の前提にはしない。

実行環境は手順1で具体化する。実際に使うNode.js、npm、CLI、Viewer内蔵Core、照合処理に影響する実行環境の情報などを記録する。動作・組版検証はまずmacOSで行う。

調査用の依存は製品の依存から分離する。[backlog](../backlog.md)の再評価条件と照合し、必要な再評価を検証計画に含める。

## 4. 成果物

調査資料は`research/book-index/`に配置する。

| 配置案 | 内容 |
|---|---|
| `README.md` | 目的、環境、再現方法、関連する手順書へのリンク |
| `sources.md` | 公式資料・規格・ソースコードなどの参照先と確認内容 |

| `scripts/` | 変換・組版・照合・検査に必要な調査コード |

再現に必要な入力・コードと、判断の根拠になる結果を選んでGit管理する。大量の再生成可能な出力やキャッシュは管理対象から外す。

第三者由来の資料・コード・テストデータを取り込む場合は、[ライセンス方針](../specs/licensing.md)に従う。

## 5. 作業の進め方

各手順では、作業・文書化・検証の後に開発者へ内容を共有する。開発者の確認と依頼を受けて独立レビューへ進む。

初回レビューは会話履歴を引き継がない新しいサブエージェントが担当する。指摘の扱いを二人で検討し、修正した場合は必要な検証と再レビューを行う。

レビュー結果を二人で確認した後、実施記録を更新する。Git操作とPRへの書き込みは開発者が担当する。次の手順は、コミットと着手依頼を受けて開始する。

日本語文書は`yomiyasu`で見直す。

## 6. 作業手順

### 手順1：既存機能と照合規格を調べ、検証計画を具体化する

**作業**

Vivliostyle側の索引機能の現状を最初に調べる。語・読み・出現箇所の指定、索引の生成、ページ番号、同一ページの集約を、どこまで提供しているか整理する。

不足する部分について、関連する既存ツールやライブラリを調べる。自前実装を最初の候補にしない。

JISの該当規格・版・適用範囲を特定し、読みの正規化と照合順序の関係を整理する。確認できる規定と、資料不足などで確認できない部分を区別する。

候補ごとに必要な環境、利用条件、入力情報、処理の段階を整理する。手順2～4の具体的な構成、検証データ、独立した期待値、確認方法を作成する。この手順では変換・組版実験を行わない。

**検証・独立レビューの観点**

- 既存機能の対応状況に、対象版と根拠があること。
- 必須要件と条件付きの希望に検証項目が対応していること。
- 実装結果をそのまま期待値に使っていないこと。
- JIS準拠を判断できる範囲と、できない範囲が明確であること。
- 依存リスクとライセンス上の利用条件を確認していること。

**二人の確認**

検証候補、環境、期待値、依存リスクへの対応、手順2～4の具体的な内容を合意する。

具体的なAPI、構成数、語の一覧、ページ配置は調査結果に依存するため、この地点で確定する。後続の検証には、具体化した手順への合意と着手依頼を受けてから進む。

### 手順2：索引の必須機能を検証する

**作業**

手順1で選んだ既存機能を優先して、複数原稿から平坦な索引を生成する。

同じ語の複数箇所への出現、別原稿への出現、異なる読みを持つ項目を含め、収集漏れ、誤った統合、ページ番号の誤りを確認する。

ユーザーCSSで列数を変更する例を確認する。通常の本文とコード内の記法例が保持されていることも検査する。

不足がある場合は、必要な情報や最小限の補助処理を調査用に用意し、既存機能だけの結果と区別する。

**検証・独立レビューの観点**

- 索引項目と出現箇所が期待値に対応していること。
- 表示されたページ番号が、PDFの対象ページのノンブルと一致すること。
- 並べ替え、項目の統合、本文保持をそれぞれ確認していること。
- 必要な補助を含めた成立条件が明記されていること。

PDFは対象箇所を画像化して目視し、可能な部分は独立した期待値による自動検査と併用する。

**二人の確認**

必須機能の成立範囲、不足、clonoが受け渡す必要のある情報を確認する。

### 手順3：読みの正規化とJISの照合順序を検証する

**作業**

手順1で合意した語と期待順序を使い、候補となる既存の照合処理を比較する。

自然な読み、正規化で同じ読みになる語、規格で区別や順序を確認する必要がある文字の組み合わせを扱う。著者の入力と並べ替え用の情報を分けて確認する。

完全に同じ比較結果となる項目がある場合は、残る順序の扱いを記録する。調査用の並びを製品の仕様として確定しない。

**検証・独立レビューの観点**

- 期待順序の根拠を規格の該当箇所などへ辿れること。
- 正規化と照合を混同していないこと。
- 元の語・読みを失ったり、異なる索引項目を誤って統合したりしないこと。
- 候補の適合範囲と相違点を説明できること。
- 一部の実例の一致を、全面的な規格準拠へ拡大していないこと。

**二人の確認**

JIS準拠をどこまで確認できたか、候補ごとの制約、追加確認が必要な事項を確認する。既存候補で不足する場合も、この工程で独自の照合エンジンの開発へ進まない。

### 手順4：同一ページの参照集約を検証する

**作業**

同じ項目が同じページに複数回出現する例と、異なるページにも出現する例を使い、ページ番号の集約を確認する。

内容や配置を変えて改ページ位置を動かし、組版後のページに応じて結果が更新されるか確認する。

組版前に得られる情報と、組版後に得られる情報を区別する。既存機能で足りない場合は、補助に必要な処理段階と情報、再組版の要否を整理する。

**検証・独立レビューの観点**

- 同じページの重複だけを除き、別ページの参照を失わないこと。
- 改ページ位置を変えた場合も、実際のページと一致すること。
- 集約後のページ番号の並びを確認していること。
- 索引自身のページ数などが変わる構成では、その影響を考慮していること。
- 未達の場合も、索引の必須機能への影響と分けていること。

**二人の確認**

実現可能性、制約、必要な補助処理を確認する。実装規模や影響が調査の範囲を超える場合は、根拠と未確認事項を残して追加作業を相談する。

### 手順5：責務分担と全体の構造を見直す

**作業**

T08～T10と各検証結果を照合し、次をまとめる。

- 既存機能へ任せられる処理。
- clonoが扱う候補となる情報・補助処理。
- ユーザーCSSへ任せる範囲。
- 必須要件と条件付きの希望それぞれの到達点。
- バージョン更新が必要な候補と、その影響。
- 未確認事項、追加確認に必要なもの、確認する時点。

調査コード・資料と、既存部分との関係を含めて構造を見直す。リファクタリングは必要性を判断し、実施する場合は範囲と検証方法を合意してから着手する。

既存のT08～T10で追跡できる事項は重複登録しない。独立した後続課題が見つかった場合はbacklogへ記録する。

**検証・独立レビューの観点**

- 要件ごとに結果と根拠を辿れること。
- 資料上の対応、実測、未確認の推測を区別していること。
- 条件付きの希望を、必須要件や実現済みの機能へ変更していないこと。
- 調査用の記法やコードを、製品仕様として扱っていないこと。
- 再現方法、文書間のリンク、ライセンス表示に不足がないこと。

**二人の確認**

調査の結論、残る制約、構造の見直し結果、後続で判断する事項を確認する。

## 7. 完了条件

- 索引に関する既存機能の対応状況を、対象版と根拠付きで整理している。
- 必須機能について、成立範囲と不足を実測で確認している。
- JIS準拠と同一ページ集約について、可否または判断できない理由と追加確認事項を整理している。
- 既存機能とclonoの責務分担を判断できる。
- 再現資料、検証結果、必要なレビューと再レビュー、二人の確認、構造の見直し、作業記録が揃っている。

すべての希望を実現することは、本調査の完了条件にしない。全手順の確認後は「全手順の実施・内部確認完了」と記録し、外部レビューと作業全体の完了状況は対応するPRで確認する。
