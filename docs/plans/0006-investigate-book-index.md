# 0006 索引を既存機能で実現できる範囲を調べる

- 状態：手順1～3・4Aの実施・検証・独立レビュー・必要な修正と再レビュー・二人の確認完了。4Bの具体化した計画も内容確認・レビュー済み。4B・5は未着手。標準APIの照合に関する制約と製品での扱いは手順5へ引き継ぐ。規格全体の精査と候補実装の適合判定は未実施。

## 1. 目的

索引の生成、読み順の並べ替え、参照先ページ番号の表示について、Vivliostyle・VFM・関連する既存ツールで満たせる範囲と不足を調べる。

前作の執筆時点で不足していた機能が、現在も不足しているとは仮定しない。既存機能に任せられる処理を確認し、clonoで補う必要がある情報や処理を判断できる状態にする。

要件の出発点は、[旧前処理スクリプトの要件整理](../../research/legacy-preprocessor/results/requirements.md)のF23・F24、N05・N06、T08～T10と、本手順書の範囲相談で確認した希望とする。

## 2. 前提と対象範囲

[開発フロー](../development-workflow.md)と、そこから参照する憲章・SDD・Sora Flowに従う。採用済みの[Markdown処理経路](../specs/implementation-environment.md)は維持する。

### 必須要件として確認するもの

| 対象 | 確認する内容 |
|---|---|
| 索引情報 | 著者が指定した語と読み、出現箇所を索引の生成に利用できること |
| 索引生成 | 複数原稿から索引情報を集め、同じ項目の参照先をまとめた平坦な一覧を作れること |
| 並べ替え | 著者が指定した読みに基づいて項目を並べられること |
| ページ番号 | 索引項目の出現ページを列挙できること |
| レイアウト | ユーザーCSSで列数などを変更できること |
| 内容保持 | 索引情報の指定によって、本文の語やコード内の記法例を意図せず変えないこと |

本全体のページ番号は通しの連番とし、ローマ数字などへの切り替えは扱わない。

本文の表記と索引に載せる名前を分ける機能や、異なる表記を一つの索引項目へまとめる機能は、今回の要件に含めない。

### 条件付きの希望として確認するもの

- 自然な読みを受け取り、並べ替えに必要な正規化を支援できること。
- 可能ならJISの日本語文字列照合順番に準拠できること。
- 正規化すると同じ読みになる異なる語についても、照合順序を確認できること。
- 同じ索引項目が同じページに複数回出現した場合、ページ番号を一つにまとめられること。

著者が指定した読みと、並べ替えのために導出した情報は区別する。漢字から読みを自動推定する機能は求めない。

JISについては、該当する規格、版、適用範囲を調査で特定する。一般的な日本語ソートが動いたことや、少数の例が一致したことだけで、規格への準拠を結論しない。

条件付きの希望が満たせない場合も、必須要件への影響と分けて整理する。

### 評価する出力

索引の表示とページ番号はPDFを主な評価対象とする。生成HTMLや中間Markdownは、語・読み・参照先などの情報が、どの段階で保持・処理されるかを確認する材料にする。

索引から本文へのリンクを既存機能が提供する場合は、その有無と確認範囲を記録する。リンクの提供を新たな必須要件にはしない。

### 今回扱わないもの

- clonoの製品実装。
- 製品の入力記法、設定形式、拡張APIの確定。
- 階層構造のある索引と、項目間の「○○を参照」などの誘導。
- 連続するページ番号の範囲表記。
- 前作の記法やデザインの再現。
- 本全体の入出力・章順共有の詳細設計。
- 脚注・コラム・見出し差し替えなどとの全体的な組み合わせ検証。
- 製品の依存更新、配布・公開方法の決定。
- 今回の調査と直接関係しない既存文書の整備。

階層化は今回の対象外とするが、将来の採用を見送る判断ではない。将来のためだけの拡張機構も、今回設計しない。

## 3. 調査環境と資料

採用済みの環境を比較の基準にしつつ、調査時点のVivliostyle Core・CLI・VFMの公式資料、更新履歴、公式の実装例を確認する。

利用できる機能について、次を区別して記録する。

- 基準のバージョンで利用できる機能。
- 新しいバージョンで追加された機能。
- 提案・開発中など、公開版での利用を確認できない機能。

必要に応じて対象版のソースコードと、関連する既存ツール・ライブラリの一次資料を確認する。最新版への更新を調査の前提にはしない。

実行環境は手順1で具体化する。実際に使うNode.js、npm、CLI、Viewer内蔵Core、照合処理に影響する実行環境の情報などを記録する。動作・組版検証はまずmacOSで行う。

調査用の依存は製品の依存から分離する。[backlog](../backlog.md)の再評価条件と照合し、必要な再評価を検証計画に含める。

### 検証環境

既存の基準版を使用し、調査用の依存と生成物は製品から分離する。

| 対象 | 使用する版・構成 |
|---|---|
| Node.js | 24.22.0 |
| Markdown処理 | 採用済みのremark系で加工してMarkdownへ再出力し、VFM 2.7.2でHTML化する |
| 組版 | Vivliostyle CLI 11.3.3。実際に使用するViewer内蔵Coreの版も確認する |
| PDF検査 | pypdf 6.21.1、pdfplumber 0.11.9、Pillow 13.0.0 |
| 実行環境 | まずmacOS。OS・npm・ブラウザー・ICUなどの実版を記録する |

PDF検査用の依存は、前回の調査環境を変更せず、今回の調査用環境へ用意する。画像化に使うPopplerの実版も記録する。

依存の導入前に、既存の依存リスクの確認結果と、今回の呼び出し経路・設定・実行場所を照合する。新しい問題や利用条件の変更が見つかった場合は、対応を合意してから該当する検証へ進む。

### JISに基づく照合順序の検証方針

JISCのメンテナンスにより保留していたJIS X 4061:1996の本文閲覧が可能になり、適用範囲、照合方法、仮名の照合規則、適合性と処理系定義事項に関する主要な条項を確認した。規格全体の精査と、候補実装の適合判定は未実施である。

今回の調査では、ソート順序を明示し、その順序を決める根拠を規格に求める。全面適合を長期的な目標とし、まず規格から根拠を確認できた範囲について、候補実装との一致・不一致を検証する。

一致を確認した範囲、異なる動作、未確認事項を分けて記録する。少数の比較例の一致を、規格全体への適合の根拠にはしない。「部分適合」などの表現を用いる場合も、規格の適合性の規定と照合し、確認した範囲を具体的に示す。

漢字クラス、文字の符号化、全半角や結合文字の扱いなど、処理系に関わる事項を追加調査する。規格に基づく期待値と検証範囲を具体化し、独立レビューと二人の確認を経て、着手依頼を受けてから比較実験を行う。

## 6. 作業手順

### 手順1：既存機能と照合規格を調べ、検証計画を具体化する

**作業**

Vivliostyle側の索引機能の現状を最初に調べる。語・読み・出現箇所の指定、索引の生成、ページ番号、同一ページの集約を、どこまで提供しているか整理する。

不足する部分について、関連する既存ツールやライブラリを調べる。自前実装を最初の候補にしない。

JISの該当規格・版・適用範囲を特定し、読みの正規化と照合順序の関係を整理する。確認できる規定と、資料不足などで確認できない部分を区別する。

候補ごとに必要な環境、利用条件、入力情報、処理の段階を整理する。手順2・3・4A・4Bの具体的な構成、検証データ、独立した期待値、確認方法を作成する。この手順では変換・組版実験を行わない。

**検証・独立レビューの観点**

- 既存機能の対応状況に、対象版と根拠があること。
- 必須要件と条件付きの希望に検証項目が対応していること。
- 実装結果をそのまま期待値に使っていないこと。
- JIS準拠を判断できる範囲と、できない範囲が明確であること。
- 依存リスクとライセンス上の利用条件を確認していること。

**二人の確認**

検証候補、環境、期待値、依存リスクへの対応、手順2・3・4A・4Bの具体的な内容を合意する。

具体的なAPI、構成数、語の一覧、ページ配置は、この地点で確定する。ただし、次の事項は、それぞれの追加調査の結果を受けて具体化する。

- 手順3の比較方法、追加入力、期待値、判定範囲は、同手順の比較実験前に具体化し、独立レビューと二人の確認を行う。
- 手順4Bの複数ページ検証に使う追加入力・構成・期待値は、手順4Aで具体化する。

JISに基づく検証は第3節の方針に従う。後続の検証には、具体化した手順への合意と着手依頼を受けてから進む。

### 手順2：索引の必須機能を検証する

**作業**

採用済みのMarkdown処理経路に、索引情報の収集と一覧生成に必要な最小限のAST処理を加える。

本文には出現箇所を識別するIDを、巻末索引には項目ごとの参照リンクを生成する。ページ番号はCSSの`target-counter()`で表示する。

調査用の入力は、次の記法を使用する。

```markdown
:index[位置情報]{reading="いちじょうほう"}
```

この記法を製品の入力仕様として確定しない。

索引項目は、調査用に次の規則で扱う。

- 語と読みが完全一致する指定を、同じ索引項目へまとめる。
- 同じ語に異なる読みが指定されていた場合は、不一致として検出する。
- 不一致の診断では、両方の原稿名・位置・読みを示す。
- 読みの比較結果が同じでも、語が異なる項目は統合しない。
- 読みは英字の語も含めて明示し、指定漏れを検出する。
- 元の語・読みと、並べ替えに使う情報を区別する。

並べ替えには手順3と共通の`Intl.Collator`を使い、この手順では基本的な読み順を確認する。

**検証用原稿と期待値**

本文A・本文B・巻末索引の3原稿で、4項目・7出現箇所を用意する。強制改ページとページの識別文字を使い、参照先とノンブルを照合できる構成にする。

| 通しページ | 出現箇所 |
|---|---|
| 1：本文A | 位置情報を2箇所、Androidを1箇所 |
| 2：本文A | テストを1箇所 |
| 3：本文B | 位置情報・テスト・APIを各1箇所 |
| 4以降 | 巻末索引 |

語・読みと、集約前の期待ページ番号は次のとおりとする。索引項目は表の順に並ぶことを確認する。

| 項目 | 読み | ページ番号 |
|---|---|---|
| Android | あんどろいど | 1 |
| 位置情報 | いちじょうほう | 1, 1, 3 |
| API | えーぴーあい | 3 |
| テスト | てすと | 2, 3 |

この手順では、同じページ番号の重複を許容する。

PDFは次の4構成を基本とする。

1. 基準の原稿順、索引2列。
2. 本文A・Bを交換、索引2列。
3. 基準の原稿順、索引3列。
4. 基準の原稿順、索引4列。

本文の順序を交換した場合は、本文Bが通し1、本文Aが通し2・3となる構成にする。位置情報は`1, 2, 2`、テストは`1, 3`となることを確認する。

別の小さな変換例で、次も確認する。

- 「橋」「箸」のような、同じ読みの異なる項目の保持。
- 同じ語への異なる読みの指定と、読みの指定漏れの検出。
- 索引指定のない語を自動登録しないこと。
- 通常の本文・強調・インラインコード・コードブロック内の記法例の保持。

**成果物**

調査用原稿・CSS・AST補助・索引生成処理、検査コード、構成別の結果、実行環境、再現方法を用意する。

**検証・独立レビューの観点**

- 4項目・7出現箇所を、収集側から独立した期待値と照合していること。
- 各参照の原稿・ID・表示ページ番号・対象ページのノンブルが一致すること。
- 原稿順と列数を変えても、項目や参照を失わないこと。
- 項目の同一性と、照合上の同順位を混同していないこと。
- 不一致を原稿上で修正できる診断情報があること。
- 元原稿を変更せず、通常の内容やコード内の記法例を保持すること。

収集結果・生成HTML・PDFを別々に検査する。PDFは画像化して表示も確認する。また、手順4Aで利用する参照先のページ対応を、PDFから取得できるか観測する。

**二人の確認**

必須機能の成立範囲、補助処理の量、診断内容、本文保持、PDFから取得できる情報を確認する。

### 手順3：読み・表記の比較結果と情報の保持を検証する

**目的**

著者が指定した読みと本文の表記について、候補となるソート順序、その規格上の根拠、実行環境への依存と制約を説明できる状態にする。

読み単体の比較と、読みが同順位の場合に表記を比較する方法を、別々に検証する。調査結果をもとに候補を評価し、製品の最終仕様はこの手順だけで確定しない。

**追加調査**

比較実験に先立ち、次を整理する。

- JISの「読み・表記照合」と、適用する照合規則の組み合わせ。
- 選択できる漢字クラスと、それぞれの順序・適用条件。
- 文字の符号化、追加文字、全半角、結合文字などに関する規定と、今回の入力との対応。
- 採用済みのNode.js・ICUと`Intl.Collator`で指定・確認できる範囲、確認できない部分。
- 候補ごとの順序、規格との差異、実装・運用の負担。
- 適合性の規定と、文書へ明示する必要がある処理系定義事項。

別の既存実装を比較する必要がある場合は、対象と導入方法を相談する。追加調査だけを理由に、依存・別ランタイム・独自の照合エンジンを追加しない。

**比較実験前の確認**

追加調査の結果から、次を具体化する。

| 対象 | 確定する内容 |
|---|---|
| 比較方法 | 読み単体と、読み→表記の比較手順 |
| 漢字・文字の扱い | 選択する漢字クラス、対象文字と未対応の範囲 |
| 比較データ | 既存の14組、表記比較の追加入力、同順位を確認する入力 |
| 期待値 | 前・後・同順位の期待結果、根拠となる条項、処理系上の前提 |
| 判定範囲 | 規格との一致・不一致を判定する比較と、観測にとどめる比較 |
| 情報保持 | 元の語・読み・出現箇所と、比較用に導出する情報の区別 |

具体化した検証計画とテスト項目を独立レビューにかけ、指摘の採否、必要な修正・再レビュー、二人の確認を行う。計画と判断理由を記録し、開発者のコミットと着手依頼を受けて比較実験へ進む。

具体化・レビュー済みの内容は[手順3の比較実験計画](../../research/book-index/results/step3-plan.md)を参照する。入力・期待値・判定範囲、情報保持の検査、実施順序と環境確認は同計画に従う。

未確定の比較方法や期待値を、実行結果に合わせて決めない。

**比較処理**

次の設定を最初の比較候補とする。

```javascript
new Intl.Collator('ja', {
  usage: 'sort',
  sensitivity: 'variant',
  numeric: false,
  ignorePunctuation: false,
});
```

著者が指定した元の読みを渡し、清濁・小書き・仮名種別の違いを事前に消さない。追加調査後に合意した比較実験計画では、表記にも同じ設定の比較器を使う。規格との差異を確認するための候補であり、製品の最終仕様にはしない。

指定した設定、`resolvedOptions()`、Node.js・ICU・CLDR・Unicodeのバージョンを記録する。

**比較項目**

| 比較例 | 確認する内容 |
|---|---|
| あい・あお・いち | 基本の読み順 |
| は・ば・ぱ | 清濁の比較結果 |
| あー・あぁ・あゝ・ああ | 長音・小書き・繰返しの比較結果 |
| ああ・アア | 平仮名・片仮名の区別 |
| いちじょうほう・いちしようほう | 前作の手動変形前後の比較結果 |
| が（U+304C） ／ か＋結合濁点（U+304B U+3099） | Unicode上の異なる表現の扱い |
| `テスト` ／ `ﾃｽﾄ` | 全角・半角の仮名 |
| `ガ` ／ `ｶﾞ` | 濁点を含む全角・半角の仮名 |
| `API` ／ `ＡＰＩ` | 半角・全角の英字 |
| `api` ／ `API` | 英字の小文字・大文字 |
| `2` ／ `２` | 半角・全角の数字 |
| `API2` ／ `API10` | 複数桁の数字を含む語 |
| `APITest` ／ `API-Test` | ハイフンの有無 |
| `C` ／ `C++` | 記号が付いた技術用語 |

各組の元の文字列を加工せず比較し、前・後・同順位の結果を記録する。

規格から期待値と適用条件を確定できた比較には、一致・不一致を付ける。根拠や適用条件が未確定の比較は観測結果として保存し、判断できない理由を記録する。期待値は条項と選択した処理系上の条件から定め、`Intl.Collator`や別の実装の出力を、そのまま正解にはしない。

読み→表記の比較では、読みが同順位の異なる項目を用意し、表記比較へ進むことを確認する。読み単体の比較結果と、表記まで比較した結果を区別して保存する。

比較結果が同順位でも、異なる索引項目を統合しない。

読み単体で並べる構成では、読みが同順位の項目の出現順を維持する。読み→表記で並べる構成では、両方を比較しても同順位の項目の出現順を維持する。出現順は、その構成で指定した原稿順と各原稿内の出現順による。

この出現順による扱いは調査用の暫定方針であり、JISの規則とは扱わない。

手順2の読み単体・出現順による処理は比較の基準として残し、表記比較を加えた場合の違いを確認する。
