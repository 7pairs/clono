# 憲章策定からの引き継ぎ事項

この文書は、[プロジェクト憲章](project-charter.md)の策定時に合意した運用の詳細と、今後の議論に必要な判断材料を引き継ぐための暫定文書である。

合意済みの事項と未決事項を区別する。恒久的な仕様や判断理由の置き場にはせず、正式な文書へ反映した項目には参照先を記載し、引き継ぎ完了を示す。未決事項は、実装への着手指示や採用決定を意味しない。

## 1. 合意済み・引き継ぎ状況

以下は合意済みであり、開発フローへ反映した。各項目に反映先と引き継ぎ状況を記載する。

### 1.1 作業計画

- 引き継ぎ: 完了
- 反映先: [開発フロー 2. 作業計画と着手](development-workflow.md#2-作業計画と着手)

着手前の作業計画は、プロジェクトオーナーへの説明と、作業範囲の約束を兼ねる。厳密なSDDツールのtasks形式は前提としない。

以下を短くまとめる。

- 目的と完了条件
- 対象と対象外
- 変更予定
- 検証方法
- プロジェクトオーナーがレビューし、コミットを判断しやすい区切り

作業計画は、実装中の発見に合わせて更新する。完了時には結果と未解決事項を残す。範囲変更の更新は、憲章に定める再合意を経て行う。

### 1.2 記録先の役割分担

- 引き継ぎ: 完了
- 反映先: [開発フロー 3. 記録の配置と更新](development-workflow.md#3-記録の配置と更新)、[4. 調査と検証](development-workflow.md#4-調査と検証)

| 記録先 | 内容 |
|---|---|
| 仕様 | 期待する振る舞い、記法、境界条件、具体例 |
| ADR | 設計上の選択と、その理由 |
| 作業計画 | 作業の目的、範囲、完了条件、検証方法、進捗、未解決事項 |
| 調査結果 | 調査した問い、条件・バージョン、方法、観測結果、解釈、未確定事項 |

小さな設計判断もADRの対象とするが、同じ論点に関する判断は一つにまとめてよい。

長く必要な結論は、作業計画だけに残さず、仕様やADRへ反映する。各記録は必要に応じて相互に参照し、重複を避ける。

調査結果は事実と根拠を残し、その結果から導いた採用判断は仕様やADRへ記録する。

### 1.3 開発フロー決定前のレビュー

- 引き継ぎ: 完了（開発フローの適用から正式運用へ移行）
- 反映先: [開発フロー 6. レビューとマージ条件](development-workflow.md#6-レビューとマージ条件)

開発フローが決まるまでは、PRの第三のレビュアーとして暫定的にCodeRabbitを採用する。憲章の初版も対象とする。

これは移行期間の合意済みの運用であり、正式なレビュアー選定を確定するものではない。

### 1.4 文書の状態と日付

- 引き継ぎ: 完了
- 反映先: [開発フロー 3.4 ヘッダ](development-workflow.md#34-ヘッダ)

憲章のヘッダには、状態、作成日、最終更新日を記載する。

- 状態はレビューの進捗ではなく、文書としての位置づけを表す。PRでは、マージ後の状態を記載する。憲章の初版は「有効」とする。
- レビュー中かどうかはPR側で管理し、文書には「初版レビュー待ち」などの進捗を記載しない。マージ後に状態だけを更新する追加PRを不要にするためである。
- 作成日と最終更新日は、マージ日ではなく、文書を作成・更新した日とする。マージのタイミングに合わせた日付の修正は行わない。
- 文書の更新時には、最終更新日の確認も行う。

規範文書には上記を適用する。開発フローの議論で、作業計画は更新時点の実際の状態を記載することに合意した。状態は「計画済み・進行中・完了・中止」を基本とし、完了時の更新は当該PRに含める。

各記録に作成日・最終更新日を記載し、状態などの項目は用途に応じて設ける。

## 2. 決定事項と今後の判断材料

### 2.1 開発フローとレビュー運用

- 運用の引き継ぎ: 完了
- 反映先: [開発フロー](development-workflow.md)
- 選定理由の正式なADRへの反映: 未完了

以下の運用を開発フローで定めた。

- 作業計画と各記録の配置、書式、更新手順
- 調査用フィクスチャと実行手順の管理方法
- 第三のレビュアーの正式な選定と運用
- レビュー指摘の扱いと具体的なマージ条件
- コミットメッセージなどの開発規約

第三のレビュアーにはCodeRabbitを採用することで合意した。理由は、無料で利用できる実績、実装担当とは異なる視点を入れたいこと、以前の開発で「そら」の見落としを拾った実績である。

無料運用を前提とし、有料化は別途相談する。制限時は回復を待つことを基本とし、1時間程度の待機を許容する。利用できない場合は、相談してレビュー用の別セッションの「そら」で代替する。会社契約のClaude Codeは私用の候補に含めない。

PRは変更・検証・自己確認が揃ってから作成する。自動レビューを基本とし、自動実行されなければ手動で依頼する。作成後の軽微な修正による自動レビューも許容する。

指摘は修正、理由を示した不採用、追跡先とマージしてよい理由を残した別作業化のいずれかで対応し、確認後に会話をResolveする。レビューの実施を確認し、未解決の会話を残さない。動作や設計に影響する修正は再レビューを依頼する。

同じモデルによるレビューでは似た見落としをする可能性がある。代替レビュアーも、実装時の説明だけに頼らず、仕様と変更内容を確認する。

コミットメッセージは、スコープを付けない軽量なConventional Commitsとし、型と日本語の件名を使用する。

CodeRabbitの公開情報と今回の実行表示には差があり、適用プラン名は未確定である。プロジェクトオーナーの管理画面では、2025-10-29にEssentialsの契約を終了した表示があり、クレジットカードを登録せず試用を終了した。その後も無料で自動レビューが行われた実績がある。今回の[憲章PRのコメント](https://github.com/7pairs/clono/pull/2#issuecomment-5948271284)には`Plan: Advanced`の表示があった。OSS扱いである可能性はあるが、断定しない。

確認した公開情報は、[公式プラン説明](https://docs.coderabbit.ai/management/plans)、[レート制限](https://docs.coderabbit.ai/management/rate-limits)、[モデル運用の説明](https://www.coderabbit.ai/blog/why-users-shouldnt-choose-their-own-llm-models-choice-is-not-always-good)である。複数モデルを利用する説明はあるが、各レビューで実装担当と異なるモデルが使われる保証は確認できていない。

運用は適用プラン名に依存させず、今後、選定理由と確認時点の不確実さをADRへ反映する。

### 2.2 技術選定

実装言語とビルドツールは未決定である。ただし、ClojureScriptの採用には強い選好がある。

- ClojureScriptは、clonoという名前の由来の一つである。
- 名前のもう一つの由来は、プロジェクトオーナーが応援するVTuberの千羽黒乃さんである。
- プロジェクトオーナーは、推しVTuberに由来するツール名を大切にしたいと考えている。
- この動機を選定条件として扱い、単なる好みとして無視しない。
- 絶対条件ではないが、重大な技術的障害がある場合は、具体的な検証結果をもとに再検討する。

技術的な適合性と名前への愛着を区別し、どちらも正式な技術選定のADRに記録する。

以前のビルドツールはshadow-cljsだったが、今回の採用は未決定である。実行方法、入力と出力の扱い、利用環境など、選定に必要な最低限の要件を確認してから判断する。

### 2.3 独自記法と変換方式

以前はGeneric Directives Proposalに基づくカスタムディレクティブを採用していた。多少冗長でも迷わず書けることが、採用理由の一つだった。

今回は、その記法、ASTの採用、変換パイプラインの具体的な方式を自動的に引き継がない。記法の一貫性と明確さを重視する原則に基づき、必要な調査と設計を行う。

Markdown内にHTMLを含める方式と、HTMLファイルを出力する方式は、どちらも現時点では排除しない。具体的な方式は機能ごとの設計で決める。

一枚絵の扉ページは、HTML出力の可能性を説明するための例として挙げられたものであり、採用が決まった機能ではない。

### 2.4 ライセンス

採用するライセンスは未決定である。以前はApache License 2.0だったが、継続するかは改めて議論する。

プロジェクトオーナーには、ライセンスを明記していなかったコードの無断流用でトラブルになった経験がある。このため、コードを追加する前にライセンスを決定し、`LICENSE`で明示する。

### 2.5 成功条件の具体化

次回作で必要な代表的な原稿と検証項目を、今後の仕様で定める。文法の使い方や使い分けを、推測や試行錯誤に頼らず確認できることも検証対象とする。

外部にも同様の要望があるという見込みは、現時点では仮説である。外部需要の確認は、Thunder Clawのために開発する前提条件にはしない。

## 3. 合意済みの進行順序

1. プロジェクト憲章
2. 開発フロー
3. ライセンスの議論・決定と`LICENSE`の配置
4. 開発環境の土台を作るための最初の作業計画
5. 言語・ビルドツールの選定
6. プロジェクトファイルと`.gitignore`の作成
7. `README.md`の作成

詳細な機能要件より先に、開発フローを整える。技術選定に必要な最低限の要件は、選定前に確認する。

## 4. 初版作成の理由と影響

以前の開発では、プロジェクトオーナーがコードの概要を把握しきれなくなったことと、コードの拡大に伴う品質の低下が大きな問題となった。また、小さな判断の取りこぼしと、合意したフェイズを越える実装によってコミット単位に困ることがあった。

今回の憲章は、軽量なSDDを維持しつつ、明示的な着手、範囲変更時の再合意、完了時の停止、小さな判断の記録、再実行可能な調査の保存、第三者レビューを原則として明文化する。

以前の憲章は比較材料として使用し、技術選定を自動的に継承せず、今回の対話で合意した内容を初版に反映した。作業計画や記録の運用詳細は、憲章を読みやすく保つため、この文書から開発フローへ引き継ぐ。

## 5. 開発フロー清書時の引き継ぎ

2026-10-03に、合意した開発フローを文書化した。作業計画、記録、調査・検証、セッション間の継承、レビュー、品質点検、Sora Flow、バージョン方針を反映した。

憲章のレビュー条項には、レビュー済みの内容を新しいファイル変更なしで昇格させる場合に、累積差分の再レビューを省略できる条件を追加した。第三者レビューそのものの省略を認める変更ではない。

コード理解と品質の低下を防ぐため、製品コードやテストを変更する通常PRを3件マージするごとに品質点検を行う。改善不要でも根拠を記録し、点検に伴うリファクタリングPRは次の3件に数えない。

READMEとAGENTSの作成時には、開発フローへの導線を追加する。具体的なCI構成、バージョン情報の保存先・更新方法、配布物の手順は、技術選定後に定める。

未完了の引き継ぎは、CodeRabbitの選定理由のADR、技術選定、独自記法・変換方式、ライセンス、成功条件の具体化、未作成文書の導線と技術選定後の手順である。このため、この文書はまだ削除しない。
