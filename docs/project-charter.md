# clono プロジェクト憲章

## 1. 目的

clonoは、Vivliostyle Flavored Markdown（VFM）による書籍制作に、出版物で必要となる表現力と文書横断機能を加えるためのツールである。

clonoはVivliostyleを置き換えるものではない。Vivliostyleを利用した制作工程を補完し、制作者がツールの不足を個別のビルドスクリプトで埋めることなく、品質の高い技術同人誌の制作に集中できる状態を目指す。

## 2. 対象利用者

clonoは個人を中心に開発する。最初の利用者は、開発者本人と、開発者が所属する同人サークル「[Thunder Claw](https://thunder-claw.com/)」の共同制作者とする。共同制作者がclonoの開発へ参加することは前提としないが、利用者として要望やフィードバックを提供する場合がある。

そのうえで、Vivliostyleを使って紙面や内容の品質にこだわる同人誌制作者へ広く利用可能なツールを目指す。利用者がソフトウェア実装やclonoの内部技術に詳しいことを前提としない。利用者の職種や制作上の役割を限定せず、異なる専門性を持つ制作者が利用できることを重視する。

## 3. 成功の定義

clonoをサークルの次回作の制作工程へ組み込み、必要な機能を実制作で利用できることを最初の成功とする。

成功した状態では、開発の関心をclonoそのものから原稿の執筆と紙面の制作へ移すことができる。機能数や技術的な完成度だけではなく、一冊の本を完成させるための実用品になったかどうかで成功を判断する。

## 4. 中核原則

### 4.1 実制作を優先する

機能は、想像上の汎用性ではなく、実際の書籍制作で必要となるかどうかを基準に選ぶ。

次回作で必要な機能から開発し、利用例のない拡張や将来のためだけの抽象化を急がない。

### 4.2 変換の正しさを前提条件とする

参照番号、見出し、脚注、索引などを誤って変換すると、出版物の内容そのものを損なう。変換の正しさは他の価値と交換可能な優先事項ではなく、満たすべき前提条件とする。

変換結果は可能な限り人間が検査できる形で出力し、誤りを黙って通過させない。問題がある場合は、利用者が原因と位置を理解できるように報告する。

### 4.3 VFMとの親和性と執筆体験を両立する

既存のVFM原稿、記法、制作知識を活かせることを重視する。clonoを利用するために、原稿全体を専用形式へ移行させない。

VFMとの互換性は執筆体験の一部として扱う。ただし、出版に必要な能力をVFMだけでは十分に表現できない場合は、原稿の可読性を保ちながら拡張する。

### 4.4 独自記法を必要最小限にする

VFM、HTML、CSSおよびVivliostyleの機能で十分に実現できる場合は、それらを優先する。

独自記法は、書籍全体の意味解決が必要な機能、または執筆体験を明確に改善する機能に限って導入する。特定の構文を前提とせず、現在利用できる標準や既存機能を調査してから仕様を決定する。

### 4.5 導入と利用の負担を抑える

内部実装でNode.jsや開発者向けの技術を利用しても、その知識を利用者へ不必要に要求しない。

導入手順、基本操作、エラーメッセージおよびドキュメントを通じて、clonoの実装技術に詳しくない制作者でも利用方法を理解できるようにする。

### 4.6 技術的な難所を早期に検証する

ページ脚注、文書横断参照、索引など、実現方法がVivliostyleの能力や組版結果に左右される機能は、小さな技術検証を仕様確定や大規模な実装より先に行う。

難しい機能を一度に完成させようとせず、検証可能な単位へ分割する。技術的不確実性を長期間抱えたまま、周辺機能だけを増やさない。

### 4.7 継続可能な開発を選ぶ

clonoは個人を中心に開発するオープンソースプロジェクトである。高額なサービスや、継続的に大きな保守負担を生む構成への依存を避ける。

忙しい時期を挟んでも再開できるように、仕様、重要な設計判断および実行可能な例をリポジトリへ残す。開発手続きは、正確さを支える範囲にとどめ、開発そのものを妨げる儀式にしない。

## 5. 対象範囲

clonoは、次の制作能力を対象とする。ここで定めるのは実現する能力であり、特定の独自記法や実装方式ではない。

### 5.1 局所的な表現

- 空行
- 強制改行
- 強制改ページ
- 段落の右寄せ
- 定義リスト
- コラムなどの囲み枠

これらはVivliostyleおよびVFMの現行機能を調査し、独自記法が必要なものだけをclonoで拡張する。

### 5.2 ファイル単位の意味解決

- ページ下部へ出力する脚注

### 5.3 書籍単位の意味解決

- 見出し、画像、表およびコードリストへの参照用IDの付与
- 表へのキャプションの付与
- 章、節および小節の番号参照
- 章、節および小節の番号と見出しタイトルの参照
- 画像、表およびコードリストの番号参照
- 索引へ掲載するキーワードの指定と索引の生成

ファイル単位および書籍単位の意味解決は、最初の実制作に必要な中核機能とする。

## 6. 対象外

次のものはclonoの対象外とする。

- GUIエディター
- 紙面デザインを作成する機能
- VivliostyleまたはVFMの代替
- 一般用途のMarkdown変換器
- コミュニティの拡大や多数のコントリビューター獲得それ自体

対象外の機能がなければ利用できない状況が判明した場合は、暗黙にスコープを拡大せず、本憲章を見直す。

## 7. 判断の優先順位

複数の選択肢が中核原則を満たす場合は、次の順序で判断する。

1. 次回作の実制作で役立つこと
2. 執筆体験とVFMとの親和性
3. 導入と運用のしやすさ
4. 機能の多さ

変換の正しさと結果の検査可能性は、この優先順位を適用する前の必須条件とする。

## 8. 互換性と動作環境

現時点では、互換性を維持すべき公開済みバージョンや既存利用者はいない。そのため、初期仕様では後方互換性を要件とせず、目的に適した仕様と設計を自由に選択する。正式リリース後の互換性方針は、必要となる段階で別途定める。

基本機能は特定のOSへ依存させず、可能な限りクロスプラットフォームで動作させる。実制作に不可欠な機能をクロスプラットフォームで実現することが困難な場合は、最初の利用環境であるmacOSを優先できる。ただし、OS依存部分を必要以上にコアへ持ち込まない。

Vivliostyleが利用するNode.jsエコシステムへの依存は許容する。

## 9. Spec as Code

仕様と実装の関係を保つため、少なくとも次の情報をリポジトリで管理する。

- 本プロジェクト憲章
- 機能仕様
- 重要な設計判断とその理由
- 利用例を兼ねた自動テスト

仕様は実装とともに更新する。一方で、監査、形式的な承認フロー、要件の完全な追跡管理を目的としたプロセスは導入しない。

## 10. 言語方針

機械や不特定多数の利用者へ向けた情報には英語を使い、設計判断や正確な理解が必要な情報には日本語を使う。

- ソースコード、識別子、コードコメント、ログメッセージおよびCLIメッセージは、原則として英語で記述する。
- `README.md`は、リポジトリの入口として英語で記述する。
- 機能仕様、設計文書および開発文書は、日本語で記述する。
- Issue、Pull Requestおよびそこでの議論は、日本語で記述する。
- 日本語組版を検証するテストデータには、目的に応じて日本語を使用する。

公開範囲や利用者層の変化により必要性が生じた場合は、文書やメッセージの多言語化を改めて検討する。

## 11. 憲章の変更

本憲章は、プロジェクトの目的と判断基準を示すための生きた文書である。

実制作から得られた知見によって変更できるが、個別機能の都合だけで暗黙に原則を曲げない。目的、対象範囲、中核原則または成功の定義を変更するときは、理由を議論し、本憲章へ明示的に反映する。
