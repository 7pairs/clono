# Sora Flow

## 1. 目的

Sora Flowは、Git Flowをもとに、リリース準備の変更とレビューをdevelop側で完了させてから、変更禁止のreleaseブランチをmainへ昇格させるGitワークフローである。

本文書における「そら」は、開発者がCodex上で設定しているAIの人格を指す。

リリース固有の変更も通常のPRと同じ経路でレビュー・検証し、mainへの昇格時にはレビュー済みの累積差分を重複レビューしない。一方、昇格する内容の確認とCIは省略しない。

特定のプロジェクトやレビュー製品には依存しない。対象ファイル、コマンド、ブランチやタグの命名規則、レビュー製品の設定、リリースの公開方法は、各プロジェクトの開発フローで定める。

## 2. ブランチとマージの原則

### 2.1 develop

developは、通常の変更とリリース準備の変更を取り込むブランチである。

変更は作業ブランチで行い、develop向けPRで必要なレビューと検証を完了してから取り込む。

### 2.2 release

releaseは、レビュー・検証済みのdevelopの内容を固定し、mainへ昇格させるための一時的なブランチである。

release上では、実装、バージョン情報、文書などのファイルを変更しない。修正が必要になった場合は、develop側で対応して作り直す。

releaseは、作業場所や永続的なリリース記録として利用しない。

### 2.3 main

mainは、リリースする内容を受け入れるブランチである。

mainへ入れる変更は、すべてdevelop側で必要なレビューと検証を終え、releaseからの昇格を通じて取り込む。developを通さないmainの変更は禁止する。

緊急修正も同じ経路を用いる。この経路では対応できない状況が生じた場合は、開発者とそらが相談し、運用を再検討する。独断で例外経路を使わない。

### 2.4 マージ方式

develop向けPRと、releaseからmainへの昇格PRは、merge commitを使ってマージする。

個々の作業コミットと、PR単位の取り込みを履歴から追える状態を保つ。

## 3. リリース準備

リリース準備は、releaseではなく、developから作成したリリース準備ブランチで行う。

1. リリースするバージョンと内容を決める。
2. developからリリース準備ブランチを作成する。
3. バージョン情報や文書など、リリースに必要な変更を行う。
4. develop向けPRを作成し、必要なレビューと検証を完了する。
5. リリース準備PRをdevelopへマージする。

releaseを作成する前に、次の条件を満たしていることを確認する。

- リリース対象とバージョンが決まっている。
- バージョン情報や必要な文書の更新がdevelopに取り込まれている。
- リリースに含めるすべての変更が、必要なレビューと検証を終えている。
- 対象となるdevelopのコミットで、リリース前に必要な検証が通っている。

個々のPRの検証だけでなく、取り込み後の組み合わせも確認する。具体的な検証内容は、各プロジェクトの開発フローで定める。

## 4. developの凍結

リリース準備PRをマージした後、リリースが完了するか、第7.4節に従って中止後の通常開発再開に合意するまで、developへの通常の変更のマージを一時的に停止する。

凍結中も作業ブランチでの開発は行えるが、通常の変更はdevelopへ取り込まない。

リリースに必要な修正が見つかった場合は、通常のレビュー・検証を経た修正に限り、developへ取り込める。その間も、通常の変更のマージは停止したままとする。

## 5. releaseの作成とmainへの昇格

準備完了を確認したdevelopのコミットから、releaseブランチを作成する。続いて、releaseからmainへの昇格PRを作成する。

昇格前に、次を確認する。

- releaseが、準備完了を確認したdevelopのコミットを指している。
- release作成後に、変更が追加されていない。
- mainとの差分がレビュー・検証済みのリリース内容と一致し、予定外の変更や取り込み漏れがない。
- 昇格PRのCIが通っており、マージ競合がない。

これらを確認した上で、merge commitを使ってmainへマージする。

昇格PRでは、レビュー済みの累積差分のコードレビューを繰り返さない。レビュー済みの内容を昇格させる条件が成立していることを確認し、CIは実行する。

重複レビューを抑止する具体的な方法は、各プロジェクトの開発フローで定める。

## 6. マージ後の確認とリリースの完了

mainへマージした後、次の順序で確認と公開を行う。

1. mainのマージ結果が、固定したreleaseの内容と一致していることを確認する。
2. mainのマージコミットに対するCIの成功を確認する。
3. そのマージコミットにバージョンタグを付ける。
4. タグを共有先へ反映する。
5. 共有先のタグが、期待するmainのマージコミットを指していることを確認する。
6. 各プロジェクトで定めたリリース公開を行う。
7. 一時的なreleaseブランチを削除する。

次の条件が揃ったところをリリース完了とする。

- 検証済みのmainのマージコミットを、公開したタグが指している。
- プロジェクトで定めたリリース公開が完了している。
- 一時的なreleaseブランチを削除している。

完了後、developへの通常の変更のマージを再開する。

リリース済みの内容を示す記録は、mainのマージコミットに付けたバージョンタグとする。releaseブランチは保存目的で残さない。

リリース準備と修正はdevelopに存在するため、リリース後にreleaseからdevelopへ戻すためだけのマージは行わない。

## 7. 問題が見つかった場合

### 7.1 mainへのマージ前

release作成後に修正が必要になった場合は、昇格を止める。

developから修正用ブランチを作成し、develop向けPRで通常のレビューと検証を行う。修正を取り込んだdevelopで準備完了の条件を確認し、releaseを作り直して昇格前の確認をやり直す。

releaseへ直接修正を追加しない。

### 7.2 mainへのマージ後、公開前

mainのCI失敗や内容の問題が見つかった場合は、タグ付けとリリース公開を止める。

原因を確認し、コードの修正が必要なら、develop向けPRでレビューと検証を行う。修正済みのdevelopからreleaseを作成し、同じ昇格手順を踏む。

環境の一時的な問題など、コードの修正が不要な場合は、原因に応じてCIの再実行などで確認する。対応は開発者とそらが相談して決める。

問題への対応中も、mainへの直接修正は行わない。

### 7.3 公開処理の失敗

タグの反映やリリース公開に失敗した場合は、リリース完了と扱わず、原因と対応を開発者とそらが確認する。

内容を変更せずに公開処理を再試行する場合は、タグと成果物の公開状態を確認し、公開済みのタグが期待するmainのマージコミットを指していることを確認する。公開処理を再実行しても公開済みの状態を損なわない場合、または未完了の手順だけを再実行できる場合に限り、同じタグ・同じ内容で再試行できる。タグがまだ公開されていない場合は、第6節のタグの反映と確認から再開する。

内容の修正が必要な場合は、公開済みのバージョンを差し替えず、旧リリースを第7.4節に従って中止として整理する。修正はdevelop向けPRでレビュー・検証し、新しいバージョンの準備と昇格・公開を行う。

公開済みのタグや成果物の扱いは、第8節に従う。

### 7.4 リリースの中止

リリースを中止する場合は、開発者とそらが次を確認し、必要な対応を行う。

- 公開済みのタグと成果物の有無、およびそれらを残すか取り下げるか。扱いは第8節に従う。
- 不要になったreleaseブランチと未マージの昇格PRの整理。
- mainへ取り込み済みの変更を残すか、戻す必要があるか。

mainの変更を戻す必要がある場合も、develop側で変更を作成し、通常のレビュー・検証とreleaseからの昇格を経て反映する。mainへの直接修正は行わない。

中止の理由と対応結果を記録し、リリース成功による完了とは区別する。

必要な対応を終えて二人が通常開発の再開に合意したら、developの凍結を解除する。新しいバージョンへのリリース対応を引き続き行う場合は、凍結を維持する。

## 8. 公開済みのタグと成果物

公開済みのバージョンタグは、原則として削除・移動・付け直しを行わない。同じバージョンが同じ内容を示す状態を保つ。

公開後に不具合が見つかった場合は、通常の経路で修正し、新しいバージョンとしてリリースする。

タグを誤ったコミットへ付けて公開した場合も、黙って付け替えず、開発者とそらが対応を検討する。

ただし、公開を継続すべきでない情報や成果物が含まれる場合は、開発者とそらが対応を判断し、公開物やタグの削除を許容する。削除したバージョンは再利用せず、修正版は新しいバージョンで公開する。

タグの削除だけで、対象の公開物をすべて取り下げられるとは限らない。配布先を含む具体的な取り下げ対象と対応は、各プロジェクトの開発フローで扱う。

## 9. 各プロジェクトで定める内容

Sora Flowを採用するプロジェクトでは、開発フローに少なくとも次を定める。

- ブランチとタグの命名規則。
- リリース準備で更新するファイル。
- 各段階で必要な検証とCI。
- レビューに使用するツールと、昇格PRの重複レビューを抑止する方法。
- タグの共有先とリリースの公開方法。
- 公開物を取り下げる際の対象と対応。

作業への着手、レビュー結果の扱い、各段階での合意は、採用する開発方法に従う。Sora Flowの手順が定義されていることだけを理由に、必要な合意や着手依頼を省略しない。
