# 手順4Bの追加調査・試作結果

2026-10-24（日本時間）。開発者のコミット報告と着手依頼を受け、[修正後の計画第6節](step4b-plan.md#6-再開前の追加調査試作)を実施した。保存済みB01の2PDFを読み取り、本文文脈と文字位置から全7出現箇所を識別できた。初回と最終のページ対応は、固定期待値とも互いにも一致した。その後、独立レビューは指摘なしとなり、二人で方式・負担を確認してF07に採用する方針で合意した。第7節を参照する。6構成の再実行と4B全体の完了を示す結果ではない。

## 1. 対象と保持した記録

停止時のB01の初回・最終PDF、独立した期待値、既存のPython環境、固定版のViewer・CLIに同梱されたソースマップを使った。組版・PDF編集、新しい依存の導入、Vivliostyle Core（組版エンジン）の改変、不可視リンクの追加は行っていない。

今回の記録はresults/step4b-followup/へ分離した。停止時の2PDF、step4b-results.json、step4b-stop.json、既存のstep4bログ、生成HTML・CSSのハッシュを実行前後で照合し、変更がないことを確認した。コード・期待値・環境と対象PDFのハッシュは[実行記録](step4b-followup/body-context.json)に保存した。

## 2. 参照先欠落の原因について確認した範囲

保存済みPDFでは、索引出現箇所の名前付き参照先が初回7個・最終6個で、除いたidx-a-2だけが最終PDFにない。元の本文HTMLにはそのIDが残る。この観測は[停止時の記録](step4b.md)と同じである。

固定版のソースマップから、次の経路を読解した。ソースマップと対象ソースのハッシュ、ソース名・行番号は実行記録のsourceEvidenceに残した。第三者のソース全文はリポジトリに追加していない。

| 対象 | 読解した内容 |
|---|---|
| Viewer/Core 2.45.1、vgen.tsのID処理 | 元のIDを保持し、変換したIDを持つアンカーを生成・登録する。読解したID処理には、索引からリンクされている場合だけ生成する条件は見つからなかった |
| epub.tsのtransformFragment | 原稿URLとフラグメントをviv-id-形式へ変換する |
| CLI 11.3.3、output/pdf.ts | ブラウザーのpage.pdfでPDFを生成し、そのPDFを後処理へ渡す |
| output/pdf-postprocess.ts | PDFを読み込み、メタデータ・目次・ページ枠等を処理して保存する。読解した処理では、索引で使わなくなったIDを明示的に削除する処理は見つからなかった |

静的なコード読解だけでは、実際の組版後DOMにidx-a-2用のアンカーがあったことや、ブラウザー出力直後のPDFに参照先があったことは確認できない。今回の保存物から、Viewer・ブラウザー出力・後処理のどの段階で参照先が欠落したかは特定していない。リンクの削除とPDF参照先の欠落が対応する観測を、Chromiumの仕様や不具合と断定しない。

合意した範囲でページ確認の候補を試せたため、原因特定のための新規組版や調査範囲の拡張は行わなかった。[参照資料の追記](../sources.md#7-手順4bの追加調査2026-10-24)も参照する。

## 3. 本文文脈による識別方法

[試作](../scripts/body_context.py)は、pdfplumberで各ページの文字と座標を読み、既存の文字配置処理で行へまとめる。計画で固定した索引ページを除き、本文の全ページを探索する。原稿・IDごとの期待ページを使って探索範囲を狭めない。

独立したexpected.jsonのdestinationContextsと各行の文字を照合し、各文脈の開始位置を特定する。抽出された「⼀」等を元の文脈の「一」と照合するため、文字ごとにNFKCを適用し、正規化後の文字から元の文字座標へ対応付ける。原稿やHTMLを書き換える正規化ではない。

候補が0件なら欠落、2件以上なら曖昧さとして、原稿・ID付きで診断する。候補が一つなら、ページと開始位置を記録して固定期待値と照合する。異なるIDの文脈が文字範囲を共有することは許容する。

本文Bの3文脈は、同じページ・同じ行で、開始位置がそれぞれ異なった。「位置情報とテストとAPIを確認する。」「テストとAPIを確認する。」「APIを確認する。」の重なりを曖昧さとして扱わずに識別できた。

初回PDFは全7箇所、最終PDFはリンクを残した6箇所について、本文文脈の開始位置と名前付き参照先の位置も照合した。今回の文字枠とアンカーの差を考慮し、横位置の差を1pt以内、文字上端とアンカーの上からの座標の差を-1～5ptとした。この許容差は固定入力に対するもので、他の書体・組版条件での妥当性を確認したものではない。

全14文脈が一意に見つかり、全7箇所のページは固定期待値・初回と最終の間で一致した。省いたidx-a-2も、最終PDFの名前付き参照先を使わずに確認できた。これは保存済みB01についての結果で、旧実行記録の失敗状態や、最終PDFの従来の一括検査を成功へ変更していない。

検査を先に作り、未実装による8件の失敗を確認してから試作した。[検査コード](../scripts/body-context.test.py)の全8件が成功した。

| 検査 | 確認したこと |
|---|---|
| 初回PDF | 全7文脈の固定ページと名前付き参照先の開始位置が一致する |
| 最終PDF | 省いた箇所を含む全7文脈の固定ページ・初回との一致を確認できる |
| 重なる3文脈 | 同じ行の異なる開始位置として識別できる |
| 省いた文脈の削除 | a.html#idx-a-2の欠落を検出する |
| 別の本文ページへの複製 | 期待ページ以外も探索し、同じIDに候補が2件ある曖昧さを検出する |
| 別の本文ページへの移動 | 移動先のページ2で識別し、期待ページ1との不一致を検出する |
| 索引ページへの移動 | 索引の文脈を本文の代わりにせず、本文での欠落を検出する |
| 同一ページの参照先座標の交換 | 本文Bの2箇所の名前付き参照先を交換し、開始位置の不一致を検出する |

文字の削除・複製・移動は、実PDFから抽出した文字と位置情報をメモリー上で変更し、行への配置・候補探索・判定を通した。完成したページ対応表だけの改変ではない。座標交換も実PDFの名前付き参照先をメモリー上で変更し、照合処理を通した。保存済みPDFは変更していない。既存4Aの8検査も成功した。

記録は[失敗確認](step4b-followup/test-red.txt)、[試作後の成功確認](step4b-followup/test-green.txt)、[実行ログ](step4b-followup/probe.txt)、[4Aの回帰検査](step4b-followup/regression-4a.txt)から辿れる。pdfplumberのFontBBox警告は今回も出たが、文字抽出と上記の検査は成功した。

## 5. 負担と適用範囲

既存のPython 3.12.14、pypdf 6.21.1、pdfplumber 0.11.9を使った。今回の単発計測では、各PDFの読取り・文脈識別・固定ページと参照先位置の検査は初回46.319ms、最終45.041ms、ソース根拠やハッシュの確認を含む全体は120.545msだった。起動時間は含まず、一般の本の処理時間や繰り返し計測の評価ではない。

試作はbody_context.pyが83行、実行・計測はprobe-body-context.pyが116行、検査はbody-context.test.pyが103行。合計302行のうち、識別・照合の候補は83行で、残りは調査記録・検査用である。調査用の固定期待値と座標の許容差を使っており、製品の実装量ではない。

今回の短い文脈は行内に収まる。複数行をまたぐ文脈や、一つのIDに同じ文脈の開始候補が複数ある原稿を解決する仕組みは作っていない。原稿・IDは固定入力の固有文脈から対応付けており、PDF内部のIDそのものを復元しているわけではない。
