# 手順3：比較実験前の追加調査

2026-10-23（日本時間）。[手順書0006](../../../docs/plans/0006-investigate-book-index.md)の手順3の追加調査。[調査の入口](../README.md)・[参照資料](../sources.md)。本資料は、比較方法と検証範囲を相談するためにまとめた調査結果であり、以下の提案は追加調査時点の内容として残す。初回独立レビューの任意改善1件を採用し、漢字クラスを見分ける入力案を補強した。同じうみの再レビューで指摘の解消を確認し、新しい必須修正・任意改善はなかった。JIS本文の独立閲覧による確認は行っていない。その後に合意・レビューした内容は[比較実験計画](step3-plan.md)を参照する。比較実験、照合処理の実装変更、依存の追加は未実施。

## 1. 調査の結論

既存の`Intl.Collator`を低負担の比較候補として残せる。ただし、日本語ロケールと`sensitivity: 'variant'`の指定だけでは、JIS X 4061:1996の基本照合規則と同じ結果を保証できない。特に、平仮名・片仮名を区別するICUの第4レベルを、対象版のJavaScript APIから指定できないことを公開コードで確認した。

漢字については、JISの基本漢字クラスの区点順と、拡張漢字クラスの符号位置順が異なる。CLDRの`unihan`も後者の代用にはならない。まず基本漢字クラスを規格上の比較基準とし、`Intl.Collator`の結果と照合する案を推奨する。これは、候補実装が基本漢字クラスに対応すると認定する判断ではない。

全半角と結合表現は分けて扱う。正準等価な文字列を同順位とすることはECMA-402から期待できるが、全半角の互換文字は同じ根拠では扱えない。JISの文字への対応を確定できない組は観測対象に残し、入力へ一律にNFKC等を適用する案は採らない。

## 2. 根拠と確認方法

JISCの本文ビューアーで、既読の条項に加えて4.4.7の数字、4.4.9のラテンアルファベット、4.4.11の漢字クラスを確認した。第1～6節の関連規定を、候補実装の公式資料・公開コードと照合した。規格全文の精査や全面的な適合判定ではない。規格本文・ビューアー画像は保存・収録していない。

候補実装は、手順2で記録したNode.js 24.22.0、ICU 78.3、CLDR 48、Unicode 17.0を基準とする。Node.js v24.22.0タグのV8コードとICUの版表示を確認した。CLDR release-48の日本語照合データは規則の説明に用いるが、そのXMLと実行時の組込みデータとの同一性を検証したものではない。再現時には[手順2の環境記録](environment.json)に加え、実際の版と`resolvedOptions()`を記録する。

参照資料J09～J14とJ05・J06から根拠を辿れる。公開コードの静的読解、規格から導いた期待値案、実測結果を区別し、本資料には実測結果を含めない。

## 3. JISで選択する事項

### 照合方法と規則

JIS第3節・5.2では、照合方法と照合規則を区別する。読み・表記照合は読み列を先に比較し、同順位の場合に表記列を比較する。読みの自動生成を規定する方法ではない。

第4節の基本照合規則は、まず基底文字列を比較し、同じ場合に照合属性を比較する。簡易照合規則は基底文字列だけを比較する。清濁・小書き・仮名種別の区別を調べる今回は、基本照合規則を比較基準とする案が合う。読み単体の比較と読み→表記の比較は、これまでの合意どおり別に記録する。

JISの属性比較とICUの比較レベルは、名称や段数が似ていても同じ手順とは限らない。仮名種別が同順位になる場合だけ追加で比較する処理を付けても、文字列全体でJISと一致する証明にはならない。

### 漢字クラス

4.4.11の各クラスは照合属性を持たず、次の範囲と順序を使う。

| クラス | 範囲と順序 | 今回の扱いの案 |
|---|---|---|
| 最小漢字クラス | 規定の5文字のみ | 一般的な漢字表記の比較には不足するため、主な比較基準にしない |
| 基本漢字クラス | 規定の5文字に続き、JIS X 0208の漢字6355字を区点順に並べる | 最初の比較基準にする |
| 拡張漢字クラス | 規定の5文字に続き、当時のJIS X 0221のCJK統合漢字から重複する仝を除いた20901字を符号位置順に並べる | 今回の主な比較基準への採用は保留する |

規定の5文字は、〃・仝・々・〆・〇の順。処理系が漢字クラスを定義する場合も、この5文字を含める必要がある。「拡張」は現在のUnicodeの漢字すべてを意味しない。現代の追加漢字を含めるなら、文字の追加と順序を別途定義する必要がある。

CLDRの日本語`standard`には明示的な漢字列があるが、その存在だけでJISのクラス全体との一致とはしない。`unihan`は部首・残画数による順序を用いるため、JIS拡張漢字クラスの符号位置順とは異なる（J06・J13）。漢字の読みは引き続き著者が指定する。

### 符号化・追加文字・全半角・結合表現

第1節・6.2では符号化方法を処理系定義とし、追加する文字クラス・文字とその順序等も宣言対象にしている。4.3.1には照合で無視する文字の規定がある。現代のUnicode文字すべてに規格の順序が自動で与えられる、と解釈しない。

| 対象 | 確認したこと | 検証計画への提案 |
|---|---|---|
| 文字列表現 | JavaScript APIの文字列と、JISが定義する文字クラスの対応を決める必要がある | 実験用データにコードポイントを併記する。符号化・文字対応の宣言案は実験前に明示する |
| 合成済みのがと、か＋結合濁点 | ECMA-402は正準等価な文字列を同順位とする。JISから同じ結論を導くには文字対応の前提が必要 | ECMA-402に基づく期待値と、JISに基づく判定を分ける。濁点を単に捨てない |
| 全半角の仮名・英数字 | CLDRには半角仮名との対応を記す規則がある。互換等価と正準等価は別の関係 | 既存の全半角4組はまず観測対象にする。JIS上の対応を確定するまで一致・不一致を付けない |
| 規定外の漢字・記号等 | 対応範囲や追加定義を明示する必要がある | APIが値を返すことと、JISに根拠があることを分けて記録する |

比較用の変換を追加する場合も、項目の同一性は語・読みの完全一致のままとする。同じ語に異なる読みが指定された場合の診断、元の表記・読み・出現箇所の保持を変更しない。

### 適合性と宣言

6.1は、規定された照合方法と照合規則を少なくとも一つずつ実現し、規定と同じ比較結果を返すことを求めている。選択した方式の一部の比較例が一致しただけでは、規格への適合を主張できない。

今回の報告では「部分適合」を認定のように使わず、「JISを参照し、確認した範囲・一致点・差異・未確認事項を示す」と記す案を推奨する。全面適合を長期的な目標とする合意は維持する。

6.2に対応して、符号化方法、有効文字列長の上限、追加クラス・文字と順序・属性、マクロン・サーカムフレックス付きラテン文字の扱い、漢字クラスを整理する必要がある。代表読み照合に固有の定義事項は、著者指定の読みを使う今回の対象外とする。調査候補で未確定の項目を、製品の保証値として埋めない。

## 4. Node.js・ICU・Intlで指定できる範囲

| 対象 | 静的調査で確認した内容 | 制約・次の確認 |
|---|---|---|
| 感度 | 対象版のV8は`variant`をICUの第3レベルへ設定する（J11） | ICUが平仮名・片仮名の区別に使う第4レベルに達しない（J05）。実際の各組の比較結果は未測定 |
| ロケール拡張 | ECMA-402の関連キーは`co`・`kn`・`kf`。対象版のV8もこの3個を使う（J10・J11） | ICUの任意のオプションをロケール名に付けて有効にできるわけではない。`ks`指定による第4レベルの有効化は候補にしない |
| 数字 | `numeric: false`を指定できる | 自然順の数値比較を求める候補にはしない。実際の文字列比較は実験で確認する |
| 記号 | `ignorePunctuation: false`は対象版でICUのNON_IGNORABLEへ対応する | 記号を無視しないことと、JISの記号クラス内の順序が一致することは別 |
| 正準等価 | ECMA-402の要求があり、対象版のV8もICUの正規化を有効にする | 元の入力文字列を書き換える理由にはしない |
| 解決結果 | `resolvedOptions()`でロケール・感度等を記録できる | 内部の全規則や漢字クラスへの適合を示す情報ではない。実装・データの版も記録する |

したがって、手順2の設定を維持して比較する価値はあるが、JIS基本照合規則の完全な代替とは扱えない。特に「ああ／アア」は差異が生じると予想する。これは資料とコードからの予測であり、比較実験の結果ではない。

## 5. 比較候補と負担

| 候補 | 規格との関係・想定する負担 | 推奨する扱い |
|---|---|---|
| A：既存の`Intl.Collator`で読み単体、同じ設定で読み→表記を比較 | 依存の追加は不要。規格との差異と実行環境への依存が残る。読みの同順位判定がJISと違えば、表記比較へ進む条件も違う | 最初の比較実験の候補とする |
| B：読みの比較はA、表記をJISの漢字順等で別途比較 | 対象範囲、5文字の優先順、符号位置とUTF-16の違い、漢字以外との比較を定義する必要がある。読み側の差異は残る | 今回は実装しない。Aの結果から必要性を判断する |
| C：JISを実現する別の既存実装、またはICUを直接操作する構成 | 既存実装の版・文字範囲の検証、別ランタイムやネイティブ連携等の導入・配布・運用負担を評価する必要がある | 全面適合へ進む際の再調査候補とし、導入は別途相談する |

Aでは、手順書の読み比較設定を表記にも使う案とする。採用は未確定であり、製品仕様にも昇格させない。同順位なら、読み単体では読み比較の後、読み→表記では両キー比較の後に、構成で指定した原稿順・原稿内出現順を使う既存方針を維持する。

## 6. 期待値を具体化するための案

次表は比較実験前の相談材料であり、合意済みの期待値ファイルではない。基本照合規則を基準とし、ASCIIの英数字・ハイフン・プラス等を規格の該当文字へ対応付ける前提も、検証計画に明記する必要がある。`<`は先に並ぶ、`=`は照合上の同順位を表す。

| 既存の比較例 | 期待値の案・判定の扱い | 根拠 |
|---|---|---|
| あい・あお・いち | あい < あお < いち | 4.1・4.4.10の基底文字列 |
| は・ば・ぱ | は < ば < ぱ | 4.4.10.2の清濁 |
| あー・あぁ・あゝ・ああ | あー < あぁ < あゝ < ああ | 4.4.10の長音・繰返しの基底文字と記号種別 |
| ああ・アア | ああ < アア | 4.4.10.2の仮名種別 |
| いちじょうほう・いちしようほう | いちしようほう < いちじょうほう | 基底文字列が同じになり、先に相違する「し／じ」の清濁で決まる（4.1・4.4.10） |
| が／か＋結合濁点 | 同順位。ECMA-402の判定対象とし、JIS判定とは分ける | J10の正準等価性 |
| テスト／ﾃｽﾄ、ガ／ｶﾞ、API／ＡＰＩ、2／２ | 観測対象 | 全半角をJISの文字へ対応付ける前提を未確定として残す |
| api／API | api < API | 4.4.9の大小属性 |
| API2／API10 | API10 < API2 | 4.1・4.4.7の文字単位の比較 |
| APITest／API-Test | API-Test < APITest | 4.3のクラス順と文字対応の前提 |
| C／C++ | C < C++ | 4.1の接頭辞と文字列長 |

読み→表記については、次を追加する案とする。

| 入力の案 | 独立した期待値・確認する内容 |
|---|---|
| 児島・小島、どちらも読みは「こじま」 | 基本漢字クラスでは児島 < 小島。5.2の読み・表記照合の例と4.4.11を根拠にし、表記比較へ進むことを確認する |
| 亜（U+4E9C）・一（U+4E00）、読みは比較用に同一とする | 基本漢字クラスでは亜 < 一。J14の対応では亜は16区1点、一は16区76点であり、4.4.11の区点順から定める。符号位置順では一 < 亜となるため、両順序を見分けられる |
| 〃（U+3003）・仝（U+4EDD）・々（U+3005）・〆（U+3006）・〇（U+3007）・亜（U+4E9C）、読みは比較用に同一とする | 基本漢字クラスでは、この列挙順。4.4.11の先頭5文字の順序と、その直後に通常漢字が続く関係を確認する。文字対応はJ14を参照する |
| 𠮷（U+20BB7）・亜（U+4E9C）、読みは比較用に同一とする | J14に掲載されない𠮷を、基本漢字クラス外の入力候補とする。まず候補実装の結果と元の項目が保持されることを観測する。規格上の追加文字の定義や範囲外文字の処理を確定するまで、両者の前後・同順位にJISの期待値を付けない |
| 表記を合成済みのが／か＋結合濁点とし、読みは同一にする | 両キーが同順位となる条件をECMA-402から定める。文字列として異なる項目を保持し、出現順を使うことを確認する |
| ああ／アアを読みとして持ち、表記は別の語にする | JISでは読みで順位が決まる組を用い、候補が読みを同順位としたときに表記比較へ進む影響を分けて記録する。具体的な表記と全体の期待値は計画具体化時に定める |

漢字クラスの確認で読みを同一にするのは、表記比較へ確実に進むための調査用条件であり、自然な読みを指定する例ではない。追加した3組は、順序の違い、先頭5文字と通常漢字の境界、範囲外の入力を少数で確認する案とし、クラス全体の検査には広げない。J14は歴史的な対応表で、対応が一意・普遍的だとは扱わない。上記の文字対応を実験の前提として明記する案であり、製品全体の符号化・対応方針の確定ではない。

入力データ、比較処理、独立した期待値、判定の根拠は分けて保存する。元の文字列と出現箇所を保持する検査、手順2の項目同一性・診断を壊さない検査も、具体的な検証計画に含める。

## 7. 次に合意する事項

1. JISの比較基準を「読み・表記照合と基本照合規則」、漢字は基本漢字クラスとする案。
2. 最初の実験は候補Aとし、読み・表記に同じ設定を使って差異を測る案。第4レベルを補う処理や別の照合エンジンは追加しない。
3. 正準等価性はECMA-402で判定し、全半角4組はまず観測対象とする案。規格上の文字対応や追加文字をどこまで確定するか。

合意後に、比較方法、追加入力、コードポイント、期待値の根拠と適用条件、情報保持の検査項目を検証計画へ具体化する。その計画の独立レビュー、必要な修正・再レビュー、二人の確認、開発者のコミットと着手依頼を経て比較実験へ進む。手順3全体の完了や、候補の採用を今回の追加調査だけで決めない。
