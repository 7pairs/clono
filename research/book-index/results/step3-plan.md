# 手順3の比較実験計画

2026-10-23（日本時間）。[手順書0006](../../../docs/plans/0006-investigate-book-index.md)の手順3を具体化した計画。[調査の入口](../README.md)・[追加調査](step3-research.md)・[参照資料](../sources.md)。チャット上の草稿の独立レビュー、指摘への対応と再レビューを経て、開発者の依頼でファイルに反映した。その後、開発者のコミットと着手依頼を受けて比較実験・検証を実施し、成果物の独立レビューと二人の確認を終えた。手順3完了。[実験結果と合意内容](step3.md)を参照する。

## 1. 目的と比較基準

著者が指定した読みと表記を、Node.js標準の`Intl.Collator`で並べ替えた場合の順序を確認する。規格との一致点・差異、同順位になる条件、情報を保持できる範囲を説明できるようにする。

比較基準は、JIS X 4061:1996の基本照合規則と基本漢字クラスとする。読み→表記の比較は、同規格5.2の読み・表記照合を基準とする。

正準等価な文字列の同順位はECMA-402に基づいて判定する。全半角や基本漢字クラス外の文字など、規格上の対応条件を確定していないものは観測対象とする。

対象の比較例がすべて一致することや、規格全体への適合は完了条件にしない。独自の照合規則、別の照合エンジン、依存パッケージは追加しない。

## 2. 比較方法と入力の扱い

読みと表記の両方に、次の設定を使う。

```javascript
new Intl.Collator('ja', {
  usage: 'sort',
  sensitivity: 'variant',
  numeric: false,
  ignorePunctuation: false,
});
```

元の文字列をそのまま渡す。平仮名化、全半角変換、NFC・NFKC等の事前変換、清濁・小書きの除去は行わない。

| 構成 | 比較手順 |
|---|---|
| 読み単体 | 読みを比較し、同順位なら最初の出現順を維持する |
| 読み→表記 | 読みを比較し、同順位なら表記を比較する。両方が同順位なら最初の出現順を維持する |

出現順は、指定した原稿順と各原稿内の出現順による。これは調査用の暫定方針であり、JISの規則とは扱わない。

比較結果は符号で扱い、負・ゼロ・正に分類する。戻り値が必ず`-1`・`0`・`1`になるとは仮定しない。

各入力には元の文字列とコードポイント列を記録する。期待値の根拠に使う文字対応は、今回の実験の前提として明記する。

- 仮名・英字・数字は、入力表に示す文字を規格の対応する文字として扱う。
- ASCIIのハイフンマイナス`U+002D`はハイフン、プラス`U+002B`は加算記号として対応付ける。この条件付きの判定であることを結果にも残す。
- 漢字と先頭5文字の対応は、参照資料J14の該当箇所を使う。
- 全半角の互換文字、結合表現、クラス外の文字まで、この対応を拡張しない。

## 3. 文字列単体の比較

既存14組を維持する。順序を示した組では、組内の異なる文字列の全組み合わせを両方向で比較する。各文字列と自身の比較も確認する。

`<`は先に並ぶこと、`=`は照合上の同順位を示す。

| ID | 入力と期待値 | 判定の根拠 |
|---|---|---|
| R01 | あい < あお < いち | JIS 4.1・4.4.10 |
| R02 | は < ば < ぱ | JIS 4.4.10.2の清濁 |
| R03 | あー < あぁ < あゝ < ああ | JIS 4.4.10の基底文字と記号種別 |
| R04 | ああ < アア | JIS 4.4.10.2の仮名種別 |
| R05 | いちしようほう < いちじょうほう | JIS 4.1・4.4.10。基底文字列が一致し、「し／じ」の清濁で決まる |
| R06 | が（`U+304C`） = か＋結合濁点（`U+304B U+3099`） | ECMA-402の正準等価性 |
| R07 | テスト ／ ﾃｽﾄ | 観測のみ |
| R08 | ガ ／ ｶﾞ | 観測のみ |
| R09 | API ／ ＡＰＩ | 観測のみ |
| R10 | api < API | JIS 4.4.9の大小属性 |
| R11 | 2 ／ ２ | 観測のみ |
| R12 | API10 < API2 | JIS 4.1・4.4.7の文字単位の比較 |
| R13 | API-Test < APITest | JIS 4.3と、第2節の文字対応条件 |
| R14 | C < C++ | JIS 4.1と、第2節の文字対応条件 |

期待値は入力・比較処理から分けて保存し、規格の条項と前提から手書きする。候補実装の結果や、その結果を整列した一覧から生成しない。

R07～R09・R11には、前後・同順位の期待値を置かない。実測結果と、判定を保留する理由を保存する。

## 4. 読みと表記を組み合わせた比較

各ケースを独立した入力として収集する。異なるケースで同じ語に別の読みを指定しても、一つの原稿群として混在させない。

「比較用の同一読み」はすべて「ひかく」とする。自然な読みの例ではなく、表記比較へ進むための条件として使う。

| ID | 項目と読み | 確認する結果 |
|---|---|---|
| K01 | 児島・小島、読みは両方「こじま」 | 読みは同順位。読み→表記では児島 < 小島。JIS 5.2・4.4.11 |
| K02 | 亜（`U+4E9C`）・一（`U+4E00`）、比較用の同一読み | 読み→表記では亜 < 一。16区1点と16区76点を根拠とし、符号位置順との違いを確認する |
| K03 | 〃・仝・々・〆・〇・亜、比較用の同一読み | 読み→表記では列挙順。JIS 4.4.11の先頭5文字と通常漢字の関係を確認する |
| K04 | 𠮷（`U+20BB7`）・亜、比較用の同一読み | 表記の比較結果は観測のみ。両項目と出現箇所を保持する |
| K05 | 合成済みのが・か＋結合濁点、比較用の同一読み | ECMA-402に基づき両キーとも同順位。異なる項目として保持し、出現順を維持する |
| K06 | 一の読みを「ああ」、亜の読みを「アア」とする | JISでは読みで一 < 亜が決まる。候補が読みを同順位にした場合、表記比較へ進む影響を記録する |

K02・K03の文字対応はJ14、順序はJIS 4.4.11を根拠とする。K04ではクラス外文字の追加定義等が未確定のため、JISの順位を期待値にしない。

各ケースは、記載順と逆順の2通りで入力する。読み単体では同順位の項目が入力順を維持し、読み→表記では必要な場合に表記で並ぶことを確認する。

K05はさらに2原稿へ分けて配置し、原稿順の交換によって最終的な出現順が入れ替わることを確認する。

K06では、読みの比較結果、表記比較を実施したか、表記の比較結果、最終結果を別々に記録する。JIS上の読みの同順位と、候補実装上の同順位を混同しない。

## 5. 情報保持と比較処理の検査

手順2の収集処理と成果物を基準にする。収集処理が返す項目はすでに読み順へ整列されているため、各項目の最初の出現箇所から出現順を復元し、その順にした複製へ2方式の比較を適用する。

原稿や収集結果を、比較のために直接書き換えない。

| ID | 検査項目 |
|---|---|
| P01 | 読みの結果がゼロ以外なら、表記比較へ進まず、その順位を使う |
| P02 | 読みがゼロなら、読み→表記の構成でだけ表記比較へ進む |
| P03 | 読み単体では読みの同順位、読み→表記では両キーの同順位の場合に、出現順を維持する |
| P04 | 語と読みが完全一致する複数の指定を一項目へまとめ、すべての出現箇所を保持する |
| P05 | 読みや表記の比較結果が同順位でも、文字列として異なる項目を統合しない |
| P06 | 同じ語への異なる読みの指定と、読みの指定漏れを引き続き検出する |
| P07 | 元の語・読み・原稿名・位置・出現箇所IDを、比較前後で保持する |
| P08 | 手順2の既存検査を再実行し、通常の本文やコード内の記法例の保持、既存の診断を確認する |

P06には、同じ語へ「が」と「か＋結合濁点」を読みとして指定するケースを含める。照合上は同順位でも完全一致ではないため、不一致として検出することを確認する。

比較手順の分岐は、比較結果を制御できる検査用の比較関数でも確認する。これは処理の検査にだけ使い、JISの期待値の根拠にはしない。

## 6. 実施順序と結果の判定

1. 合意済みの入力・期待値・根拠・適用条件をデータ化し、確認した計画と照合する。
2. P01～P07の検査コードを作り、比較処理が未実装の状態で、狙った機能不足によって失敗することを確認する。
3. 調査用の比較処理を最小限追加し、処理の検査と手順2の既存検査を通す。
4. R01～R14・K01～K06を実行し、両方式の結果を保存する。
5. 期待値のある比較に一致・不一致を付け、観測対象は結果だけを記録する。
6. 同順位になった組、比較段階の違い、用途上の影響を確認する。

規格との不一致と、調査処理の不具合は分ける。

- JISとの不一致は候補の特性として記録し、一致させるための処理をその場で追加しない。
- ECMA-402に基づく期待値との不一致は要調査として残し、入力・環境・検査の誤りを確認してから結果を評価する。
- 分岐、出現順、情報保持、既存診断の検査が失敗した場合は、結果を確定しない。調査処理を修正して再検証する。

期待値を変更する必要が分かった場合は、実測結果から合わせ込まず、根拠と変更理由を相談してから扱いを決める。

この実験では組版やPDF生成を行わない。手順2の生成物は比較前の基準として保持する。

## 7. 環境・成果物・再現方法

手順2と同じNode.js 24.22.0と固定済みの依存環境を使う。新しい依存や別ランタイムは導入しない。

実行前に、Node.jsが24.22.0であることと、指定した`Intl.Collator`が日本語ロケールへ解決されていることを確認する。日本語ロケールの確認は、`resolvedOptions().locale`を`Intl.Locale`で解釈した`language`が`ja`であることによる。解決されたロケール名の完全一致は要求しない。

前提と異なる場合は、実際の環境情報と差異を記録し、基準環境としての比較実験を開始しない。別環境で比較する必要がある場合は、扱いを二人で相談してから進め、基準環境の一致・不一致判定へ混在させない。

実行時には次を記録する。

- Node.js・V8・ICU・CLDR・Unicodeの版。
- OSとアーキテクチャ。
- 指定したロケール・オプションと`resolvedOptions()`。
- 実行前の環境確認結果。前提と異なる場合は、その差異と基準環境の比較実験を開始しなかったこと。
- 実行コマンド、入力・期待値データの識別情報。

成果物は既存の索引調査ディレクトリに追加する。次の役割で分ける。以下の入力・コード・出力ファイルは実験時に作成するものであり、計画のファイル化時点では未作成。

| 配置案 | 内容 |
|---|---|
| fixtures/collation-cases.json | 入力、コードポイント、原稿順・出現箇所 |
| fixtures/collation-expected.json | 独立した期待値、条項、前提、判定区分 |
| scripts/compare-collation.mjs | 比較の実行と結果保存 |
| scripts/collation.test.mjs | 比較手順・情報保持の検査 |
| results/step3-comparisons.json | 比較段階別の実測結果と判定 |
| results/step3.md | 結果の説明、制約、負担、再現方法 |

実行方法は[調査の入口](../README.md)で示す既存の調査環境を作業場所とし、次を基本とする。実験用のコードと入力を作成した後に実行する。

```sh
node --test scripts/index.test.mjs scripts/collation.test.mjs
node scripts/compare-collation.mjs
```

結果には、ケースID、元の文字列・コードポイント、読みと表記の個別結果、表記比較の実施有無、最終順位、期待値、判定根拠を残す。

機械可読な結果と説明文の対応を確認し、規格に一致した比較、不一致、観測のみ、未確認事項を報告する。

## 8. レビューと完了の確認

比較実験前に、本計画とテスト項目の独立レビュー、必要な修正・再レビュー、二人の確認、文書反映を済ませる。開発者のコミットと着手依頼を経て実験を開始する。

実験後は、次を確認して成果物の独立レビューへ進む。

- 対象ケースを実行し、結果と根拠を辿れる。
- 比較手順・情報保持・既存診断の検査が通っている。
- 同順位と項目の同一性を区別できている。
- 規格との差異、観測対象、未確認事項を説明できる。
- 標準APIで済む範囲と、残る不足・負担を整理できている。

製品のソート仕様や、追加処理を採用する判断は、結果を二人で確認してから行う。
