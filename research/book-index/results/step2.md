# 手順2：索引の必須機能の検証結果

2026-10-22（日本時間）。[手順書0006](../../../docs/plans/0006-investigate-book-index.md)の手順2について、実装と検証を実施した。独立レビューの必須修正1件と再レビューの任意改善1件に対応し、再検証・再レビューと二人の確認を終え、手順2完了とした。手順3以降は未着手。

## 1. 結果

最小限のAST補助で語・読み・出現箇所を収集し、巻末索引のリンク一覧を生成できた。ページ番号の計算と段組みはVivliostyle・CSSへ任せた。4構成すべてで4項目・7出現箇所を保持し、計16ページ・28リンクの表示番号、原稿、ID、飛び先のページと位置、ノンブルを独立した期待値と照合した。

| 構成 | Android | 位置情報 | API | テスト | 結果 |
|---|---|---|---|---|---|
| 本文A・B、2列 | 1 | 1, 1, 3 | 3 | 2, 3 | 一致 |
| 本文B・A、2列 | 2 | 1, 2, 2 | 1 | 1, 3 | 一致 |
| 本文A・B、3列 | 1 | 1, 1, 3 | 3 | 2, 3 | 一致 |
| 本文A・B、4列 | 1 | 1, 1, 3 | 3 | 2, 3 | 一致 |

索引の順序はAndroid、位置情報、API、テスト。ページ番号は`target-counter(attr(href), page)`で表示し、JavaScriptでは計算していない。同一ページの参照は、合意どおり重複を残した。

全ページをPNG化し、構成ごとの一覧画像と索引ページの原寸画像を目視した。文字欠け、重なり、不要な白紙ページ、ノンブルの欠落は見つからなかった。3列指定では4項目が2項目ずつ最初の2列へ入り、3列目が空いた。列間隔と配置は3列の幅に一致し、4項目とも存在する。短い索引で指定列数すべてが埋まるとは限らない。

## 2. 処理と責務

[AST補助](../scripts/index.mjs)は、採用済みのremark経路で本文の`textDirective`だけを収集する。語・読みは加工せず保存し、比較用のキーを別に持つ。同じ語と読みの完全一致で項目をまとめ、同読み異語は分ける。同順位は、指定した原稿順・原稿内の出現順を維持する。入力ファイルは書き換えない。

本文の指定は出現箇所ごとのspanへ置き換える。IDは原稿の識別子と出現順から作り、原稿順を交換しても同じ箇所のIDを保つ。索引生成はそのIDへのリンクを列挙する。[組版スクリプト](../scripts/build.mjs)は変換と検査、実験用のCLI呼び出しを接続する。

これは調査用の処理である。原稿名は重複しないASCIIの識別子、索引ラベルは装飾のない文字列に限定し、それ以外はエラーにする。今回のIDは原稿内へ指定を挿入・削除した後も同じとは保証しない。製品の入力記法、ID方式、API、組版を呼ぶ責務は確定していない。

## 3. 検査と診断

| 観点 | 検査と結果 |
|---|---|
| 収集 | 手書きの[固定期待値](../fixtures/expected.json)と語・読み・原稿・ID・項目順を照合。4項目・7箇所が一致 |
| HTML | 収集結果とは別に、固定期待値からspanと索引リンクを検査。全構成で一致 |
| PDF | [検査コード](../scripts/verify-pdfs.py)が実際のリンク矩形内の数字、表示項目、名前付き参照先の原稿・ID・ページと、本文座標から得た各出現箇所の固有の文脈を照合。ノンブルとページ識別文字も一致 |
| 同読み異語 | 橋・箸を別項目として保持。同順位で原稿順を交換する検査も成功 |
| 読みの不一致 | 両方の原稿名・行・列・読みを含むエラーを検出 |
| 読みの指定漏れ | APIの読みが未指定の場合、原稿名・行・列とreading必須のエラーを検出 |
| 本文保持 | 通常の本文・強調・インラインコード・コードブロック内の記法例をHTMLで確認。索引指定のない語を自動登録しない |
| 検査の対照 | リンク欠落、表示番号の誤り、飛び先ページの誤り、ID重複を模した観測値は4件とも失敗。加えて、名前付き参照先をメモリー内で置換・交換する12ケースも、抽出から判定までの経路で検出 |

不一致の診断例は次のとおり。

```text
位置情報: conflict-a.md:1:1 reading=いちじょうほう; conflict-b.md:3:1 reading=いちしようほう
missing.md:1:1: reading required for API
```

[単体検査](../scripts/index.test.mjs)は、未実装の収集処理で期待する機能不足による5件の失敗を確認してから実装し、5件すべての成功を確認した。失敗・成功ログを保存した。コードブロック末尾の改行はVFM単体でも除かれるため、本文保持の検査では元原稿を直接VFMへ渡したコード内容とも比較した。Markdown再出力のバイト一致は求めず、元原稿の不変と本文・コードの内容保持を区別している。

pdfplumberはフォント記述のFontBBoxについて警告を出した。検査を無効化せず、座標・文字・リンクの照合はすべて成功した。表示の確認はPoppler画像でも実施した。既存の負の対照4件は、観測値を変更した判定部分の検査である。追加した12ケースは、PDF読み取り後の名前付き参照先だけをメモリー内で変更し、文字抽出と文脈の判定まで実行する。PDFをファイルへ書き直す検査はしていない。

## 7. 初回独立レビューと指摘対応

開発者の依頼を受け、会話履歴を引き継がないレビュアー（こはく）が手順2の成果物全体を確認した。必須修正1件、任意改善なし。開発者とそらは指摘を採用し、修正依頼を受けて対応した。再レビューと二人の完了確認は未実施。

指摘は、同一ページの位置情報2箇所を取り違えてもPDF検査が成功するという検査上の不足だった。以前は座標付近の本文が語で始まるかまでしか確かめておらず、各出現箇所を区別できていなかった。現存PDFでは両箇所の座標と本文が正しく分かれていることを、レビュアーが別途確認した。

固定期待値に7出現箇所それぞれの固有の文脈を手書きで追加した。例えば位置情報の2箇所は「位置情報を調べる。」「位置情報をもう一度確認する。」で区別する。参照先座標から抽出した本文との一致を検査し、抽出した文字列もPDF観測値に保存する。

PDF抽出では「一」が互換文字「⼀」になるため、期待する文脈と抽出した文脈に限り、Unicode NFKCで比較する。元の原稿・索引語・読み・並べ替えキーは変更しない。これはPDFの内容検査のための比較処理であり、手順3の読みの照合方法を決めるものではない。

[追加検査](../scripts/verify-pdfs.test.py)は、各構成の名前付き参照先について、2箇所目を1箇所目へ、1箇所目を2箇所目へ、両箇所の交換の3通りを試す。4構成で計12ケースを実行し、PDF・観測記録への書き込みをせずに、通常の抽出と判定の経路へ渡す。

- 修正前：[失敗ログ](logs/destination-context-red.txt)で、12ケースとも想定した例外が出ず、見逃しを再現した。
- 修正後：[成功ログ](logs/destination-context-green.txt)で、12ケースすべてを固有の文脈の不一致として検出した。
- 正常系：[PDF検査ログ](logs/pdf-verification.txt)で4構成・16ページ・28リンクと既存の負の対照4件が成功した。ASTの単体テスト5件も再実行して成功した。
- 出力の不変：4つのPDFは変換時の記録・再検査記録・実ファイルのSHA-256が一致した。原稿、生成処理、CSS、依存、PDFは変更せず、再組版や画像の再生成は行っていない。
