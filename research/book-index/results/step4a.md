# 手順4A：ページ集約の方式と負担

2026-10-23（日本時間）。[手順書0006](../../../docs/plans/0006-investigate-book-index.md)の手順4A。[調査の入口](../README.md)・[手順2の結果](step2.md)。既存PDFからのページ対応取得と、集約後に残すリンク一覧の作成・検証を実施し、初回独立レビューの必須修正1件に対応した。再検証・再レビューと二人の確認を終え、4A完了。[4Bの計画](step4b-plan.md)も内容確認・レビュー済みで、コミットと着手依頼を受けて実施する。4Bにはまだ着手していない。

## 1. 結果

手順2の4つのPDFから、原稿・出現ID・物理ページの対応を全28箇所について取得できた。各索引項目の出現順に参照を走査し、同じページでは最初の参照を残すことで、各構成7リンクを6リンクへ集約できた。HTMLやPDFは再生成していない。

| 構成 | Android | 位置情報 | API | テスト | リンク数 |
|---|---|---|---|---|---|
| base-2 | 1 | 1, 1, 3 → 1, 3 | 3 | 2, 3 | 7 → 6 |
| swapped-2 | 2 | 1, 2, 2 → 1, 2 | 1 | 1, 3 | 7 → 6 |
| base-3 | 1 | 1, 1, 3 → 1, 3 | 3 | 2, 3 | 7 → 6 |
| base-4 | 1 | 1, 1, 3 → 1, 3 | 3 | 2, 3 | 7 → 6 |

4構成とも、位置情報のa.html#idx-a-2を同じページのa.html#idx-a-1へ集約した。swapped-2ではb.html#idx-b-1を先頭に残し、a.htmlのページ2の2箇所を一つにした。別ページの参照や、同じページにある別項目の参照は保持した。

根拠は[対応表と集約前後の全参照](step4a-pages.json)。削除候補にも、元の原稿・位置・ID・ページ、代わりに残す原稿・IDを記録している。元の収集情報やPDF内のリンクは削除していない。

## 2. 方式と依存

[ページ対応・集約処理](../scripts/page_aggregation.py)では、既存のpypdfを使い、実際のPDFの名前付き参照先を読む。今回観測した/viv-id-接頭辞と:XXXXの符号化を復号し、URLの原稿名とフラグメントIDを照合する。IDだけで別原稿の参照を同一視しない。

ページ番号はpypdfが取得する0始まりのページ位置へ1を足した物理ページとする。今回の本は先頭から連続するノンブルと一致する。PDFのPageLabelsや、ローマ数字・前付けによる番号体系の違いは扱わない。

索引項目の語と読みは手順2の収集結果を使う。語・読みの完全一致で既にまとめられた項目の内部でだけページを集約し、別の項目との比較・正規化は行わない。並び順と全出現箇所は維持し、残すリンクの一覧を別に作る。

収集情報はGit管理しているstep2-conversion.jsonから読むが、ページ対応は保存済みのstep2-pdf.jsonを流用せず、毎回実際のPDFから取得する。手順2で検査済みのPDFであることを、変換記録・PDF検査記録・実ファイルの3者のハッシュ一致で確認する。元原稿のハッシュも確認する。

追加依存、Core改変、別ランタイムの導入は不要だった。指摘対応後はページ対応・集約が67行、実行・独立した期待値との照合・結果保存が68行、検査が140行のPythonコードとなった。処理対象は名前付き参照先と全出現箇所で、組版回数は増やしていない。

## 3. 検査

[独立した期待値](../fixtures/page-aggregation-expected.json)は、手順2の固定ページ配置と原稿順、今回の集約規則から手書きした。抽出したページ対応や集約処理の出力からは作成していない。残すリンクと除くリンクの両方を原稿・ID・ページで指定した。

[検査コード](../scripts/page-aggregation.test.py)を先に作り、未実装のページ対応・集約処理で7検査、サブケースを含む12件のNotImplementedErrorを確認した。実装後は7検査すべて成功した。[未実装時のログ](logs/step4a-red.txt)・[成功ログ](logs/step4a-green.txt)を保存している。

| 観点 | 検査と結果 |
|---|---|
| 実PDFの対応 | 4構成・全28箇所の原稿・ID・物理ページが独立した期待値と一致 |
| 集約の範囲 | 同一項目・同一ページだけを集約し、残す6リンクと除く1リンクが一致 |
| 項目の同一性 | 同じページの同読み異語、異なる読みを持つ項目を別々に保持する単体検査が成功。収集段階の同語異読みの診断方針を変更したものではない |
| 原稿の区別 | 異なる原稿に同じフラグメントIDを置く対照でも、原稿別に正しいページを取得 |
| 対応不足 | 複数の対応欠落を、原稿名とIDを含むエラーで検出。途中までの集約結果を成功として返さない |
| 名前付き参照先 | 実PDFをメモリー上で欠落・未対応形式・曖昧な別名の3通りに変え、いずれも対象の原稿・IDを示すエラーとして検出 |
| ページ値 | 無効な物理ページの対照を検出 |
| 不変性 | 集約で入力項目を変更しないこと、実行前後でPDF・元原稿・既存記録のハッシュが変わらないことを確認 |

同じPDFの参照先が同一ページ内で別の位置に入れ替わる問題は、手順2で文脈照合済みのPDFとハッシュが同じことを前提にしている。今回のページ集約は座標や本文の文脈を再検査するものではない。再組版する4Bでは、最終PDFを独立に検査する必要がある。

不足・曖昧さ・形式の違いを推測で補わず、対応取得に失敗した場合は終了する。指摘対応後はmain()の先頭で最小限のrunning-not-finalを保存し、その後に入力のハッシュ取得・読込みを行う。全構成の照合が済んでからverifiedとする。入力読込み前の失敗でも、古い成功結果が残らないことを検査した。出力先自体に書き込めない場合や、Python起動・モジュール読込み前の失敗まで保証するものではない。

## 4. 負担と制約

PDF読込み、名前付き参照先の解析、集約までの計測区間は、指摘対応後の保存実行でbase-2が約10.12ms、swapped-2が約9.60ms、base-3が約9.60ms、base-4が約9.31msだった。ハッシュ取得、期待値との照合、最終JSON書出しは含まない。小さな4ページの本に対する観測であり、大量項目の性能保証ではない。

実装・運用上の主な制約は、Viewer・Chromiumが生成する名前付き参照先の私的な形式への依存である。これはVivliostyleが公開する索引向けの安定APIではない。現環境では4構成とも同じ方式で取得できたが、バージョンを更新した場合は再確認が必要。今回のPDFのCreatorはCore 2.45.1・Chrome 153.0.8010.36で、現在のChromeを更新しても既存PDFを読む今回の結果は変わらない。

原稿名は既存調査と同じ、重複しないASCIIの識別子に限る。任意のディレクトリ構造、同名原稿、別の名前付き参照形式、任意のPDFへの一般化はしていない。物理ページとノンブルの対応も、合意済みの連番前提に限る。

4Bで必要なのは、今回の残すリンク一覧を索引HTMLへ反映して一度だけ追加組版し、最終PDFを検査する工程である。本文のページ対応が変わったときに反復する仕組みや、Viewer内部の改変は不要な範囲を検証対象とする。実現可能性は確認できたが、追加組版の時間と検査・版依存を含めた製品上の負担はまだ評価し切れていない。
