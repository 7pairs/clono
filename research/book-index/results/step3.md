# 手順3：読み・表記の比較実験結果

2026-10-23（日本時間）。[手順書0006](../../../docs/plans/0006-investigate-book-index.md)・[比較実験計画](step3-plan.md)・[追加調査](step3-research.md)・[参照資料](../sources.md)。開発者のコミットと着手依頼を受け、合意した比較実験を実施した。実装・検証を実施済み。成果物の独立レビューと二人の確認は未実施であり、手順3完了とは扱わない。

## 1. 結論

標準の`Intl.Collator`で、今回の基本的な読み順、清濁、長音・小書き・繰返し、英字の大小、数字や記号を含む比較を実行できた。読み単体と読み→表記を分け、元の項目と出現情報を保持する処理も成立した。

一方、JISとの不一致をR04・K03・K06で確認した。平仮名・片仮名が同順位となり、そのため読み→表記ではJISなら読みで順位が決まる組も表記比較へ進んだ。また、基本漢字クラスの先頭5文字を含む順序も、今回の候補とは異なった。標準APIの設定だけで、比較基準のすべてを満たしたとは言えない。

全面適合や製品仕様は確定していない。これらの差異を用途上許容するか、別の対応が必要かは、結果を二人で確認して判断する。独自の補正処理や追加依存は導入していない。

## 4. 読みと表記を組み合わせた結果

次表の並びは各ケースの正順入力に対する結果。読み単体で同順位となる項目は、逆順入力では逆順を維持した。両キーを比較しても同順位となるK05は、両方式とも入力順を維持した。

| ID | 読み単体の並び | 読み→表記の並び | 判定 |
|---|---|---|---|
| K01 | 児島・小島 | 児島・小島 | 読みは同順位。表記の児島 < 小島はJISと一致。逆順入力でも表記比較で児島が先になる |
| K02 | 亜・一 | 亜・一 | 読みは同順位。表記の亜 < 一は基本漢字クラスの区点順と一致。逆順入力でも同じ表記順 |
| K03 | 〃・仝・々・〆・〇・亜 | 〃・々・〇・〆・亜・仝 | 読みは同順位。表記の順序はJISと不一致。逆順入力でもこの表記順 |
| K04 | 𠮷・亜 | 亜・𠮷 | 読みは同順位。表記は観測のみ。両項目を保持 |
| K05 | が・か＋結合濁点 | が・か＋結合濁点 | 両キーとも同順位。ECMA-402の期待値と一致。別項目として保持 |
| K06 | 一・亜 | 亜・一 | ああ／アアが同順位となり、表記比較へ進む。JISは読みで一 < 亜が決まるため不一致 |

K03のJIS基準は「〃 < 仝 < 々 < 〆 < 〇 < 亜」。異なるのは、仝と々・〆・〇・亜との関係、および〆と〇との関係だった。通常漢字の例が一致したK02だけでは分からなかった差を、先頭5文字の追加で確認できた。

K05では、2項目を別原稿へ分けて原稿順も交換した。読み単体・読み→表記の両方で、指定した原稿順と原稿内の出現順を保持した。

K06は、読み単体の正順入力では結果の並びがJIS基準と偶然同じになる。しかし読みの比較自体は同順位であり、JISとは異なる。逆順入力と比較段階の記録から、この違いを確認できた。最終的な一覧の並びだけで一致を判定していない。

## 5. 情報保持と判定の確認

P01～P03では、読みが非ゼロなら表記比較を呼ばないこと、読みがゼロの場合の分岐、両キーが同順位の場合の出現順を確認した。比較関数が-23・71・-42を返す検査も使い、戻り値が±1であることに依存しないようにした。

P04～P07では、語・読みの完全一致による集約、同順位の異なる項目の保持、同語異読みと読み欠落の診断、元の語・読み・sortKey・原稿名・位置・ID・全出現箇所の保持を確認した。元原稿と収集結果が並べ替えによって変更されていないことも比較した。正準等価な「が／か＋結合濁点」を同じ語の読みとして別々に指定すると、従来どおり不一致を検出した。

P08として既存5件を再実行し、本文、強調、インラインコード、コードブロックの記法例の保持と、既存の診断を確認した。組版やPDF検査は再実行していない。

318比較記録の内訳は、一致264・不一致30・観測24。自己比較、逆向き、読み単体と読み→表記、原稿構成違いによる繰り返しを含むため、独立した比較例の数や適合率としては扱わない。不一致のあるケースはR04・K03・K06で、ECMA-402を根拠とするケースの不一致はなかった。

保存結果の照合では、別処理で期待値ファイルの順位から判定を計算し直し、全318記録と集計が一致した。これは保存・判定処理の確認であり、JIS本文の解釈を独立レビューした結果ではない。

## 6. 処理の量と残る制約

比較処理は23行の調査用モジュール、実行・保存・整合検査は147行、検査コードは91行となった。保存した期待順位・判定・ハッシュを照合するPythonスクリプトも残した。既存のindex.mjs、既存テスト、依存とlockfileは変更していない。読み順に並んだ収集結果から、全出現箇所の順を使って項目の最初の出現順を復元し、複製を安定ソートする構成とした。

比較実行の計測区間は今回の一回で約9.85msだった。入力の読込み、収集、比較、整合検査を含み、環境確認とハッシュ取得、最終JSON書出しは含まない。小さな固定入力の保存実行での観測であり、性能保証やベンチマークではない。

今回確認した文字列単体の入力は最大8コードポイント。製品で扱える文字列長の上限は定めていない。ファイルはUTF-8、JavaScript内部はUTF-16文字列として扱い、コードポイント列を併記した。独自の正規化や互換変換は行っていない。

JIS 6.2に関連する漢字クラスは比較基準として選んだもので、候補APIの内部設定として指定したものではない。現代の追加漢字、追加文字クラス、マクロン・サーカムフレックス付きラテン文字、一般の全半角対応、任意長の入力は検証していない。処理系定義事項をすべて満たした宣言や、JISへの適合は主張しない。

独自エンジンや仮名種別だけの補正は追加していない。規格との差異を許容して標準APIを使うか、どの差異に対応する必要があるかは未決定。ページ集約と全体の構造見直しは、既存計画の手順4A以降で扱う。

## 7. 再現方法と現在地

[調査の入口](../README.md)の既存環境を用意し、research/book-indexを作業場所にする。Node.js 24.22.0と日本語ロケールへの解決が実行前条件。新しい依存は不要。

```sh
node --test scripts/index.test.mjs scripts/collation.test.mjs
node scripts/compare-collation.mjs
```

入力は[collation-cases.json](../fixtures/collation-cases.json)、独立した期待値・根拠・条件は[collation-expected.json](../fixtures/collation-expected.json)。期待値は計画から転記し、候補実装の出力から作成していない。元データのコードポイント表現も実行時に照合する。

保存記録の照合も再現する場合は、既存のPython 3で`python3 scripts/audit-collation.py`を実行する。候補APIを呼ばず、保存結果と期待値・ハッシュ・検査ログを照合し、照合記録を出力する。通常の比較実行にPythonは不要。

環境条件が異なる場合は、step3-comparisons.jsonへ差異と未開始の状態を記録し、比較を開始せず終了コード1を返す。条件を満たす実行では実測結果を同ファイルへ保存する。JISとの不一致だけでは失敗終了にせず、ECMA-402に基づく期待値との不一致があれば結果を要調査として保存し、終了コード1を返す。収集・保持・整合検査の失敗は例外として終了し、実験結果を確定しない。実行開始時に出力をrunning-not-finalの状態へ更新するため、途中で失敗しても前回の成功結果が今回の結果として残らない。
